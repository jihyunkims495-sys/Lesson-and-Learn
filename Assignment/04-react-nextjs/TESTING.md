# 인증·데이터 분리 검증

2026-11-16 오류 재시도 개선 전 실연결에서 비밀번호 로그인·두 계정 SDK 검증 24개와 프로덕션 빌드·서버 시작·브라우저 검증 15단계를 통과했습니다. 아래 절차는 개발 환경과 배포 환경에서 확인할 동작을 정리합니다.

1. 실습 DB에 schema-practice.sql 실행 후 실행 환경에 공개키와 URL을 설정합니다. 가입 시 생성되는 practice_profiles와 Todo CRUD의 practice_todos를 대상으로 확인합니다. 이 SQL은 전용 이름이 이미 있으면 덮어쓰기 없이 전체 실패합니다.
2. Supabase Auth URL 설정에 개발/배포 사이트 URL과 각각의 /auth/callback을 추가합니다.
3. 브라우저 1에서 테스트 회원 A 가입·메일 확인·로그인. 할 일 2개 생성, 하나 수정, 완료 체크.
4. 새로고침 후 동일한 데이터가 보이는지 확인합니다. 동적 상세 URL과 존재하지 않는 UUID의 404를 확인합니다.
5. 별도 시크릿 창에서 B 가입·로그인. A의 할 일이 목록에 없어야 합니다. A의 상세 URL을 입력해도 404여야 합니다.
6. B 세션에서 A의 id를 사용해 직접 Supabase 수정/삭제 요청 시 RLS가 차단하는지 확인합니다. 화면 숨김만으로 통과 처리하지 않습니다.
7. 네트워크 연결을 끊은 뒤 저장 실패 메시지·버튼 복구·데이터가 성공으로 오인되지 않는지 확인합니다.
8. 로그아웃 후 /todos 및 상세 URL 접근이 /login으로 이동해야 합니다.
9. 데이터가 없는 신규 계정에서 빈 상태, 첫 페이지 로드 시 loading.tsx, 조회 실패 시 error.tsx 재시도를 확인합니다.

변경은 응답 성공 후 상태에 반영하므로 실패한 쓰기를 화면에 성공으로 표시하지 않습니다. 인증 구독은 useEffect 반환 함수에서 해제합니다. RLS가 실제 데이터 권한의 최종 경계입니다.

비동기 응답 이후 상태가 바뀌는 제어 체크박스는 클릭한 뒤 최종 체크 상태를 기다려 검증합니다. 오류 메시지 선택자는 앱의 main 영역으로 한정하여 프레임워크의 접근성 알림과 구분합니다.

최초 Next.js 16.4.0 빌드는 알려진 취약점으로 중단되어 같은 릴리스 계열의 16.4.6으로 수정했습니다. 최초 HTTP 검사에서 loading.tsx가 있는 경로의 스트리밍 응답(HTTP 200 안의 브라우저 redirect/not-found)을 단순 HTTP 307/404로 가정한 검사를 수정했습니다. 최종 검사는 상태와 본문의 이동·not-found 의미를 함께 확인합니다.

HTTP smoke는 `npm run test:smoke`로 실행합니다. 이 명령 자체는 로컬 loopback URL과 가짜 publishable 값으로 비로그인 경로를 확인합니다. 실제 비밀번호 로그인·Todo CRUD·RLS와 브라우저 흐름은 위의 실연결 검증에서 별도로 확인했습니다. 배포할 때는 해당 환경의 Supabase 공개 설정으로 다시 빌드해야 합니다.

조회 실패 후 재시도는 서버 데이터를 새로 요청하고 오류 경계를 초기화하도록 보완했습니다. `npm run test:ui`가 로컬 모사 응답으로 빈 상태, loading 표시와 해제, error 경계, 재시도 시 새 요청과 복구, 잘못된 로그인 안내와 버튼 복구, 회원가입 요청 형식과 확인 안내를 검사합니다. 실제 가입 메일 발송을 모사 응답으로 검증했다고 판단하지 않습니다.

오류 재시도 개선 후 전체 SDK·브라우저 실연결 회귀는 아직 재실행하지 않았습니다. 위 24개·15단계는 개선 전 검증 시점의 결과입니다.

로그인 가능한 두 계정을 사용했으므로 회원가입 메일의 발송·수신과 인증 callback 교환은 이번 실연결 검증에 포함하지 않았습니다. 토큰 만료를 유도한 갱신, Vercel 배포 및 배포 주소에서의 재검증도 남아 있습니다.

설정 값의 형식 검사와 로컬 PostgreSQL 검증, 실제 Supabase Auth·SDK·브라우저 검증은 서로 다른 범위를 확인합니다.

인증 쿠키를 갱신하는 Proxy는 SDK가 제공하는 캐시 헤더를 응답에 전달하고, 인증 callback의 성공/실패 이동 응답도 저장하지 않도록 설정합니다. `npm run test:auth-cookies`로 이 계약을 검사합니다. 합성 코드 교환은 실제 이메일 수신·확인을 대체하지 않습니다.

스키마 검증은 `./scripts/verify-local-postgres.ps1`로 practice 전용 스키마를 확인합니다. `-Schema original` 옵션은 별도로 보존한 schema.sql 예제의 검증이며 현재 앱의 설치 명령과 구분합니다. practice 전용 스키마는 기존 인증 계정을 자동으로 backfill하지 않으며, 적용 이후 가입 이벤트로 프로필이 생성됩니다.
