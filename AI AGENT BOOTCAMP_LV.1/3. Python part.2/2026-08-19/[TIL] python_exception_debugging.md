# TIL | 2026-08-19 | Python 예외 처리와 디버깅

> **예외처리. 공부에 예외처리는 없나...**

> 오늘은 예외가 발생했을 때 프로그램을 어떻게 처리하고, 문제가 생긴 위치를 어떻게 추적하는지 배웠다. 아직 혼자 처음부터 코드를 작성하기는 어렵지만, 완성된 코드를 읽고 실행 흐름을 따라가는 힘은 조금씩 생기고 있다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- **구문 오류와 실행 중 예외의 차이**
  - `SyntaxError`, `IndentationError`: 코드 문법이나 구조 자체가 잘못되어 실행 전에 발견되는 오류
  - `ValueError`, `IndexError`, `ZeroDivisionError` 등: 문법은 맞지만 실행 중 특정 값이나 상황 때문에 발생하는 예외
- **`try / except / else / finally` 실행 흐름**
  - `try`: 예외가 발생할 가능성이 있는 코드를 실제로 실행하는 구간
  - `except`: `try`에서 발생한 예외를 종류별로 처리하는 구간
  - `else`: 예외가 하나도 발생하지 않았을 때만 실행
  - `finally`: 성공/실패와 상관없이 마지막에 실행되는 공통 마무리 구간
- **`raise`**
  - 예외를 정의하는 문법이 아니라 개발자가 예외를 직접 발생시키는 키워드
  - `raise`가 실행되면 현재 정상 실행 흐름이 중단되고, 예외를 처리할 수 있는 `except`를 찾는다.
- **사용자 정의 예외**
  - `Exception`을 상속받아 새로운 예외 클래스를 만들 수 있다.
  - `Exception`을 상속받은 클래스의 자식 클래스도 예외 계열이 된다.
  - `__str__()`은 예외 객체를 문자열로 보여줄 때 사용할 메시지를 정의한다.
- **`except ValueError as e`**
  - `e`는 특별한 예약어가 아니라 발생한 예외 객체를 잠깐 받아두는 변수다.
- **리스트 인덱싱에 변수 사용하기**
  - `menu[index]`는 새로운 문법이 아니라 `menu[1]`처럼 인덱스 위치에 숫자가 저장된 변수를 넣은 구조다.
- **디버깅 기본 도구**
  - Traceback, Breakpoint, Variables 패널
  - Step Over / Step Into / Step Out / Continue

### 핵심 코드

```python
menu = ["김밥", "라면", "떡볶이"]

try:
    index = int(input("조회할 인덱스 번호를 입력하세요: "))
    result = menu[index]

except ValueError:
    print("숫자만 입력할 수 있습니다.")

except IndexError:
    print("존재하지 않는 위치의 데이터")

else:
    print(f"선택한 메뉴는 {result}입니다.")

finally:
    print("메뉴 조회를 종료합니다.")
```

```python
def set_order(count):
    if count <= 0:
        raise ValueError("주문 수량은 1개 이상이어야 합니다.")

    print(f"주문 수량이 {count}개로 설정되었습니다.")


try:
    set_order(-3)
except ValueError as e:
    print(f"시스템 경고: {e}")
```

### 오늘 수행한 실습

- 메뉴 리스트에서 사용자가 입력한 인덱스로 값을 조회하며 `ValueError`와 `IndexError`가 발생하는 위치를 구분했다.
- `raise`를 사용해 잘못된 주문 수량에서 의도적으로 `ValueError`를 발생시켰다.
- 사용자 정의 예외와 `__str__()`의 기본 역할을 확인했다.
- `ZeroDivisionError`가 발생하는 코드를 실행하고 Traceback의 맨 아래에서 예외 이름과 실제 발생 위치를 역추적했다.
- VS Code에서 Breakpoint를 걸고 Variables 패널로 변수 상태를 확인했다.
- 반복문 누적값을 Step Over로 따라가고, Step Into / Step Out의 차이를 직접 확인했다.
- Jupyter Notebook에서는 `Debug Cell`, 일반 `.py` 파일에서는 파일 전체를 Debug 모드로 실행한다는 차이를 확인했다.

## 2. Why — 왜 필요한가?

### 이 개념이 필요한 이유

- 사용자가 어떤 값을 입력할지는 개발자가 완전히 통제할 수 없기 때문에 실행 중 발생할 수 있는 문제에 대비해야 한다.
- 예외 처리가 없으면 작은 입력 오류 하나로 프로그램 전체가 종료될 수 있다.
- `raise`를 사용하면 파이썬 문법상 정상인 값이라도 서비스 규칙에 맞지 않는 데이터를 개발자가 직접 차단할 수 있다.
- 실제 코드는 길기 때문에 모든 줄을 처음부터 읽기보다 Traceback과 Debugger로 문제 위치와 변수 상태를 좁혀가는 것이 효율적이다.

### 내 생각

> `try-except`는 예외 케이스를 처리하는 Python 키워드 구조라고 이해했다. `try`는 단순히 값을 검수하는 곳이 아니라, 예외가 발생할 가능성이 있는 코드를 실제로 실행해보는 범위다. `except`는 그 안에서 발생한 예외를 종류별로 받아 처리한다. 아직 `raise`는 정확히 내 것이 된 느낌은 아니고 내일이면 잊어버릴 것 같아서 반복학습이 필요하다. 다만 `return`이 함수를 정상적으로 끝낸다면, `raise`는 예외를 발생시키면서 정상 흐름을 끊는다는 차이는 조금 이해했다.

## 3. How — 어떻게 작동하는가?

### 작동 과정

1. `try`에서 예외가 발생할 가능성이 있는 코드를 실제로 실행한다.
2. 예외가 발생하면 `try`의 남은 코드는 실행하지 않고, 일치하는 `except`로 이동한다.
3. 예외가 없으면 `else`가 실행된다.
4. `finally`는 성공 여부와 관계없이 마지막에 실행된다.
5. `raise`를 만나면 개발자가 지정한 예외가 발생하고 현재 정상 실행 흐름이 중단된다.
6. 함수 안에서 발생한 예외를 바깥 `except`가 처리할 수 있다.
7. 문제가 생겼을 때는 Traceback의 맨 아래에서 최종 예외를 먼저 보고 위쪽으로 올라가며 실제 문제 줄과 호출 경로를 확인한다.
8. 더 자세한 흐름이 필요하면 Breakpoint에서 멈추고 Variables와 Step 명령을 이용해 변수 변화를 확인한다.

### 내 말로 설명하기

> 예외 처리는 "문제가 생기지 않게 만드는 것"이라기보다 "문제가 생겼을 때 프로그램이 어떻게 대응할지 정해두는 것"에 가깝다. `try`에서 실제 코드를 돌려보고, 문제가 생기면 `except`가 받아서 처리한다. `else`는 성공했을 때 가는 길이고, `finally`는 어떤 길을 탔든 마지막에 모이는 공통 마무리 구간이다. 디버깅은 예외를 처리하는 문법이 아니라 왜 문제가 생겼는지 찾아가는 과정이다.

## 4. 오늘의 문제 해결

### 문제 상황 1 — 메뉴 조회 예외 처리

- 하려고 했던 것: 사용자가 입력한 인덱스로 메뉴를 조회하고 예외를 종류별로 처리하기
- 발생한 문제: `ValueError`와 `IndexError`가 각각 어느 줄에서 발생하는지 헷갈렸고, `except ValueError(index)`처럼 예외 클래스에 변수를 넣으려고 했다.

### 문제가 발생한 코드

```python
try:
    menu = ["김밥", "라면", "떡볶이"]
    index = int(input("조회할 인덱스 번호를 입력하세요: "))

except ValueError(index):
    print("숫자만 입력할 수 있습니다.")

except IndexError(menu):
    print("존재하지 않는 위치의 데이터")
```

### 문제의 원인

- `except` 뒤에는 변수 값이 아니라 잡고 싶은 예외 클래스 이름을 적어야 했다.
- `IndexError`를 처리하려면 실제로 `menu[index]`를 조회하는 코드가 `try` 안에 있어야 했다.
- `index = int(input(...))`를 `try` 밖에 두면 숫자로 바꿀 수 없는 입력에서 발생한 `ValueError`를 아래 `except`가 잡을 수 없다.

### 해결한 코드

```python
menu = ["김밥", "라면", "떡볶이"]

try:
    index = int(input("조회할 인덱스 번호를 입력하세요: "))
    result = menu[index]
except ValueError:
    print("숫자만 입력할 수 있습니다.")
except IndexError:
    print("존재하지 않는 위치의 데이터")
else:
    print(f"선택한 메뉴는 {result}입니다.")
finally:
    print("메뉴 조회를 종료합니다.")
```

### 해결 원리

> 기준은 "변수냐 아니냐"가 아니라 그 코드에서 내가 처리하려는 예외가 발생할 가능성이 있느냐였다. `int(input(...))`에서는 `ValueError`, `menu[index]`에서는 `IndexError`가 날 수 있기 때문에 둘 다 `try` 안에 둔다.

### 문제 상황 2 — 디버거 버튼과 실행 흐름

- Breakpoint와 현재 실행 위치 표시가 헷갈렸다.
- Step Over / Step Into / Step Out 아이콘을 실제 VS Code 화면에서 구분해야 했다.

### 해결 원리

- Breakpoint: "여기서 멈춰"
- Variables: 멈춘 순간 변수에 어떤 값이 들어있는지 확인
- Step Over: 현재 줄 실행 후 다음 줄, 함수 내부에는 들어가지 않음
- Step Into: 함수 내부로 진입
- Step Out: 현재 함수의 남은 코드를 실행하고 호출한 바깥쪽으로 복귀
- Continue: 다음 Breakpoint까지 계속 실행

> Python Tutor가 학습용으로 코드 실행 흐름을 시각화해주는 도구라면, VS Code Debugger는 같은 사고방식을 실제 개발 코드에 적용하는 실무형 도구라고 연결해서 이해했다.

## STAR 문제 해결 기록

### Situation — 상황

> 사용자 입력으로 메뉴를 조회하는 예외 처리 실습에서 어떤 코드가 `ValueError`와 `IndexError`를 발생시키는지 구분하고 `try-except` 구조를 직접 작성해야 했다.

### Task — 해결 과제

> 입력값 변환 오류와 리스트 범위 오류를 각각 처리하고, 정상 조회와 최종 종료 메시지까지 실행 경로에 맞게 구성해야 했다.

### Action — 실행한 행동

1. 메뉴 데이터, 사용자 입력 인덱스, 조회 결과 변수의 역할을 분리했다.
2. `int(input(...))`와 `menu[index]`에서 각각 발생 가능한 예외를 연결했다.
3. `try → except → else → finally` 실행 경로를 직접 따라가며 코드를 수정했다.
4. Debugger에서는 Breakpoint를 걸고 Step 명령과 Variables 패널을 이용해 실행 흐름을 직접 확인했다.

### Result — 결과

- 해결 결과: `ValueError`, `IndexError`, 정상 조회 세 가지 경로를 구분하여 코드를 완성했다.
- 새롭게 이해한 점: `try`는 불확실한 변수를 검수하는 곳이 아니라 예외 가능성이 있는 실행 코드를 감싸는 구간이다.
- 다음에 같은 문제가 생겼을 때 확인할 것: 먼저 `어느 줄에서 → 어떤 값 때문에 → 어떤 예외가 날 수 있는가?`를 표시하고 그 줄을 `try` 안에 배치한다.
