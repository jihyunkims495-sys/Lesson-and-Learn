# TIL | 2026-11-05 | 공연·회차 의존성 분리와 트랜잭션 유지

> LV.2 · Week 12 · 백엔드 아키텍처 & API 설계

> **회차 서비스가 필요한 공연 기능만 계약으로 정의하고, 기존 잠금·트랜잭션 흐름을 유지하며 wiring을 정리했다.**

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- 서비스 간 의존성을 설계할 때는 상대 서비스 전체보다 실제로 사용하는 기능을 기준으로 계약을 정의할 수 있다.
- `Protocol`은 필요한 메서드의 형태를 정의한다. 실제 객체를 만드는 책임은 wiring에 둔다.
- 여러 서비스가 하나의 요청을 처리할 때는 같은 DB 세션·트랜잭션을 사용하는지 확인해야 한다.
- 인터페이스를 분리했다는 사실만으로 잠금과 트랜잭션이 보장되지는 않는다. 실제 주입 구조와 실행 순서를 검증해야 한다.

### 핵심 코드

회차에서 사용하는 공연 기능 두 가지를 계약으로 정의했다.

```python
from typing import Protocol

from asyncticket.shared.domain.catalog import CatalogActor
from asyncticket.shows.domain.show import Show


class ShowAccess(Protocol):
    async def find_by_id(
        self,
        show_id: int,
        *,
        for_update: bool = False,
    ) -> Show: ...

    async def authorize_owner(
        self,
        show_id: int,
        actor: CatalogActor,
    ) -> Show: ...
```

회차 서비스는 이 계약을 받고, wiring에서는 기존 공연 서비스를 실제 구현으로 주입한다.

### 실제 작성한 코드와 검증 상태

| 구분 | 내용 |
|---|---|
| 작성·수정 | ShowAccess 계약, 회차 서비스 타입, 공통 wiring, 공연·회차 wiring, 회귀 테스트 |
| 검증 방법 | 최소 기능 대역, 실제 wiring을 사용하는 SQLite 테스트, PostgreSQL 방언 SQL 컴파일, HTTP 요청 |
| 확인 결과 | 전체 회귀 62개와 DB 세션 테스트 3개 통과, HTTP 요청 20건 통과 |
| 미완료 | 실제 PostgreSQL 잠금 경합·대기 검증, JWT 인증 연결 |

## 2. Why — 왜 필요한가?

회차 서비스는 공연을 생성·수정·삭제하는 기능까지 사용할 필요가 없다. 공연 존재 확인과 소유권 확인만 요구하도록 계약을 좁히면 두 서비스 사이의 연결 범위를 명확히 할 수 있다.

DB 세션과 정책처럼 함께 사용하는 정의를 공통 wiring으로 옮기면, 회차 wiring이 공연 wiring에서 가져오는 것도 공연 서비스 provider로 줄어든다.

## 3. How — 어떻게 작동하는가?

1. 요청이 들어오면 DB 세션을 주입한다.
2. 공연·회차 wiring이 같은 요청의 DB 세션을 사용해 서비스를 조립한다.
3. 회차 서비스는 `ShowAccess`를 통해 공연 존재나 소유권을 확인한다.
4. 쓰기 작업에서는 공연 행을 잠근 뒤 회차 변경을 수행한다.
5. 성공하면 commit하고, 실패하면 rollback한다.

소유권 확인이 끝났다고 중간에 commit하면 공연 잠금이 먼저 풀릴 수 있다. 따라서 공연 잠금부터 회차 변경 완료까지 같은 트랜잭션으로 이어지는 것이 중요하다.

## 5. 오늘의 문제 해결

### 문제 상황

회차가 사용하는 기능은 두 가지였지만 구체적인 공연 서비스 전체에 의존했다. 또한 공통 DB 세션·정책 정의를 공연 wiring에서 가져오고 있었다.

### 해결 방법

- 공연 조회·소유권 확인을 `ShowAccess` 계약으로 분리했다.
- DB 세션·정책 정의를 `wiring/common.py`로 이동했다.
- 실제 공연 서비스 구현과 기존 저장소·트랜잭션 로직은 유지했다.
- 조회·소유권 확인만 있는 대역으로 회차 기능이 동작하는지 확인했다.

### 검증에서 확인한 점

- 요청당 DB provider가 한 번 사용됐다.
- 공연 잠금 SQL → 회차 쓰기 → commit 순서가 유지됐다.
- 수정·삭제에서는 공연 잠금 → 회차 잠금 → 쓰기 순서도 확인했다.
- commit 실패 시 rollback되고 데이터가 원복됐다.
- 공통 예외 처리기 → 공연·회차 예외 처리 → wiring이 각각 한 번 등록됐다.
- 공연장 라우터가 유지됐다.

잠금 SQL은 PostgreSQL 방언으로 컴파일했고 데이터 변경은 SQLite에서 실행했다. 실제 PostgreSQL의 동시 잠금 대기까지 검증한 것은 아니다.

## 6. 협업과 기획 회고

서비스 전체 대신 필요한 기능만 계약으로 받자는 리뷰 의견을 코드에 반영했다. 의존성 분리와 함께 기존 잠금·세션 공유를 유지하는 조건도 검증했다.

다른 인증 변경과 합칠 때 발생할 수 있는 wiring 충돌, 예외 처리기 중복, 공연장 라우터 누락은 임시 통합 소스에서 해결 방향을 확인했다. JWT의 `User → CatalogActor` 연결은 별도 작업으로 분리했다.
