# TIL | 2026-10-22 | Next.js Todo 데이터 흐름과 상태 관리

> LV.2 · Week 10

> **화면에 데이터가 보이지 않는 문제는 UI만 고치는 것이 아니라 서버 액션, 데이터베이스 권한, 재조회, 클라이언트 상태를 순서대로 추적해야 한다.**

> 오늘은 Todo 등록과 찜 기능의 오류를 따라가며 서버 데이터와 브라우저 상태가 만나는 지점을 배웠다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- Next.js에서 Todo 등록은 폼 제출 → Server Action → Supabase 저장 → 서버 데이터 재조회 → 화면 렌더링의 흐름으로 이어진다.
- Supabase의 RLS 정책은 사용자가 접근할 수 있는 행의 조건을 정하고, GRANT는 특정 역할이 테이블에서 SELECT·INSERT·UPDATE 같은 작업을 수행할 권한을 정한다.
- Zustand의 `persist`는 상태를 브라우저 저장소에 보존하고, 하이드레이션은 저장된 값을 다시 스토어로 복원하는 과정이다.
- `params`는 동적 경로 값이고 `searchParams`는 URL의 질의 문자열 값이다.
- Metadata는 페이지 제목과 설명 같은 정보를 제공하며 검색 엔진과 공유 미리보기가 페이지를 이해하는 데 사용된다.

### 핵심 코드

```ts
export const usePinStore = create<PinStore>()(
    persist(
        immer((set) => ({
            items: [],
            add: (item: Todo) => {
                set((state) => {
                    const exists = state.items.some(
                        (savedItem) => savedItem.id === item.id,
                    );

                    if (!exists) {
                        state.items.push(item);
                    }
                });
            },
        })),
        {
            name: 'todo-pin-storage',
            partialize: (state) => ({ items: state.items }),
        },
    ),
);
```

### 오늘 수행한 실습

- Todo 등록 실패 원인을 Supabase 테이블, RLS 정책, 테이블 권한 순서로 확인했다.
- Zustand와 Immer를 이용해 Todo 찜 추가·해제 기능과 브라우저 저장 기능을 연결했다.
- 저장값 복원이 끝난 뒤 찜 목록을 렌더링하도록 하이드레이션 상태를 추가했다.
- ESLint와 TypeScript 정적 검사를 실행하고 문법·타입 오류를 수정했다.

### 실제 작성한 코드와 검증 상태

```text
작성한 코드: Todo 등록·상태 변경, Zustand 찜 스토어, 찜 목록 페이지
검증 방법: 브라우저 등록 확인, Supabase 데이터 확인, ESLint, TypeScript 검사, 프로덕션 빌드 시도
확인한 결과: Todo 등록 동작 확인, ESLint와 TypeScript 검사 통과
미완료: 후속 프로덕션 빌드는 파일 잠금 오류로 끝까지 통과하지 못함
```

## 2. Why — 왜 필요한가?

### 이 개념이 필요한 이유

- 화면에서 등록 버튼을 눌렀다는 사실만으로 데이터 저장과 목록 갱신이 모두 성공했다고 볼 수 없다.
- 인증된 사용자의 요청도 테이블 권한과 RLS 조건을 모두 만족해야 데이터에 접근할 수 있다.
- 서버가 만든 첫 화면과 브라우저 저장소에서 복원한 상태가 다르면 하이드레이션 오류가 생길 수 있다.
- 상태의 기준이 서버 데이터인지 클라이언트 상태인지 정하지 않으면 등록 후 DB에는 값이 있지만 화면에는 보이지 않는 문제가 생긴다.

### 내 생각

> 오류가 나면 한 파일의 문법만 보는 습관이 있었지만, 오늘 문제는 UI·서버·DB·브라우저 저장소가 연결된 흐름을 나눠 봐야 원인을 찾을 수 있었다. 코드를 전부 이해하지 못하더라도 기대 결과와 실제 결과, 처음 달라지는 지점을 기록하면 질문의 맥락을 다시 만들 수 있다.

---

## 3. How — 어떻게 작동하는가?

### 작동 과정

1. 사용자가 폼에 Todo를 입력하고 등록한다.
2. Server Action이 입력을 검증하고 로그인한 사용자 정보와 함께 Supabase에 INSERT를 요청한다.
3. Supabase가 역할의 테이블 권한과 RLS 정책을 검사한 뒤 행을 저장한다.
4. 서버가 Todo 목록을 다시 조회하고 새 props를 전달한다.
5. Client Component가 새 데이터를 렌더링하거나, 낙관적 상태를 사용한다면 서버 결과와 다시 맞춘다.
6. 찜 기능은 Zustand 상태를 변경하고 `persist`가 선택한 값을 브라우저 저장소에 기록한다.
7. 페이지를 다시 열면 저장값을 복원한 뒤 화면에 표시한다.

### 내 말로 설명하기

> Todo 등록은 버튼 하나의 기능이 아니라 화면에서 보낸 값이 서버와 데이터베이스를 통과해 다시 화면으로 돌아오는 왕복 과정이다. 찜 기능은 서버 데이터와 별도로 브라우저에 저장되므로, 저장값을 언제 복원했는지도 렌더링 결과에 영향을 준다.

---

## 5. 오늘의 문제 해결

### 문제 상황

- 하려고 했던 것: 로그인한 사용자가 Todo를 등록하고 메인 목록에서 확인하기
- 발생한 문제: 테이블과 RLS 정책이 있는데도 등록 요청이 허용되지 않거나 목록에 나타나지 않음
- 오류 메시지:

```text
permission denied for table todos
relation "todos" already exists
```

### 문제의 원인

- 이미 존재하는 테이블에 생성 SQL을 다시 실행했다.
- RLS 정책과 별개로 `authenticated` 역할에 필요한 테이블 작업 권한이 없었다.
- 서버에서 새 목록을 받아도 `useState(initialItems)`에 처음 복사한 클라이언트 상태는 자동으로 바뀌지 않는다.

### 해결한 코드

```sql
grant select, insert, update on table public.todos to authenticated;
```

### 해결 원리

> 테이블을 다시 만드는 대신 현재 구조를 유지하고, 인증된 역할에 필요한 작업 권한만 부여했다. RLS는 그다음 각 행에 대한 접근 조건을 검사한다. 등록 이후 화면 갱신 문제는 데이터 저장 성공과 별개이므로 서버 재조회와 클라이언트 상태 동기화를 따로 확인해야 한다.

## 7. KPT 회고

### Keep — 계속할 것

- 오늘 잘한 점: 오류 메시지와 실제 DB 상태를 대조하면서 테이블 존재 여부, 정책, 권한을 나눠 확인했다.
- 계속 유지할 학습 방법: 기대 결과 → 실제 결과 → 처음 달라진 지점 → 확인한 근거 순서로 기록한다.

### Problem — 개선할 것

- 이해하기 어려웠던 부분: Server Component의 새 데이터와 Client Component의 로컬 상태가 다시 연결되는 시점
- 반복해서 실수한 부분: 실제 `package.json`이 있는 폴더를 확인하지 않고 바깥 폴더에서 npm 명령을 실행한 것
- 아직 설명하기 어려운 부분: `revalidatePath`, `router.refresh`, 낙관적 업데이트 중 어떤 방식을 기준으로 선택해야 하는지
- 학습 외에도 발표 준비와 작업물 관리가 겹치면서 질문할 맥락을 잃기 쉬웠다.
- 실데이터가 없을 때 지표의 타당성을 무엇으로 검증할지 기준을 세우는 일이 어려웠다.

### Try — 다음에 시도할 것

- 다시 공부할 내용: Todo 한 건이 등록되어 다시 화면에 보일 때까지의 호출 순서
- 예제를 보지 않고 작성해볼 코드: 중복을 막는 Zustand `add` 함수와 찜 해제 `remove` 함수
- 다음 학습에서 바꿔볼 방법: 함수 하나씩 입력, 출력, 외부 상태 변경, 실패 결과를 표시하며 코드 리뷰한다.
- 강사에게 질문할 때 기대 결과, 실제 결과, 재현 순서, 확인 근거, 현재 추정을 다섯 줄로 정리한다.
- 실데이터가 없다면 가설 → 이벤트 → 지표 산식 → 합성 시나리오 → 예상값 대조 → 한계 명시 순서로 검증한다.
