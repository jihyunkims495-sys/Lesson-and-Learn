## 1. What — 무엇을 배웠는가?

### 핵심 개념

- **제어 입력:** `value`가 가리키는 상태의 키와 입력 요소의 `name`이 일치해야 한다.
- **폼과 Server Action:** `useActionState`는 결과 상태, 폼에 연결할 함수, 처리 중 여부를 반환한다. 서버에서는 입력 검증·인증·프로필 처리를 수행한다.
- **상태 변화와 Effect:** `useEffect`의 의존성 배열을 통해 성공 상태 변화에 따른 화면 이동 같은 후속 처리를 연결한다. 개발 모드의 추가 실행과 실제 사용자 동작을 구분한다.
- **로그인 후 화면 이동:** `redirectUrl` 변수와 `'redirectUrl'` 문자열은 다르다. `push`와 `replace`는 방문 기록을 남기는 방식이 다르고, `refresh`는 현재 화면의 서버 데이터를 다시 요청한다.
- **인증과 데이터 저장:** Supabase Auth 사용자 생성 성공과 `profiles` 저장 성공은 별개의 결과다. 세션·권한·사용자별 데이터 접근도 추가 확인이 필요하다.
- **요구사항 구체화:** 원하는 기능을 나열하는 데서 더 나아가 진입점, 상태 유지, 예외 흐름, 데이터 기준, 완료 조건을 정해야 한다.

### 핵심 코드

입력 상태를 갱신하는 현재 실습 코드의 핵심 부분이다.

```tsx
const onChange = (e: ChangeEvent<ElementType>) => {
    setForm(prev => ({...prev, [e.target.name]:e.target.value}));
};
```

`name="email"`이면 `form.email`을, `name="password"`이면 `form.password`를 갱신한다. 입력값 자체를 객체의 키로 쓰면 화면이 읽는 상태 필드가 바뀌지 않는다.

폼과 Action을 연결한 코드도 확인했다.

```tsx
const [state, formAction, isPending] = useActionState(
    signInAction,
    INITIAL_ACTION_STATE,
);
```

### 실제 작성한 코드와 검증 상태

- 입력 상태 키는 현재 코드에서 `e.target.name`을 사용하는 것으로 확인했다.
- 로그인 폼의 바깥쪽 JSX 태그가 닫힌 구조를 확인했다.
- 오전 실습에서 개발 서버를 재실행한 뒤 로그인 라우트의 HTTP 200 응답을 확인했다.
- 로그인 성공 후 목적지 이동, 기존 인증 사용자와 프로필 행의 연결, 세션 유지까지는 검증하지 못했다.
- 오후에는 프로젝트 기능 명세를 작성했다. 추천·혜택·GA4 수집을 새로 구현하거나 실행 검증한 결과는 아직 없다.

## 2. Why — 왜 필요한가?

로그인 페이지가 열린다고 해서 로그인이 끝난 것은 아니다. 입력이 올바르게 전달되고, 인증 결과와 프로필 데이터가 일치하며, 원래 가려던 화면까지 돌아가야 사용자 흐름이 완성된다.

ONEPIECE에서도 같은 문제가 이어진다. 장바구니 버튼이 보여도 다른 페이지에서 사용할 수 없거나, 로그인 뒤 선택한 상품이 사라지거나, 혜택 표시와 주문 금액이 다르면 구매 과정이 끊어진다.

> 오늘은 기능의 존재보다 기능 사이의 연결과 확인 기준을 구체적으로 적는 일이 필요하다고 느꼈다.

## 3. How — 어떻게 작동하는가?

### 오전 인증 실습의 실행 흐름

1. Client Component에서 입력 상태를 관리한다.
2. 폼이 `formAction`을 호출하고 입력값을 `FormData`로 전달한다.
3. Server Action이 입력을 검증하고 Supabase Auth를 호출한다.
4. 인증 결과에 따라 프로필을 생성하거나 조회하고 성공·오류 결과를 반환한다.
5. Client Component가 결과를 받아 오류를 표시하거나 화면을 이동·갱신한다.

### 프로젝트에 연결한 기준

1. 고객이 무엇을 하려는지부터 적는다.
2. 어느 화면에서 어떤 동작으로 기능에 진입하는지 정한다.
3. 이동 전후에 보존할 상품·옵션·수량·입력 상태를 적는다.
4. 필요한 데이터와 정보 부족·실패 상태를 구분한다.
5. 무엇을 확인해야 완료인지 체크리스트로 만든다.

## 4. 설계·명세 변경 기록

### 변경 전 문제

‘구매 여정을 짧게 한다’, ‘AI 추천을 넣는다’, ‘회원 혜택을 준다’는 표현만으로는 실제 구현 범위를 정하기 어려웠다. 장바구니 진입 방식, 추천 종류, 혜택 계산 수준에 따라 화면과 데이터 요구가 달라졌다.

### 수정할 때 중요하게 본 기준

- 충분한 상품 탐색과 구매 결정 이후의 불필요한 조작을 구분한다.
- 실제 고객 경험, 그 경험에 대한 해석, 앞으로 검증할 가설을 나눈다.
- 구현된 결과와 작성한 명세, 향후 실행할 계획을 구분한다.
- 같은 데이터를 여러 화면에서 읽는 경우 상태와 금액이 일치하도록 한다.

### 수정 내용과 이유

| 항목 | 오늘 정리한 내용 | 구현에 미치는 영향 |
| --- | --- | --- |
| 고객 가설 | 고관여 고객의 깊은 탐색과 중관여 고객의 후보 비교를 함께 고려 | 탐색 시간만 줄이는 방향으로 UI를 판단하지 않는다. |
| 장바구니 | 메인에 한정하지 않고 자사몰 전역에서 우측 오버레이로 확인 | 공통 진입점·장바구니 상태·닫기 후 복귀를 함께 확인한다. |
| 상품 목록 | 판매량순·추천순·신상품순을 ‘정렬’로 구분 | 카테고리·URL 상태 유지와 각 순위의 데이터 기준이 필요하다. |
| 상품 상세 | 비슷한 상품 추천과 회원 신체·구매 정보 기반 추천을 구분 | 공통 추천과 개인화 입력·정보 부족 상태를 따로 설계한다. |
| 장바구니 혜택 | 테스트 회원·쿠폰·등급·리워드로 적용 흐름 시연 | 임의의 운영 정책을 확정하지 않고 테스트 계산·주문 금액 전달을 검증한다. |
| 회원·구매 데이터 | 결제 승인된 유효 주문과 취소 처리 기준을 고려 | 구매 이력·순위·이벤트 집계가 어떤 상태를 기준으로 하는지 명시한다. |
| 측정 | 고객 성향에 따라 브라우저에서 행동하는 AI 에이전트를 사용 | 프로필 생성, 행동 실행, GA4 수집 확인을 각각 기록한다. |

### 레퍼런스에서 배운 점과 다음 적용

상세의 ‘비슷한 상품’ 진입 UI를 살펴보며 추천 기능도 진입점·결과 목록·원래 상품으로의 복귀까지 하나의 흐름으로 보게 됐다. 다음에는 현재 상품 선택 상태를 유지하면서 추천 후보를 확인하는 방식을 구현 범위에 연결할 예정이다.

## 5. 오늘의 문제 해결

| 최초로 확인한 문제 | 직접 원인 | 최소 수정·조치 | 확인 결과와 남은 작업 |
| --- | --- | --- | --- |
| 로그인 입력값이 유지되지 않음 | 입력값을 상태 객체의 키로 사용 | 키를 `e.target.name`으로 변경 | 현재 코드에서 수정 확인. 전체 로그인 흐름은 별도 검증 필요 |
| 로그인 폼 JSX 오류 | 바깥 요소의 닫는 태그 누락 | 닫는 태그 보완 | 현재 파일의 닫힌 구조 확인 |
| 회원가입 후 프로필 생성 실패 | 코드가 요구한 `name` 컬럼이 테이블에 없음 | 컬럼 추가 | Auth 사용자 생성과 컬럼 추가 확인. 기존 사용자 ID와 프로필 연결은 미확인 |
| 로그인 성공 후 잘못된 경로로 이동할 가능성 | `router.push('redirectUrl')`로 문자열 전달 | 변수 전달로 바꿔야 함 | 현재도 수정 전. 수정 후 실제 주소 확인 필요 |
| 오류 표시 아이콘 참조 문제 | `FiAlertCircle` import 누락 | 해당 아이콘 import 필요 | 미수정. 대상 린트 재확인 필요 |
| 브라우저에서 사이트 연결 실패 | 개발 서버가 실행되지 않음 | Webpack 개발 서버 재실행 | 오전 실습에서 로그인 라우트 HTTP 200 확인 |

리다이렉트의 수정 방향은 다음과 같다. 아래 수정안은 아직 실습 코드에 반영하거나 성공 흐름을 검증하지 않았다.

```tsx
// 현재 코드: 문자 그대로의 경로를 전달한다.
router.push('redirectUrl');

// 수정안: 변수에 저장된 목적지를 전달한다.
router.push(redirectUrl);
```

> 입력 상태, 서버 프로세스, 인증, 프로필 저장, 화면 이동을 분리해 보면 첫 번째로 잘못된 단계를 찾기 쉬웠다. 한 단계가 성공한 것을 전체 흐름의 성공으로 기록하지 않기로 했다.

## 6. 협업과 기획 회고

### 오늘 Task를 정한 회의 — 목적과 결과물 맞추기

오늘 회의에서는 각자 만들 기능뿐 아니라, 프로젝트를 어떤 과정으로 진행하고 어떤 결과물로 설명할지 다시 맞췄다. 레퍼런스 분석과 원하는 서비스 구현, 각자의 손코딩 학습을 하나의 스프린트로 연결하는 것이 중심이었다.

서비스의 성공·실패를 하나의 수치로 판정하기보다, 고객 정의→레퍼런스 해체 분석→구현→가상 고객 실행→지표 확인→UI 개선→리뷰 과정을 남기기로 했다. 원하는 UI를 빠르게 구현한 결과와 직접 손코딩하며 마주친 한계를 함께 비교하는 방향이다.

### 오늘의 네 가지 준비 작업

| Task | 회의에서 정한 범위 | 현재 기록할 수 있는 상태 |
| --- | --- | --- |
| A안: 산산기어 레퍼런스 클론·ERD 준비 | 비교 기준이 될 화면과 데이터 구조 준비 | 팀원이 이미 만들었다고 공유. 내가 실행 결과를 검증한 상태는 아님 |
| B안: ONEPIECE 바이브코딩 구현 | 정의한 고객의 구매 동선과 넣고 싶은 UI, 프론트엔드·백엔드 구현 | 오늘 수행할 작업으로 합의 |
| 가상 회원 만들기 | 고객 프로필과 구매 이력 등 초기 데이터 준비 | 내 담당. 생성·검증 결과는 아직 추가하지 않음 |
| 각 사이트 GA4 연결 | 비교 사이트의 행동 수집 준비 | 내 담당. 연결·수집 확인 결과는 아직 추가하지 않음 |

가상 고객은 정해진 경로를 클릭하기만 하는 스크립트가 아니라, 정의한 성향을 바탕으로 브라우저에서 행동하는 AI 에이전트로 정했다. 같은 고객 조건을 비교 사이트에 적용하되, 회원 데이터를 만드는 일과 에이전트를 실행해 실제 이벤트를 수집하는 일은 구분하기로 했다.

현재 정리의 A안은 레퍼런스 클론, B안은 ONEPIECE 바이브 구현이다. 손코딩 결과는 일별 누적 버전으로 별도 식별한다. 서로 다른 UI·기능에서 나온 지표 차이를 코딩 방식만의 효과로 단정하지 않는다.

### 내일부터의 작업과 일별 반복

10월 21일부터는 각자 맡은 도메인을 학습 난이도에 맞춰 직접 손코딩한다. 동시에 A안과 B안을 리뷰하고, GA4 연결을 확인·보완해 가상 고객의 실행 결과와 퍼널별 지표를 살펴본다.

1. 각자 직접 구현한 범위와 아직 막힌 부분을 정리한다.
2. 매일 약 오후 5시를 기준으로 개인 작업을 PR·리뷰 후 `dev`에 통합한다.
3. 측정 대상 버전과 배포 상태를 확인한 뒤 가상 고객을 실행한다.
4. 수집된 이벤트·중단 지점·오류를 확인하고 UI 개선 항목을 정한다.
5. 다음 구현에 반영한 내용과 재실행 결과를 누적한다.

완료 여부와 무관하게 시간만 맞춰 병합하는 뜻은 아니다. 코드 병합과 배포, 이벤트 발생과 정상 수집도 각각 확인해야 한다. 테스트 실행 결과를 실제 고객의 구매 의사나 실구매 전환율로 해석하지 않는다.

### 도메인 역할과 내가 맡은 일

| 도메인 | 역할 배정에서 연결한 작업 |
| --- | --- |
| 메인(index) | 메인 화면과 로그인 |
| 상품(product) | 상품 목록, 레퍼런스 클론·ERD와 결제 |
| 상품 상세(product-detail) | 상세 화면과 ONEPIECE 바이브 구현 |
| 장바구니(cart) — 내 담당 | 장바구니 구현, 가상 고객 데이터·행동 실행 준비, 각 사이트 GA4 연결 |

내가 맡은 장바구니는 독립적인 화면을 만드는 데서 끝나지 않는다. 어느 페이지에서나 담은 상품을 확인하고, 로그인·주문까지 선택 내용이 이어지는지 확인해야 한다. 가상 고객 실행과 GA4를 연결할 때도 브라우저 행동, 장바구니 상태, 수집 이벤트가 서로 맞는지 보는 것이 다음 과제다.

### 최종 결과물로 설명할 시나리오

1. 레퍼런스 서비스의 화면·데이터 구조·구매 경로와 측정 결과를 해체 분석한다.
2. User FGI에서 타깃과 가설이 어떻게 발전했는지 설명한다. FOMO의 구체적인 기능은 아직 미정으로 둔다.
3. ONEPIECE 구현물의 화면·경로·데이터 연결과 실제 완료 범위를 보여준다.
4. 손코딩 결과, 바이브 구현, 레퍼런스의 동작과 관측 지표를 비교한다.
5. 매일의 트러블슈팅·구현 한계·UI 개선 이유를 리뷰한다.

이 과정을 통해 결과 화면뿐 아니라 어떤 판단으로 만들었고, 어디까지 확인했으며, 다음에 무엇을 바꿀지 설명할 수 있는 기록을 남기기로 했다.

### 기능 명세로 연결한 내용

- 고객 인터뷰 두 건을 다시 정리하면서 실제 경험과 UI 가설을 구분했다. 3·4·6 그리드는 첫 번째 인터뷰 이후 정한 방향이고, 두 번째 인터뷰는 목적 구매와 판매량순 비교를 검토하는 근거였다.
- 기능 명세에는 표시·동작 규칙뿐 아니라 빈 결과·실패·로그인 복귀·금액 일치 같은 완료 기준도 넣었다.

### 범위 변경과 미정 사항

- 오늘 합의한 Task와 실제 완료한 작업은 구분한다. 가상 회원·GA4 연결 등 내 실행 결과는 이후 추가해야 한다.
- AI 추천 모델, 판매량 집계 기간, 신상품 기준일, 테스트 혜택의 수치·적용 순서는 미정이다.
- 앱 구현 방식과 FOMO의 구체적인 기능도 아직 확정하지 않았다.

## 7. KPT 회고

### Keep — 계속할 것

- 오류를 증상·원인·최소 수정·재확인 결과로 나눠 기록한다.
- ‘원하는 기능’과 ‘확인할 수 있는 완료 기준’을 함께 적는다.
- 고객이 말한 경험과 내가 도출한 가설을 구분한다.

### Problem — 개선할 것

- 기능 목록뿐 아니라 레퍼런스 분석·바이브 구현·손코딩·측정이 어떤 순서로 연결되는지 문서에 함께 남길 필요가 있었다.
- 로그인 성공 후 이동과 프로필 연결을 끝까지 확인하지 못했다.
- 추천·혜택 요구는 구체화했지만 데이터와 정책의 세부 기준은 남아 있다.
- 가상 고객 실행과 GA4 수집을 아직 실제 결과로 연결하지 못했다.

### Try — 다음에 시도할 것

- 하루 작업을 시작할 때 직접 구현할 범위와 당일 관측할 결과를 구분해 적는다.
- 로그인 흐름의 남은 오류를 하나씩 수정하고 각 단계의 실제 결과를 확인한다.
- 전역 장바구니에서 상태 보존·복귀·다른 화면과의 일치부터 검증한다.
- 가상 고객 한 명의 실행부터 시작해 브라우저 행동과 수집 이벤트를 대조한다.

## STAR 설계·협업 기록

### Situation — 상황

인증 실습에서는 입력·프로필·화면 이동 문제가 서로 다른 단계에서 나타났다. 프로젝트에서는 레퍼런스 분석·바이브 구현·손코딩·측정을 어떤 흐름으로 진행할지 맞추는 회의가 필요했다.

### Task — 해결 과제

오류의 발생 단계를 구분하고, 담당 장바구니와 구매 여정을 실제로 구현·확인할 수 있는 단위로 정리해야 했다.

### Action — 실행한 행동

1. 인증 실습의 수정된 코드와 미수정 항목을 나눴다.
2. 오늘의 네 가지 Task와 내일부터의 손코딩·리뷰·측정, 일별 통합 흐름과 역할을 정리했다.
3. 고객 인터뷰에서 가설이 바뀐 근거와 현재 구현 목표를 정리했다.
4. 장바구니의 전역 우측 오버레이, 두 종류의 추천, 테스트 혜택 시연 범위를 구체화했다.
5. 각 기능에 동작·예외·완료 기준과 다음 구현 후보를 적었다.

### Result — 결과

오늘의 준비 작업과 이후 손코딩·측정·리뷰가 이어지는 스프린트 명세를 정리하고, 내 장바구니·가상 고객·GA4 역할을 확인했다. 이를 고객 경험과 UI·추천·혜택 요구사항에 연결했다. 기능 구현과 측정이 완료된 것은 아니며, 다음에는 이 기준으로 작은 기능을 직접 구현하고 실제 결과를 추가할 예정이다.
