# Preview Notes — Next.js와 Supabase 인증·배포

## 학습 목표

- 이미지와 폰트 최적화가 초기 화면 성능에 미치는 영향을 설명한다.
- 정적 Metadata와 동적 Metadata의 사용 시점을 구분한다.
- Server Component, Client Component, Server Action의 실행 위치를 구분한다.
- Supabase Auth와 쿠키 기반 세션 흐름을 이해한다.
- 인증과 RLS 기반 데이터 권한을 서로 다른 보안 계층으로 구분한다.
- 환경변수의 브라우저 공개 범위와 배포 전 검증 순서를 이해한다.

## 전체 구조

```text
Asset·Metadata 최적화
→ 요청 단계의 경로 제어
→ Supabase 데이터 연결
→ Server Action 기반 데이터 변경
→ Auth로 사용자 확인
→ 쿠키로 세션 유지
→ RLS로 사용자별 행 보호
→ 환경변수·빌드·배포 검증
```

## 1. Asset과 Metadata

### `next/image`

- 이미지 공간을 미리 확보해 로딩 중 레이아웃 이동을 줄인다.
- 외부 이미지는 허용할 호스트 범위를 설정해야 한다.
- `alt`는 접근성과 검색 정보에 사용된다.
- 우선 로딩은 첫 화면의 핵심 이미지에 제한해서 사용한다.

### `next/font`

- 필요한 글꼴과 굵기만 빌드에 포함할 수 있다.
- 글꼴 로딩으로 인한 화면 흔들림과 외부 요청을 줄이는 데 도움이 된다.

### Metadata

| 방식 | 적합한 상황 |
|---|---|
| 정적 Metadata | 모든 방문자에게 같은 제목과 설명을 제공할 때 |
| 동적 Metadata | 라우트 값이나 조회 결과에 따라 제목·공유 정보가 달라질 때 |
| Open Graph | 메신저와 SNS 공유 카드 정보를 구성할 때 |

## 2. Next.js 실행 경계

App Router의 컴포넌트는 기본적으로 Server Component다. 브라우저 상태와 이벤트가 필요한 파일에 `'use client'`를 선언하면 그 파일부터 Client Component 경계가 만들어진다.

```text
Server Component
→ 초기 화면 구조와 서버 데이터 준비

Client Component
→ 브라우저 상태·이벤트·사용자 입력 처리

Server Action
→ 브라우저 요청을 받아 서버에서 검증·인증·데이터 변경
```

Client Component도 최초 HTML이 서버에서 만들어질 수 있다. 브라우저가 JavaScript를 연결해 상호작용 가능한 상태로 만드는 과정을 hydration이라고 한다.

## 3. Supabase 데이터와 Auth

### 클라이언트 구분

- 브라우저 클라이언트: 사용자 브라우저에서 실행되는 요청에 사용한다.
- 서버 클라이언트: Server Component와 Server Action에서 쿠키를 읽고 서버 요청을 수행한다.
- 두 클라이언트는 같은 세션을 사용하더라도 실행 위치와 쿠키 책임이 다르다.

### 인증과 권한

| 개념 | 담당 질문 |
|---|---|
| Authentication | 현재 사용자가 누구인가? |
| Session | 로그인 상태를 다음 요청까지 어떻게 유지하는가? |
| Authorization / RLS | 이 사용자가 어떤 행을 읽고 바꿀 수 있는가? |

로그인 성공만으로 모든 데이터 접근이 안전해지는 것은 아니다. 데이터베이스에서는 RLS 정책으로 사용자별 접근 범위를 제한해야 한다.

## 4. 환경변수와 배포

- `NEXT_PUBLIC_` 접두사가 붙은 값은 브라우저 번들에 포함될 수 있다.
- 접두사가 없는 변수는 서버 전용 코드에서만 사용해야 한다.
- 공개용 키라도 데이터 접근 안전성은 RLS와 권한 정책에 의존한다.
- 실제 값이 들어 있는 로컬 환경변수 파일은 Git에 포함하지 않는다.

```text
개발 기능 확인
→ 정적 검사와 프로덕션 빌드
→ 비밀 파일 제외 확인
→ 저장소 반영
→ 배포 환경변수 설정
→ 인증 Redirect URL 설정
→ 로그인·CRUD·RLS 재검증
```

## 예상 난점

- `'use client'`를 페이지 전체가 CSR로 바뀐다는 뜻으로 이해하기
- TypeScript 파일 확장자가 실행 위치를 정한다고 생각하기
- `'use server'`를 SSR 표시로 이해하기
- Publishable Key가 공개 가능하므로 RLS가 필요 없다고 생각하기
- 요청 경로의 리다이렉트를 최종 데이터 권한 검사로 생각하기
- 개발 서버 실행과 프로덕션 빌드 성공을 같은 검증으로 생각하기

5. 인증 성공 후에도 RLS가 필요한 이유는 무엇인가?
