# TIL | 2026-11-23 | 포켓몬 전략 RAG 기획 킥오프

> LV.2 / Week 15 · Project 3 RAG Agent

> **포켓몬을 잘 모른다는 막막함을 사용자 질문, 데이터 범위, 청킹 기준과 평가 항목으로 바꾸며 프로젝트의 출발점을 구체화했다.**

> RAG 프로젝트는 DB부터 만드는 일이 아니라, 누구의 어떤 질문에 어떤 근거로 답할지를 먼저 정하는 일이라는 점을 이해했다.

---

## 1. What — 무엇을 배웠는가?

### RAG 교안 복습

- RAG는 문서를 저장하는 것으로 끝나지 않고, 수집·정제·청킹·색인·검색·재정렬·답변·평가가 연결된 파이프라인이다.
- BM25는 정확한 용어를 찾는 데 강하고, Vector Search는 표현이 달라도 의미가 비슷한 내용을 찾는 데 강하다.
- Hybrid Search는 두 검색 결과를 결합하고, Re-ranking은 질문과 후보 청크의 관련도를 다시 평가해 순서를 조정한다.
- 검색 품질과 답변 품질을 구분해 평가하고, 근거가 부족할 때는 무리하게 추천하지 않아야 한다.

### 프로젝트 주제와 대상 사용자

팀의 첫 기획 킥오프에서 **1세대 포켓몬 151종을 범위로 하는 포켓몬 전략 RAG**를 주제로 구체화했다. 사용자가 상대 포켓몬을 입력하면, 상성을 고려한 대응 후보와 기술 조합, 전략의 성립 조건과 주의점을 근거와 함께 설명하는 방향이다.

오늘 내가 가장 답답했던 지점은 포켓몬과 게임 규칙을 거의 모르는 상태에서는 다음 질문조차 만들기 어렵다는 점이었다.

- 무엇을 기준으로 문서를 나눠야 하는가?
- DB에는 어떤 값을 구조화해서 저장해야 하는가?
- 사용자가 무엇을 입력해야 추천이 가능한가?
- 어떤 출력을 정답으로 보고 평가해야 하는가?

이 막막함은 프로젝트가 해결하려는 사용자 문제와도 연결됐다. 피카츄 정도만 아는 초보자도 어려운 게임 용어를 모두 알지 못한 채 질문할 수 있어야 하며, Agent는 필요한 조건만 다시 묻고 쉬운 말로 추천 근거를 설명해야 한다.

### 구조화 데이터와 RAG 문서의 역할 분리

오늘 논의를 통해 모든 정보를 같은 방식으로 Vector DB에 넣는 것이 아니라, 정보의 성격에 따라 역할을 나눠야 한다는 점을 정리했다.

| 구분 | 담을 정보 | 역할 |
|---|---|---|
| 도감·규칙 데이터 | 포켓몬 ID, 이름, 타입, 능력치, 기술과 기술 타입, 타입 상성 | 정확한 조회와 상성 계산 |
| 세팅 데이터 | 게임·포맷, 기술 조합, 특성, 도구, 역할 | 추천 후보의 조건 확인 |
| 전략 문서 | 기술 선택 이유, 운용 방법, 유리·불리한 상대, 파트너, 예외 조건 | 검색과 전략 설명의 근거 |

타입 상성처럼 규칙이 명확한 값은 구조화 데이터와 코드로 계산하고, “왜 이 기술을 쓰는가”, “어떤 조건에서 유리한가”와 같은 설명은 공략 문서를 검색하는 방식이 적합하다.

### 청킹과 메타데이터 초안

전략 문서를 파일 전체 단위로 저장하면 서로 다른 게임·대전 형식·세팅의 설명이 섞일 수 있다. 따라서 다음 구조를 유지하는 청킹이 필요하다.

```text
포켓몬 → 게임·대전 포맷 → 세팅 → 설명 주제
```

설명 주제는 기술 선택 이유, 운용법, 위협적인 상대, 추천 파트너처럼 나눌 수 있다. 단, 결론의 조건을 설명하는 문장은 같은 청크에 보존해야 한다.

각 청크에는 다음 메타데이터가 필요하다.

```text
document_id, chunk_id, pokemon_id, pokemon_name,
game, battle_format, build_name, topic,
source, source_location, collected_at, version
```

이 구조는 검색 결과가 어느 포켓몬의 어떤 규칙과 세팅에 관한 설명인지 확인하고, 최종 답변의 출처를 추적하기 위해 필요하다. 아직 실제 DB 스키마와 청크 크기·겹침 값은 확정하거나 구현하지 않았다.

## 2. Why — 왜 필요한가?

### 이 설계가 필요한 이유

포켓몬 이름이 같아도 게임 버전, 싱글·더블 같은 대전 포맷, 기술·도구·특성 조합에 따라 전략이 달라질 수 있다. 이 조건을 구분하지 않으면 검색 결과가 서로 섞이고, 타입 상성만으로 실제 승리를 보장하는 것처럼 잘못 설명할 수 있다.

또한 “상성이 좋다”와 “실제 대전에서 안정적으로 대응한다”는 같은 말이 아니다. 실제 전략에는 사용하는 기술, 속도, 특성, 도구와 상대의 행동이 함께 영향을 준다. 따라서 Agent는 추천 결과와 함께 적용 조건과 한계도 설명해야 한다.

### 내 생각

> 처음에는 게임을 즐기기 위해 이렇게 많은 것을 공부하는 사람이 정말 있을까 싶었다. 하지만 게임 규칙을 모르는 내 입장에서 질문을 만들다 보니, 오히려 초보자가 무엇을 몰라서 검색조차 시작하지 못하는지가 보였다. 포켓몬 지식이 부족한 상태는 프로젝트를 방해하는 조건이면서 동시에 초보 사용자 경험을 설계할 수 있는 출발점이 될 수 있었다.

## 3. How — 어떻게 작동하는가?

### 예상 입력과 출력

초기 버전에서는 모든 조건을 한 번에 입력받기보다, 답을 바꿀 수 있는 정보만 확인한다.

```text
입력
- 상대 포켓몬
- 기준 게임과 대전 포맷
- 보유 포켓몬 안에서 추천할지, 지원 범위 전체에서 추천할지
- 필요한 경우 현재 기술이나 선호 포켓몬

출력
- 대응 후보 최대 3개
- 기본 상성 계산 결과
- 추천 기술·세팅과 선택 이유
- 전략이 성립하는 조건과 주의점
- 검색한 근거와 출처
- 근거가 부족할 때의 지원 범위 안내
```

### 예상 처리 흐름

1. 사용자 질문에서 상대 포켓몬과 요청 의도를 파악한다.
2. 게임·포맷처럼 답을 바꾸는 조건이 빠졌다면 필요한 항목만 다시 묻는다.
3. 도감·규칙 데이터에서 타입, 기술과 기본 상성을 조회한다.
4. 같은 조건의 전략 문서를 Vector Search 또는 Hybrid Search로 찾는다.
5. 검색 후보를 Re-ranking해 질문과 관련된 근거를 상단에 배치한다.
6. 계산 결과와 전략 근거를 구분해 대응 후보, 이유, 조건과 주의점을 설명한다.
7. 답변에 사용한 청크와 원문 위치를 함께 남긴다.
8. 근거가 없거나 지원 범위를 벗어나면 필승 조합을 추측하지 않고 정보 부족을 안내한다.

### 내 말로 설명하기

> 도감 DB는 포켓몬의 기본 사실을 정확하게 찾는 곳이고, RAG는 여러 공략 중 현재 질문에 맞는 설명을 찾는 과정이다. Agent는 두 결과를 합쳐 추천하되, 계산으로 확인한 사실과 문서에서 찾은 전략을 구분해서 보여줘야 한다.

## 4. 설계·명세 변경 기록

### 변경 전 문제

- “포켓몬 도감으로 스킬 조합과 전략을 알려준다”는 아이디어만 있어 지원 게임과 포맷, 데이터 범위가 모호했다.
- 도감 데이터, 기술 정보, 공략 문서를 모두 같은 검색 데이터로 볼지 정해지지 않았다.
- “필승 조합”처럼 검증하기 어려운 표현이 목표에 포함될 가능성이 있었다.

### 수정할 때 중요하게 본 기준

- 짧은 프로젝트 기간 안에 실제 데이터와 근거를 사람이 확인할 수 있어야 한다.
- 계산 가능한 사실과 문서 검색이 필요한 설명을 구분해야 한다.
- 초보자의 질문을 받되, 게임 규칙과 근거를 벗어난 승리를 보장하지 않아야 한다.
- Vector, Hybrid, Hybrid + Re-ranking을 같은 조건에서 비교할 수 있어야 한다.

### 수정 내용과 이유

- 대상 포켓몬을 1세대 151종으로 제한해 DB와 평가 범위를 줄였다.
- 구조화 도감·상성 데이터와 서술형 전략 문서를 분리했다.
- “필승 조합” 대신 **근거가 있는 대응 후보, 적용 조건, 주의점**을 설명하는 목표로 구체화했다.
- 초보자를 주요 사용자로 보고, 쉬운 표현과 필요한 재질문을 설계 대상으로 추가했다.

### 구현에 미치는 영향

- 151종 밖의 포켓몬·폼을 추천하지 않는 범위 검증이 필요하다.
- 게임과 대전 포맷을 메타데이터와 검색 필터에 포함해야 한다.
- 검색 파이프라인과 별도로 타입 상성 계산의 정답 사례를 검증해야 한다.
- 평가셋에는 직접 검색, 표현 변형, 유사 조건 구분과 근거 없음 질문이 모두 포함되어야 한다.

### 프로젝트 요구사항에서 배운 점과 다음 적용

- 배운 점: 기능 수보다 동일한 평가 질문으로 검색 단계의 차이를 비교하고, 실패 원인을 원본 결과로 설명하는 것이 중요하다.
- 다음 작업에 적용할 항목: 개발용 10문항과 최종 평가용 20문항을 분리하고, Vector·Hybrid·Re-ranking 결과를 같은 조건에서 기록한다.

## 6. 협업과 기획 회고

### 함께 발전시킨 내용

- 팀에서 처음 제시된 의견: 포켓몬 도감을 활용해 상대 포켓몬의 상성에 맞는 후보와 전략을 설명하는 RAG를 만든다.
- 논의를 통해 구체화한 방향: 1세대 151종을 범위로 두고, 도감·상성 계산과 공략 검색의 역할을 분리한다.
- 내 구현·설계에 반영할 사항: 초보자가 실제로 할 질문을 기준으로 입력 조건, 답변 형식, 근거 부족 대응과 평가 문항을 구체화한다.

오늘은 DB 구성과 사용자 질문을 함께 논의하면서, 데이터팀이 만드는 구조가 실제 질문과 답변에 어떤 영향을 주는지 연결해 보았다. 다만 실제 테이블, 컬럼, 청킹 설정과 담당 기능은 아직 팀에서 확정하고 구현해야 한다.

## 7. KPT 회고

### Keep — 계속할 것

- 모르는 용어를 아는 척하지 않고 초보자 관점의 질문으로 바꾼다.
- 아이디어를 입력, 처리, 출력과 평가 기준으로 나눠 생각한다.
- 팀의 제약 조건이 생길 때 사용자 범위와 데이터 범위를 함께 조정한다.

### Problem — 개선할 것

- 게임의 기본 흐름과 포켓몬·기술·타입의 관계를 몰라 질문의 시작점을 잡기 어려웠다.
- 청킹과 DB 설계를 사용자 질문보다 먼저 생각하면서 전체 구조가 더 복잡하게 느껴졌다.
- 타입 상성, 기술 조합과 실제 전략을 하나의 문제처럼 생각했다.

### Try — 다음에 시도할 것

- “이 문서로 답할 수 있는 질문은 무엇인가?”를 먼저 적고 필요한 데이터와 청크를 역으로 정한다.
- 샘플 포켓몬 2~3종으로 질문 → 조회 → 검색 → 답변의 한 경로를 먼저 연결한다.
- 구조화 데이터의 계산 결과와 RAG의 전략 근거를 화면과 평가 기록에서 분리한다.
