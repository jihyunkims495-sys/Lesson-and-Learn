> LV.2 / Week 15 · Project 3 RAG Agent

> **도감을 검색해 필요한 근거를 읽고, 다음 질문을 이어가며 싱글 배틀을 준비하는 화면을 다듬었다.**

> 같은 도감 정보를 누구에게 어떤 말로 보여줄지 정하고, 화면에서 질문과 답변이 실제로 이어지는지 확인했다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- **답변 내용과 표현을 분리하기.** 지우는 기술 용어를 쉽게 풀고, 이슬이는 첫 확인 지점과 결론을 짚고, 웅이는 타입 배율과 자속을 나눠 설명한다. 세 메이트가 참고하는 Red/Blue 도감 데이터와 상성 규칙은 공통이다.
- **화면과 데이터 조회를 분리하기.** 화면은 질문 원문, 대화의 조건, 페르소나 ID를 전달하고 반환된 답변과 근거를 표시한다. 목업으로 사용 흐름을 확인한 후 실제 서버의 요청·응답 규격에 맞춰 조회 부분을 연결할 수 있다.
- **자동 스크롤에 사용자 의도를 반영하기.** 답변이 타이핑되며 영역 높이가 늘어나도 하단을 따라가고, 사용자가 위로 올려 읽기 시작하면 멈추는 규칙을 만들었다.

### 핵심 코드

질문과 현재 조건을 조회 계층에 전달하는 코드다. `signal`은 화면 이동 등으로 요청을 취소할 수 있게 전달한다.

```js
const result = await client.askQuestion({
  question,
  context: queryContext,
  personaId: state.characterId,
  signal: controller.signal,
});
```

### 오늘 수행한 실습

- React 미리보기에서 유저 타입을 고른 뒤 질문 예시와 자유 입력이 나오는 화면을 분리했다. 이후 기존 JavaScript 미리보기에서 메이트 대화, 후속 질문, 자동 스크롤과 준비 확인을 발전시켰다.
- 답변을 짧은 결론과 핵심 불릿으로 구성했다. 자세한 수치와 자료는 ‘도감 근거 보기’에서 열 수 있게 했다. 페르소나 카드와 새 답변에 메이트 이미지를 표시하고 이미지 로드 실패에는 이니셜을 사용했다.
- 밝은 하늘과 원본 셀 채색을 사용해 홈 장면을 조정했다. 포스터의 캐릭터 외곽선을 아홉 개 레이어로 분리하고, 피카츄의 점프와 리자몽의 기울기를 다른 박자로 움직이게 했다.

### 실제 작성한 코드와 검증 상태

| 확인 항목 | 검증 결과 |
| --- | --- |
| React 미리보기 | 빌드가 통과했다. 세 페르소나의 시작 질문과 에이스의 질문 전송부터 답변·근거·후속 질문이 표시되는 것까지 브라우저에서 확인했다. |

| 이미지 폴백 | 이미지 주소가 실패하거나 매핑이 없을 때 이니셜만 남는 동작을 모의 검사로 확인했다. |

## 2. Why — 왜 필요한가?

### 이 설계가 필요한 이유

- 배틀을 준비하는 사용자는 ‘지금 가진 공격 중 무엇이 통하나’에 대한 결론과 근거를 먼저 확인할 수 있어야 한다. 탐색 화면에서 그 답을 읽고 곧바로 다음 질문을 이어갈 수 있게 했다.
- 새 답변이 길어질 때마다 화면을 강제로 맨 아래로 옮기면 이전 수치나 근거를 읽다가 위치를 잃는다. 하단을 따라갈 조건과 멈출 조건을 함께 정해야 한다.

### 내 생각

> 같은 질문에 어린이와 숙련자에게 다른 설명을 줄 때, 달라질 항목은 용어와 설명의 길이다. 전기쇼크가 롱스톤에게 0배이고 전광석화는 0.5배라는 비교 결과는 그대로 보여줘야 한다.

## 3. How — 어떻게 작동하는가?

1. 사용자가 에이스·루키·마스터 중 하나를 고르고, 예시를 선택하거나 질문을 직접 입력한다. 예시는 편집 후 보낼 수 있다.
2. 현재 목업은 질문과 배틀 조건으로 로컬 도감을 조회하고 기본 상성을 계산한다. 화면은 해당 메이트의 답변과 근거, 이어서 물을 질문을 보여준다.
3. 사용자가 새 질문을 보내면 대화 하단으로 이동한다. `ResizeObserver`가 답변 영역의 높이 변화를 감지하고, 따라가기 상태일 때만 다음 프레임의 이동을 예약한다.
4. 사용자가 위로 스크롤하면 읽던 위치를 유지한다. 하단 근처로 직접 내려오거나 다시 질문을 시작하면 따라가기가 재개된다.
5. 상대 → 현재 기술 → 기술 수치 → 타입 비교 → 준비 확인 순서로 정보를 확인하고, 현재 가진 기술 중 하나를 선택한다. 예시에서 물대포의 4배는 롱스톤 상대 기본 타입 배율이다. 실제 피해량과 승률은 별도 계산이 필요하다.

## 5. 오늘의 문제 해결

### 문제 상황과 원인

레퍼런스와 비슷한 색은 나왔지만, 홈이 여전히 JPG를 네모로 붙여 놓은 것처럼 보였다. 처음 구현은 전체 이미지를 렌더링하고 일부 영역만 움직였다. 캐릭터 뒤에 원본 이미지의 하늘이 남아 있었고, 움직이는 부분도 정지한 원본 실루엣 위에 겹쳤다.

### 수정과 확인

캐릭터마다 외곽선 좌표를 지정해 보이는 영역을 잘랐다. 픽셀 좌표를 백분율로 바꿔 화면 크기가 달라져도 배치 비율을 유지하도록 했다. 브라우저에서 아홉 레이어가 표시되고 피카츄와 리자몽의 움직임과 클릭 반응이 각각 동작하는 것을 확인했다.

> “따로 움직여야 한다”는 피드백을 받으면 먼저 캐릭터가 화면에서 독립된 요소인지 확인한다. 같은 그림을 쓰더라도 렌더링 구조에 따라 구현할 수 있는 움직임이 달라진다.

## 6. 협업과 기획 회고

- 사용자 화면의 범위를 페르소나 선택, 질문 입력, 답변과 근거 확인으로 좁혔다. 검색 방식 비교와 공식 평가는 사용자 대화와 구분했다.
- 화면으로 확인할 항목과 백엔드 응답으로 검증할 항목을 나눴다. 이어서 연결하려면 질문 원문·대화 조건을 어떻게 전달할지, 답변·근거·조건 부족 상태를 어떤 형식으로 받을지 확인해야 한다.

## 7. KPT 회고

- **Keep** — 질문을 보낸 뒤 바로 다음 질문을 이어가고 준비를 마치는 데까지 화면에서 확인한다.
- **Problem** — 모션을 넣었다는 사실에 집중하면, 화면에서 캐릭터가 실제로 따로 움직여 보이는지 놓치기 쉽다.
- **Try** — 피드백을 화면에서 확인할 수 있는 조건으로 바꿔 기록한다. 예를 들어 ‘움직임을 살리기’를 ‘피카츄와 리자몽의 위치가 서로 다른 박자로 변하는지 보기’로 구체화한다.
