# TIL | 2026-11-25 | 포켓몬 RAG 질문 설계와 탐색 화면

> LV.2 / Week 15 · Project 3 RAG Agent

> **초보자와 숙련자의 질문을 실제 데이터로 검토하고, 질문에서 배틀 준비까지 이어지는 화면 흐름을 만들었다.**

> 자연스러운 질문을 만드는 일과 그 질문에 근거를 갖춰 답하는 일은 별도의 검증이 필요하다는 점을 배웠다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- 영문 Red/Blue의 싱글 배틀 준비 상황에서 세 사용자 유형의 질문 9개를 검토했다. 같은 “쎄?”도 기술의 기본 위력, 타입 상성, 실제 피해량 중 무엇을 비교하는지 문맥에 따라 달라진다.
- 질문 후보를 만들 때는 질문의 대상, 현재 기술, 비교 조건을 유지해야 한다. 생성 질문의 형식 검사와 답변 가능성 검토, 팀의 최종 채택은 서로 다른 단계다.
- 도감·기술·타입 규칙의 정확한 조회와 문서 검색의 성공은 다르다. 화면에서 로컬 계산 결과를 보여줬다고 RAG 검색이 성공한 것은 아니다.

### 오늘 수행한 작업

- 기존 질문 9개에 필요한 사실, 예상 답변, 근거와 실패 기준을 대조했다. 롱스톤에게 전기쇼크의 기본 타입 배율은 0, 전광석화는 0.5이며, 꼬부기 물대포의 타입 배율 4와 자속 1.5를 구분했다. 두 값을 결합한 명목 계수 6은 실제 피해량이나 승률이 아니다.
- 질문 생성 역할과 구조 검사 도구를 연결해 세 사용자 유형별 3개씩 Hermes 질문 후보 9개를 만들었다. 한 질문의 표현을 다시 생성할 때 나머지 8개를 유지하는 방식도 확인했다. 후보의 팀 채택과 공식 평가셋 등록은 아직 이루어지지 않았다.
- 메인 → 탐색·답변 → 배틀 준비의 세 화면을 다섯 정보 단계로 연결했다. 상대, 현재 기술, 기술 수치, 타입 비교, 준비 확인 순서이며, 사용자가 확인해야 다음 단계로 넘어간다.
- 로컬 화면은 151종 포켓몬과 165개 기술의 정제 자료를 조회하고 기본 규칙을 계산한다. 실제 검색 실험 기록이 없을 때는 Vector·Rewrite·Reranker 결과를 만들어 보여주지 않는다.

### 실제 작성한 코드와 검증 상태

다섯 정보 단위를 화면과 확인 상태가 공유하도록 정의한 코드의 핵심 부분이다.

```js
export const MAX_JOURNEY_STEPS = 5;
export const REQUIRED_UNITS = Object.freeze([
  Object.freeze({ id: "opponent", title: "상대부터 보기", requirement: "상대의 Red/Blue 타입과 기본 방어 약점" }),
  Object.freeze({ id: "current-kit", title: "내 친구와 공격", requirement: "예시 후보와 각 후보의 현재 기술, 습득 가능과 현재 보유의 차이" }),
  Object.freeze({ id: "move-values", title: "기술 정보 확인", requirement: "Red/Blue 기본 위력·명중률·PP, 기본 PP와 현재 잔량 구분" }),
  Object.freeze({ id: "type-comparison", title: "통하는 공격 비교", requirement: "기본 타입 배율·자속 분리, 무효 0과 계산 불가 구분" }),
  Object.freeze({ id: "readiness", title: "이 조합으로 준비", requirement: "현재 기술 중 조건부 선택과 예시 조건·계산 한계의 사용자 확인" }),
]);
```

위 코드는 화면 흐름을 설명하기 위한 발췌다. 저장된 로컬 검증 기록에서는 프론트 단위 검사 67개가 통과했고, P1~P3의 단계 이동과 미해결 질문 처리도 확인했다. 모바일 화면 검증은 해당 기록에서 완료되지 않았다. 이 검증은 실제 RAG 답변이나 추천 성공률의 검증이 아니다.

## 2. Why — 왜 필요한가?

### 이 설계가 필요한 이유

- “피카츄만 안다”는 말을 피카츄만 보유했다는 뜻으로 바꾸면 잘못된 조건에서 추천하게 된다.
- 기술을 배울 수 있다는 기록과 현재 그 기술을 가지고 있다는 상태도 다르다. 현재 기술에서 물대포를 제외한 질문에는 이전 추천을 그대로 재사용할 수 없다.
- PP의 기본값 25를 확인했더라도 현재 남은 횟수나 PP의 뜻을 설명할 근거까지 확보한 것은 아니다. 확인된 부분과 미해결 부분을 화면에서도 구분해야 한다.

### 내 생각

> 자연스러운 질문을 만들면 바로 답변 평가에 쓸 수 있을 것 같았지만, 질문마다 필요한 조건과 근거를 연결해야 했다. 특히 기본 상성으로 유리한 기술을 찾는 것과 실제 배틀에서 이길 포켓몬을 보장하는 것은 다른 문제다.

---

## 3. How — 어떻게 작동하는가?

### 작동 과정

1. 사용자가 직접 질문하거나 저장된 생성 질문을 입력 예시로 선택한다.
2. 포켓몬·기술 이름과 현재 주어진 조건을 확인하고, 필요한 경우 빠진 조건만 묻는다.
3. 구조화 자료를 조회하고 기본 타입 상성을 계산한다. 실제 검색 실행 기록이 있으면 그 근거와 순위를 별도로 보여준다.
4. 답변의 결론, 수치, 적용 조건, 출처를 표시한다. 일부만 답할 수 있거나 지원하지 않는 질문은 완료로 처리하지 않는다.
5. 사용자가 후보와 현재 기술을 직접 확인하면 배틀 준비 선택을 정리한다. 실제 배틀 실행은 아직 연결되지 않았다.

### 내 말로 설명하기

> 질문은 사용자의 말 그대로 받아도, 답변은 어떤 조건에서 어떤 자료로 확인했는지 따라갈 수 있어야 한다. 화면의 다섯 단계는 정보를 차례로 확인하는 과정이지 포켓몬 추천의 정답 판정이 아니다.

## 4. 설계·명세 변경 기록

### 변경 전 문제

- 질문 9개의 말투와 정보 요구가 섞이면 쉬운 표현을 만들면서도 원래 질문의 뜻을 잃을 수 있었다.
- 화면에서 로컬 조회 결과와 향후 RAG 검색 비교 결과를 같은 성과처럼 보일 위험이 있었다.

### 수정할 때 중요하게 본 기준

- 원질문의 대상·조건·요구 정보를 유지하고, 질문 후보에는 정답이나 근거를 미리 넣지 않는다.
- 화면에는 실제 연결된 데이터와 실행 상태만 표시한다.
- 사용자 유형별 표현은 달라도 확인할 사실과 계산 기준은 동일하게 둔다.

### 수정 내용과 구현에 미치는 영향

- 세 사용자 유형의 질문과 답변 검수 기준을 정리하고, 질문 후보를 `draft` 상태로 구조 검사했다.
- 다섯 단계의 공통 정보 단위를 화면에 연결했다. PP 개념 근거가 부족한 질문은 `partial`, 실제 피해량·승률 질문은 `unsupported`로 다룬다.
- 검색 비교 화면은 실제 실험 기록을 읽을 때만 해당 결과를 표시하도록 했다. 공식 비교 경로와 추천 성공 기준은 팀에서 더 정해야 한다.

## 6. 협업과 기획 회고

### 함께 발전시킨 내용

- 팀 프로젝트의 도감·상성 자료와 평가 규칙을 질문별 답변 기준에 연결했다.
- 질문 후보 생성은 개발 보조, 평가 질문의 채택과 정답·허용 근거 확정은 별도 검수로 두었다.
- 이상해씨 한 종의 파일럿 청킹·벡터 검색 기록과 151종 전체 검색·공식 평가는 다른 진행 단계임을 확인했다.

## 7. KPT 회고

### Keep — 계속할 것

- 질문 문장을 다듬을 때 원래 묻던 정보와 현재 기술 조건을 함께 대조한다.
- 기본 상성, 자속, 실제 피해량처럼 의미가 다른 수치를 나눠 설명한다.

### Problem — 개선할 것

- PP 개념 설명을 뒷받침할 검수 원문이 아직 연결되지 않았다.
- 화면의 모바일 렌더링과 실제 RAG 서비스 연결은 아직 확인이 필요하다.

### Try — 다음에 시도할 것

- 채택할 질문마다 실제 문서 ID·청크 ID·원문 위치를 연결한다.
- 모바일 화면을 직접 확인하고, 검색·답변 실행 기록을 화면의 비교 영역에 연결한다.
- 팀과 공식 평가 경로 및 추천 성공 기준을 확정한다.
