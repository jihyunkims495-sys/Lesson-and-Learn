## 전체 구조

```text
클라이언트
  → HTTP Method + URL + Header + Body로 요청
  → Uvicorn
  → FastAPI 앱
  → APIRouter가 endpoint 선택
  → Pydantic 입력 검증
  → 처리 로직과 DB 트랜잭션
  → 응답 Header + Body 생성
  → 클라이언트
```

## 1. FastAPI와 REST API

### FastAPI

FastAPI는 Python 타입 힌트를 사용하여 Web API를 구현하는 웹 프레임워크다.

주요 역할은 다음과 같다.

- HTTP 요청을 endpoint 함수에 연결
- Path, Query, Header, Body 데이터 수집
- Pydantic을 이용한 요청·응답 검증
- Python 객체를 JSON 응답으로 변환
- `Depends`를 이용한 공통 기능 주입
- OpenAPI 명세와 Swagger UI·ReDoc 자동 생성

### REST API

REST는 API를 설계하는 방식이다. 데이터를 회원·상품·주문 같은 리소스로 표현하고 HTTP Method로 행동을 구분한다.

```text
GET    /orders       주문 목록 조회
GET    /orders/10    10번 주문 조회
POST   /orders       주문 생성
PATCH  /orders/10    10번 주문 일부 수정
DELETE /orders/10    10번 주문 삭제
```

### 차이

| 구분 | FastAPI | REST API |
|---|---|---|
| 종류 | Python 웹 프레임워크 | API 설계 방식 |
| 질문 | 무엇으로 구현할까? | 어떤 원칙으로 설계할까? |
| 대표 요소 | `FastAPI`, `APIRouter`, Pydantic | 리소스, HTTP Method, 무상태성 |

FastAPI로 REST API를 구현할 수 있지만 FastAPI를 사용했다고 모든 API가 자동으로 REST 방식이 되는 것은 아니다.

## 2. 트랜잭션

트랜잭션은 여러 데이터베이스 변경을 하나의 논리적인 작업 단위로 묶는 것이다.

```text
모든 작업 성공 → COMMIT
하나라도 실패 → ROLLBACK
```

주문 생성 예시는 다음과 같다.

```text
트랜잭션 시작
  → 재고 확인 및 차감
  → 주문 생성
  → 주문 상품 생성
  → 모두 성공하면 COMMIT
```

주문 상품 생성이 실패하면 앞에서 실행한 재고 차감과 주문 생성도 함께 취소해야 한다.

### ACID

| 속성 | 의미 | 주문 예시 |
|---|---|---|
| 원자성 Atomicity | 전부 성공하거나 전부 실패 | 재고만 차감되는 상태 방지 |
| 일관성 Consistency | 업무 규칙과 제약 조건 유지 | 재고가 음수가 되지 않음 |
| 격리성 Isolation | 동시 작업이 서로 방해하지 않음 | 마지막 재고 중복 판매 방지 |
| 지속성 Durability | 완료된 결과가 장애 후에도 보존 | 완료 주문 유지 |

트랜잭션만 사용한다고 모든 동시성 문제가 해결되는 것은 아니다. 재고 중복 차감 등을 막으려면 상황에 따라 행 잠금, 조건부 갱신, Unique 제약 조건, 적절한 격리 수준과 최종 상태 검사가 필요하다.

HTTP 요청과 DB 트랜잭션은 서로 다른 개념이다.

```text
HTTP 요청
  → 입력 검증
  → DB 트랜잭션 시작
  → 데이터 변경
  → COMMIT 또는 ROLLBACK
  → HTTP 응답
```

## 3. API

API는 Application Programming Interface의 약자다. 프로그램이 다른 프로그램의 기능을 사용하기 위한 규칙이자 계약이다.

```text
사람 → UI → 프로그램
프로그램 → API → 다른 프로그램
```

Web API는 단순한 URL 하나가 아니다. 다음 규칙이 함께 있어야 한다.

- 어떤 HTTP Method를 사용하는가?
- 어떤 Path로 요청하는가?
- 어떤 Header가 필요한가?
- 어떤 Body를 보내는가?
- 성공과 실패 시 어떤 Status Code와 데이터를 반환하는가?

## 4. API 명세

API 명세는 클라이언트와 서버가 사용할 요청·응답 규칙을 문서로 정의한 통신 계약서다.

작성 이유는 다음과 같다.

- 프론트엔드와 백엔드의 통신 규칙 합의
- 개발 전 기능과 데이터 확인
- 누락되거나 중복된 endpoint 발견
- 요청·응답 Schema 설계
- 오류 처리와 테스트 기준 정의
- 변경 영향 범위 확인

### API 명세 항목

| 항목 | 의미 | 작성 이유 |
|---|---|---|
| 기능분류 | 주문·회원·상품 같은 업무 영역 | 관련 API를 그룹화하기 위해 |
| 기능명 | 주문 생성·주문 조회 같은 사람용 이름 | API 목적을 빠르게 이해하기 위해 |
| API Path | `/orders/{order_id}` 같은 리소스 경로 | 호출 주소와 Path Parameter를 합의하기 위해 |
| HTTP Method | `GET`, `POST`, `PATCH` 등 | 리소스에 수행할 행동을 표현하기 위해 |
| 요청 상세 | Path·Query·Header·Body·인증·제약 조건 | 클라이언트 입력과 서버 검증을 합의하기 위해 |
| 응답 상세 | Status Code·응답 Body·Header·오류 | 성공·실패 후 클라이언트 동작을 결정하기 위해 |

### 주문 생성 명세 예시

| 항목 | 내용 |
|---|---|
| 기능분류 | 주문 |
| 기능명 | 주문 생성 |
| API Path | `/orders` |
| HTTP Method | `POST` |
| 요청 상세 | 상품 ID, 수량, 배송지, 인증 Header |
| 응답 상세 | `201 Created`, 주문 ID, 상태, 금액 |

요청 Body 예시:

```json
{
  "items": [
    {
      "product_id": 101,
      "quantity": 2
    }
  ],
  "shipping_address": "서울시 중구"
}
```

성공 응답 예시:

```json
{
  "order_id": 1001,
  "status": "PENDING",
  "total_amount": 59000
}
```

오류도 명세해야 한다.

| Status Code | 의미 |
|---:|---|
| `400` | 잘못된 업무 요청 |
| `401` | 인증 실패 |
| `403` | 권한 부족 |
| `404` | 리소스를 찾을 수 없음 |
| `409` | 재고 부족·중복 등 상태 충돌 |
| `422` | FastAPI 입력 검증 실패 |
| `500` | 예상하지 못한 서버 오류 |

OpenAPI는 API 명세를 YAML 또는 JSON으로 표현하는 표준이고, Swagger UI와 ReDoc은 OpenAPI 명세를 사람이 읽고 테스트할 수 있게 보여주는 화면이다.

## 5. URI와 URL

URI는 리소스를 식별하는 전체 개념이고 URL은 그중 리소스의 위치와 접근 방법까지 알려주는 식별자다.

```text
URI
├── URL: 위치와 접근 방법으로 식별
└── URN: 이름으로 식별
```

| 구분 | URI | URL |
|---|---|---|
| 목적 | 리소스 식별 | 리소스 식별 + 위치·접근 방법 |
| 범위 | 상위 개념 | URI의 부분집합 |
| 예 | `urn:isbn:9780132350884` | `https://example.com/books/10` |

URL의 구성은 다음과 같다.

```text
https://api.example.com:443/orders/10?include=items
\___/   \_____________/ \_/ \________/ \___________/
scheme        host      port    path         query
```

API 명세의 API Path는 전체 URL이 아니라 URL 안의 경로 부분이다.

```text
Base URL + API Path = 전체 URL

http://127.0.0.1:8000 + /v1/order
= http://127.0.0.1:8000/v1/order
```

## 6. 서버와 클라이언트

클라이언트는 요청을 시작하고 서버는 요청을 기다렸다가 처리하여 응답한다.

| 구분 | 클라이언트 | 서버 |
|---|---|---|
| 역할 | 요청을 보냄 | 요청을 처리하고 응답함 |
| 예 | 브라우저, Postman, 모바일 앱 | FastAPI, PostgreSQL, Nginx |

같은 컴퓨터에서도 서로 다른 프로그램이 두 역할을 할 수 있다.

```text
같은 PC
├── 브라우저 프로세스: 클라이언트
└── Uvicorn + FastAPI 프로세스: 서버
```

서버와 클라이언트는 기기의 고정된 이름이 아니라 특정 통신에서 맡는 역할이다.

```text
브라우저 → FastAPI
브라우저는 클라이언트, FastAPI는 서버

FastAPI → PostgreSQL
FastAPI는 DB 클라이언트, PostgreSQL은 DB 서버
```

## 7. APIRouter

`APIRouter`는 관련 endpoint를 기능별로 묶어 별도 파일로 분리하는 도구다.

현재 주문 router는 다음과 같이 선언되어 있다.

```python
router = APIRouter(prefix="/v1/order", tags=["Orders"])
```

```python
@router.get("")
async def test1():
    return {"message": "테스트1"}

@router.get("/test")
async def test2():
    return {"message": "테스트2"}
```

최종 endpoint는 다음과 같다.

```text
GET /v1/order
GET /v1/order/test
```

계산 방식:

```text
router prefix + decorator path = 최종 Path

/v1/order + ""      = /v1/order
/v1/order + /test   = /v1/order/test
```

Router 파일을 만드는 것만으로 URL이 활성화되지는 않는다. 메인 FastAPI 앱에서 등록해야 한다.

```python
app = FastAPI()
app.include_router(order_routher)
```

폴더 위치가 URL을 자동으로 만드는 것도 아니다. `prefix`, decorator Path, `include_router()` 등록이 최종 route를 결정한다.

## 8. HTTP Header와 Body

HTTP 메시지는 크게 시작 줄, Header, 빈 줄, Body로 구성된다.

```http
POST /v1/order HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json
Authorization: Bearer <access-token>

{
  "product_id": 1,
  "quantity": 2
}
```

### Header

Header는 요청·응답을 처리하는 방법에 대한 부가정보다.

| Header | 의미 |
|---|---|
| `Host` | 요청을 받을 서버 주소 |
| `Content-Type` | Body의 데이터 형식 |
| `Authorization` | 인증정보 |
| `Accept` | 원하는 응답 형식 |
| `User-Agent` | 요청을 보낸 프로그램 정보 |

FastAPI에서는 `Header()`로 값을 가져온다.

```python
from typing import Annotated
from fastapi import Header

async def read_order(
    x_order_token: Annotated[str, Header()],
):
    ...
```

Python의 `x_order_token`은 HTTP Header의 `X-Order-Token`과 연결된다.

### Body

Body는 실제로 전달할 내용이다.

```json
{
  "product_id": 1,
  "quantity": 2
}
```

| 위치 | 역할 | 예 |
|---|---|---|
| Path | 특정 리소스 식별 | `/orders/10` |
| Query | 검색·필터 조건 | `?status=PAID` |
| Header | 인증·형식 등 부가정보 | `Authorization` |
| Body | 생성·수정할 실제 데이터 | 상품 ID와 수량 |

현재 Jinja2 코드의 `student_context`는 클라이언트가 보낸 요청 Body가 아니다. 서버가 Jinja2에 전달하는 렌더링 데이터이며, Jinja2가 완성한 HTML이 HTTP 응답 Body가 된다.

```text
GET /practice1
  → 요청 Body 없음
  → 서버가 student_context 생성
  → Jinja2가 HTML 렌더링
  → 완성된 HTML을 응답 Body로 전송
```

## 9. 소프트웨어와 하드웨어

하드웨어는 실제 물리적 장치이고 소프트웨어는 하드웨어에 수행할 작업을 지시하는 프로그램이다.

| 구분 | 하드웨어 | 소프트웨어 |
|---|---|---|
| 형태 | 물리적 부품 | 프로그램·명령 |
| 예 | CPU, RAM, SSD, 네트워크 장치 | Windows, Python, FastAPI, Uvicorn |
| 문제 | 부품 손상·고장 | 버그·문법 오류·설정 오류 |

FastAPI 실행 시 연결은 다음과 같다.

```text
Python·FastAPI 코드
  → CPU가 명령 실행
  → RAM이 실행 중 데이터 보관
  → SSD가 파일과 로그 저장
  → 네트워크 장치가 HTTP 데이터 전송
```

서버는 두 의미로 쓰일 수 있다.

- 서버 소프트웨어: Uvicorn, FastAPI, PostgreSQL
- 서버 하드웨어: 서버 소프트웨어를 실행하는 컴퓨터

## 10. HTTP Method

HTTP Method는 클라이언트가 리소스에 어떤 행동을 요청하는지 나타낸다.

| Method | 대표 역할 | 예 |
|---|---|---|
| `GET` | 조회 | 주문 목록 조회 |
| `POST` | 생성·처리 요청 | 주문 생성 |
| `PUT` | 전체 교체 | 회원 정보 전체 교체 |
| `PATCH` | 일부 수정 | 주문 상태 변경 |
| `DELETE` | 삭제 | 장바구니 항목 삭제 |
| `HEAD` | Body 없이 Header 조회 | 파일 메타데이터 확인 |
| `OPTIONS` | 지원하는 통신 옵션 확인 | CORS 사전 요청 |

Path가 같아도 Method가 다르면 다른 endpoint다.

```text
GET  /orders → 주문 목록 조회
POST /orders → 주문 생성
```

따라서 endpoint를 구분하는 핵심 조합은 다음과 같다.

```text
HTTP Method + Path = endpoint
```

### PUT과 PATCH

| 구분 | PUT | PATCH |
|---|---|---|
| 수정 범위 | 전체 교체 | 일부 수정 |
| Body | 전체 데이터 | 변경할 필드 |

### 안전성과 멱등성

| Method | 서버 상태 변경 없음 | 같은 요청 반복 시 최종 상태 동일 |
|---|---:|---:|
| GET | 예 | 예 |
| POST | 아니요 | 보장되지 않음 |
| PUT | 아니요 | 예 |
| PATCH | 아니요 | 보장되지 않음 |
| DELETE | 아니요 | 예 |

같은 주문 생성 `POST`를 두 번 보내면 주문이 중복 생성될 수 있으므로 주문·결제 API에서는 idempotency key 같은 중복 방지 장치를 사용하기도 한다.

## 11. 정적 자원과 public·static 폴더

정적 자원은 요청할 때마다 서버에서 새로 계산하지 않고 파일 그대로 전달하는 이미지, CSS, 글꼴, 아이콘 같은 자원이다.

### Next.js의 public 폴더

Next.js 프로젝트 루트의 `public` 폴더에 있는 파일은 Base URL부터 시작하는 경로로 접근할 수 있다.

```text
public/images/logo.png
→ /images/logo.png
```

`public`은 공개 제공용이므로 비밀번호, 서버 설정, 소스 코드처럼 외부에 노출하면 안 되는 파일을 넣으면 안 된다. 또한 요청 중 업로드된 파일을 영구 보관하는 저장소로 사용하는 구조와도 구분해야 한다.

### FastAPI와 Jinja2의 static 폴더

Jinja2 자체가 폴더를 자동 공개하는 것은 아니다. FastAPI가 `StaticFiles`로 특정 디렉터리를 URL 경로에 mount해야 한다.

```python
from fastapi.staticfiles import StaticFiles

app.mount("/static", StaticFiles(directory="static"), name="static")
```

```html
<link
    rel="stylesheet"
    href="{{ url_for('static', path='/css/style.css') }}"
>
```

```text
정적 파일을 보관하는 폴더
→ FastAPI가 /static 경로에 mount
→ Jinja2가 url_for로 URL 생성
→ 브라우저가 CSS·이미지를 별도 요청
```

## 12. python-multipart와 파일 업로드

`python-multipart`는 FastAPI가 `multipart/form-data` 형식의 Form 필드와 업로드 파일을 해석할 때 사용하는 패키지다.

```bash
uv add python-multipart
```

HTML 파일 업로드 Form에는 다음 설정이 필요하다.

```html
<form action="/file" method="post" enctype="multipart/form-data">
    <input type="text" name="title">
    <input type="file" name="file">
    <button type="submit">업로드</button>
</form>
```

`enctype`을 생략하면 Form의 기본 인코딩인 `application/x-www-form-urlencoded`가 사용된다. 이 형식은 일반 텍스트 필드에는 적합하지만 파일의 이름·콘텐츠 타입·바이트를 파일 part로 표현하기에 적합하지 않다.

`multipart/form-data`는 하나의 요청 Body를 boundary로 구분된 여러 part로 나눈다.

```text
요청 Body
├── title part: 문자열
└── file part
    ├── 필드명
    ├── 파일명
    ├── Content-Type
    └── 파일 bytes
```

오케스트라 악보에 여러 파트가 있는 것처럼, 하나의 Body 안에 서로 다른 종류의 데이터를 part별로 나눈다고 이해할 수 있다.

FastAPI에서는 `UploadFile`로 파일을 받는다.

```python
from fastapi import FastAPI, UploadFile

app = FastAPI()


@app.post("/file")
async def upload_file(file: UploadFile):
    content = await file.read()
    return {
        "filename": file.filename,
        "content_type": file.content_type,
        "size": len(content),
    }
```

`UploadFile`이 요청된 파일을 읽을 수 있게 해 주지만, 애플리케이션의 영구 저장 경로에 자동 보관하지는 않는다. 파일을 계속 보존하려면 검증 후 직접 디스크나 객체 저장소에 저장하는 로직이 필요하다.

## 13. 표현 계층

표현 계층(Presentation Layer)은 외부 요청을 받아 애플리케이션이 이해할 수 있는 형태로 전달하고, 처리 결과를 HTTP 응답으로 표현하는 계층이다.

FastAPI 프로젝트에서는 보통 다음 요소가 표현 계층에 속한다.

- `APIRouter`와 endpoint
- Path·Query·Header·Body 입력 수집
- 요청·응답 Schema
- HTTP Status Code와 Error Response
- JSON 또는 HTML 응답 생성

```text
브라우저·앱
→ 표현 계층: HTTP 입력을 해석하고 응답 형식을 결정
→ 애플리케이션·서비스 계층: 업무 규칙 수행
→ 저장 계층: DB 읽기·쓰기
```

표현 계층은 화면 UI만 의미하지 않는다. 백엔드에서는 HTTP API가 외부와 만나는 경계도 표현 계층이다.

## 14. Pydantic의 검증 범위

Pydantic은 타입 힌트와 제약조건에 따라 외부 입력을 파싱하고 검증한다.

```python
from pydantic import BaseModel, Field


class OrderStatusChange(BaseModel):
    status: str = Field(min_length=1)
```

Pydantic이 확인할 수 있는 항목은 다음과 같다.

- 필수 필드 존재 여부
- 자료형과 변환 가능 여부
- 문자열 길이와 숫자 범위
- 중첩 객체 구조
- 직접 정의한 validator

반면 `해당 주문이 실제로 존재하는가`, `현재 상태에서 변경 가능한가`, `요청자가 이 주문의 소유자인가` 같은 업무 규칙은 서비스 로직이나 추가 validator·Dependency에서 따로 확인해야 한다.

## 15. 토큰

토큰은 사용자가 인증되었거나 특정 권한을 가졌다는 사실을 서버에 제시하기 위한 문자열 형태의 자격 정보다.

```text
로그인 성공
→ 서버 또는 인증 시스템이 토큰 발급
→ 클라이언트가 토큰 보관
→ 요청 Header에 토큰 전달
→ 서버가 토큰의 유효성·만료·권한 확인
```

```http
Authorization: Bearer <token>
```

수업 코드의 `X-Token` 비교는 Dependency 흐름을 배우기 위한 단순 예제다. 실제 서비스에서는 비밀값을 코드에 직접 작성하지 않고, 만료·서명·권한·폐기 정책이 있는 인증 방식을 사용해야 한다.

## 16. 데코레이터를 사용하는 이유

Python 데코레이터는 함수를 다른 설정이나 동작과 연결하는 문법이다. FastAPI에서는 함수 위에 Method와 Path를 선언하여 route를 등록한다.

```python
@router.get("/{id}")
async def get_order(id: int):
    ...
```

```text
@router.get("/{id}")
→ GET + /{id} 요청을 아래 함수와 연결
→ 함수의 타입 힌트와 매개변수를 분석
→ OpenAPI 문서에 route 정보 반영
```

데코레이터 문법이 FastAPI의 유일한 등록 방법은 아니지만, Method·Path와 처리 함수를 가까이 두어 읽기 쉽기 때문에 기본 방식으로 사용한다. 즉, Python 전체에서 필수인 것이 아니라 현재 FastAPI 코드에서 route를 선언하는 대표 문법이다.

## 17. CORS와 preflight

CORS(Cross-Origin Resource Sharing)는 브라우저의 JavaScript가 다른 Origin의 자원에 접근할 때, 서버가 허용한 Origin인지 응답 Header로 판단하게 하는 정책이다.

Origin은 다음 세 가지 조합이다.

```text
프로토콜 + 도메인 + 포트
```

다음 주소는 서로 다른 Origin이다.

```text
http://localhost:3000
http://localhost:8000
https://localhost:3000
```

FastAPI에서는 `CORSMiddleware`로 허용 정책을 설정할 수 있다.

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH"],
    allow_headers=["Authorization", "Content-Type"],
)
```

### Preflight

Preflight는 브라우저가 실제 교차 출처 요청을 보내기 전에 `OPTIONS` 요청으로 허용 여부를 확인하는 절차다.

```text
브라우저
→ OPTIONS + Origin + 사용 예정 Method·Header
→ 서버가 Access-Control-Allow-* Header로 응답
→ 허용되면 실제 요청 전송
→ 허용되지 않으면 브라우저가 JavaScript의 응답 접근 차단
```

모든 교차 출처 GET·POST 요청이 preflight를 거치는 것은 아니다. 정해진 Method·Header·Content-Type 조건을 만족하는 단순 요청은 실제 요청을 바로 보내고, 응답의 CORS Header를 검사한다. `PATCH`, 사용자 정의 Header, `application/json` 같은 조건은 보통 preflight를 발생시킨다.

CORS는 브라우저가 적용하는 응답 접근 정책이므로 일반적인 서버 간 HTTP 클라이언트에는 같은 방식으로 강제되지 않는다. 그러나 인증·권한 검사는 CORS와 무관하게 서버에서 항상 수행해야 한다.

## 18. VPN과 국가 우회

VPN(Virtual Private Network)은 사용자 기기와 VPN 서버 사이에 암호화된 터널을 만들고, 네트워크 트래픽을 VPN 서버를 거쳐 목적지로 전달하는 기술이다.

```text
사용자 기기
→ 암호화된 VPN 터널
→ 다른 지역의 VPN 서버
→ 목적지 서버
```

목적지 서버에는 사용자의 원래 공인 IP 대신 VPN 서버의 공인 IP가 보일 수 있다. 다른 국가의 VPN 서버를 선택하면 서비스가 접속 위치를 그 국가로 추정할 수 있어 흔히 국가 우회라고 부른다.

VPN은 다음 문제와는 별개다.

- CORS: 브라우저의 Origin 기반 응답 접근 정책
- 인증·권한: 사용자가 해당 기능을 사용할 자격이 있는지 검사
- 서비스 지역 정책: 서비스가 VPN IP나 계정 지역을 별도로 차단할 수 있음

VPN이 익명성이나 모든 보안을 자동 보장하는 것은 아니며, VPN 제공자와 서비스 이용약관을 신뢰하고 확인해야 한다.
