# TIL | 2026-11-10 | 공연·회차 조회 캐시와 DB/API 흐름

> LV.2 / Week 13 · 프로젝트 2 작업 기록

> **공연·회차 공개 조회에 인메모리 캐시를 적용하고, 실제 예매 판단에 사용하는 DB 경로와 구분해 검토했다.**

> 캐시 대상은 반복 조회 빈도, 변경 빈도, 이전 값을 잠시 표시해도 되는 범위를 기준으로 선택한다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- 공연은 무엇을, 회차는 언제 하는지 저장한다. 좌석 등급은 회차별 등급·가격·등록 수를, 개별 좌석은 자리와 현재 상태를 저장한다.
- 예매 한 건이 생겨도 공연 소개와 일정은 보통 그대로지만, 좌석·예매·결제 상태는 바뀐다.
- 캐시는 DB에서 읽어 만든 공개 데이터의 복사본이며, DB가 원본이다.
- 현재 적용한 것은 서버 프로세스의 메모리를 쓰는 InMemoryBackend다. Redis 서버는 사용하지 않는다.

### 핵심 코드

서버 시작 시 실행하도록 연결한 캐시 초기화 함수다. 앱·상수·키 생성 함수가 있는 문맥에서 발췌했다.

```python
def init_catalog_cache(app: FastAPI) -> None:
    """실제 서버 시작 시 프로세스 메모리 캐시를 준비한다. 외부 연결은 없다."""
    FastAPICache.init(
        InMemoryBackend(), prefix=CATALOG_CACHE_PREFIX,
        key_builder=catalog_cache_key_builder,
    )
    app.state.catalog_cache_enabled = True
    logger.info("공연·회차 인메모리 조회 캐시 활성화")
```

### 오늘 수행한 실습

- 공개 조회 4개의 캐시·DB 저장 성공 후 무효화와 검사·설명 문서를 PR #72로 반영하고 dev 병합을 확인했다.
- 공연 → 회차 → 좌석 → 예매의 연결과 API 호출 순서를 하나의 사례로 정리했다.
- 공연 접근 추상 계약·인프라 어댑터를 개인 로컬에 적용하고 담당 회귀 검사를 다시 실행했다.
- 팀 테스트 배포에서 회원가입·로그인·공연/회차/좌석 조회·예매 확인 화면을 점검했다.
- k6의 API별 검증과 전체 흐름·부하 테스트 준비 사항을 정리했다. k6 실행은 하지 않았다.

### 실제 작성한 코드와 검증 상태

```text
작성한 코드: 캐시 초기화·키·무효화, 공개 data 함수 4개, 부모 공연 확인, 캐시 검사
검증 방법: 11/10 캐시 PR 게시 전 최종 소스의 단위·격리 통합·회귀 검사
확인한 결과: 프로젝트 Python 269 PASS / 실제 PostgreSQL 5 SKIP, 신규 캐시 검사 15개 포함
추가 확인: 관련 Node 검사 21개 통과, 이후 dev 동기화 시 변경된 프런트 범위 재검사
미완료: 배포 서버의 캐시 적중·무효화·성능, 실제 DB 경쟁·결제 완료·k6 부하 검증
```

269개는 프로젝트 전체 회귀 결과다. 모두 새로 작성한 검사는 아니며 이후 화면 점검에서 전체 검사를 다시 실행한 것도 아니다.

## 2. Why — 왜 필요한가?

### 이 개념이 필요한 이유

공연 상세를 여러 사람이 열면 같은 내용을 반복해서 읽는다. 구매마다 소개·일정이 바뀌지는 않아 공개 조회 결과의 재사용 대상으로 선택했다.

| 데이터 | 캐시를 판단할 때 보는 점 |
| --- | --- |
| 공연 소개·회차 일정 | 여러 사람이 같은 정보를 읽고, 구매할 때마다 바뀌지 않음 |
| 공연장 이름·주소 | 비교적 안정적이므로 다른 캐시 후보가 될 수 있음 |
| 개별 좌석 상태 | 예매 직후 달라질 수 있어 실제 확보 시 DB 조건 확인 필요 |
| 내 예매·결제 결과 | 사용자 구분과 상태 변경에 맞춘 별도 최신성 설계 필요 |

### 내 생각

> 공개 조회의 반복 DB 처리를 줄이면서, 예매를 결정하는 순간에는 필요한 최신 정보를 확인해야 한다.
> 공연·회차만 캐시 가능한 것은 아니며, 이번에는 담당 공개 조회를 우선 적용 대상으로 삼았다.

## 3. How — 어떻게 작동하는가?

### 작동 과정

1. 화면이 공연 API에 제목·소개를 요청한다.
2. 서버가 유효한 캐시를 확인한다. 있으면 공개 데이터를 재사용한다.
3. 없거나 만료됐으면 DB에서 읽고 캐시에 보관한 뒤 응답한다.
4. 회차와 좌석은 각각 필요한 API로 조회한다. 한 요청이 모든 표를 차례로 읽는 구조는 아니다.
5. 실제 예매는 DB에서 공연 시작·예매 기간을 읽고, 좌석은 현재 상태 등 조건이 맞을 때만 연결한다.
6. 공연·회차를 수정하면 DB 저장을 확정한 뒤 관련 캐시를 무효화한다.

### 내 말로 설명하기

> 공연 A의 첫 회차와 둘째 회차는 서로 다른 좌석 기록을 가진다.
> 첫 회차의 R01을 예매하면 그 좌석과 예매 기록이 바뀌고, 공연 제목은 그대로다.
> 제목·일정의 공개 조회는 재사용하되, 좌석 확보는 DB에서 현재 조건을 확인한다.

## 4. 설계·명세 변경 기록

- 변경 전: 공개 조회의 반복 DB 처리와 캐시 도입 후 오래된 값 처리 기준이 필요했다.
- 기준: 기존 API·권한·잠금·DB 저장 경로를 유지하고 공개 조회 결과만 재사용한다.
- 응답: data만 캐싱하고 공통 응답은 새로 만들어 응답 시각을 유지했다.
- 키: 서비스 객체를 제외하고 ID·검색·페이지·날짜를 구분했다.
- 최신성: DB commit 후 무효화하고 변경 세대로 늦은 이전 조회의 재사용을 방지했다.
- 초기 TTL: 공연 목록 30초·상세 60초, 회차 목록·상세 10초.
- 유의점: TTL은 복사본의 유효기간이며 응답 대기·주기적 자동 조회 간격이 아니다.
- 한계: 회차 목록의 부모 공연 DB 확인이 남고, worker 사이 무효화는 공유되지 않는다.

## 6. 협업과 기획 회고

- 조회 캐시의 적용 범위와 공통 초기화·의존성 변경 내용을 공유한 뒤 PR을 준비했다.
- 팀 화면의 조회 성공과 결제 완료 검증을 구분했다. 최종 예매 생성·결제 버튼은 제출하지 않았다.
- 기획·구현 회고에서는 병합된 코드와 미병합 개선안을 구분했다. Rich Domain 보완 PR #60은 미병합이다.

---

### 추가 구조 개선: 추상 계약과 인프라 어댑터 적용

- 회차가 요구하는 공연 조회·소유권 확인을 `ABC`와 `@abstractmethod`로 선언하고 개인 로컬 코드에 적용했다.
- 실제 공연 서비스 호출과 최소 반환 정보 변환은 회차의 인프라 어댑터로 분리했다. 조립 코드가 기존 요청 세션의 공연 서비스를 어댑터로 감싸 주입한다.
- 일반 API·캐시 검사도 새 어댑터를 거치도록 기존 테스트 연결을 바꿨다. 실제 개인 로컬에서 API·캐시 57개와 의존성·트랜잭션 4개, 총 61개가 통과했다.
- 담당 import 경계 위반 제거와 OpenAPI 전체 동일성을 확인했다. 추상 클래스 직접 생성 차단, 잠금 옵션·인증 사용자 전달, 기존 예외 전파도 확인했다.
- 기존 권한·잠금·트랜잭션·응답 계약은 유지했다. 이번 구조 개선에서 실제 PostgreSQL 경쟁·부하·배포 검사는 실행하지 않았다.
