# TIL | 2026-11-09 | AWS EC2와 Docker 배포 흐름

> LV.2 · Week 13 · AWS EC2와 Docker 서버 배포

> **로컬에서 만든 API를 AWS 서버로 옮기는 과정은 코드만 배포하는 일이 아니라 컴퓨터, 운영체제, 네트워크, 실행 환경을 차례로 연결하는 작업이었다.**

> API 연동과 구현에서 AWS까지 범위가 넓어져 막막했지만, 배포를 여러 계층으로 나누어 보면 한 단계씩 확인할 수 있다는 것을 배웠다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- EC2 인스턴스는 백엔드 애플리케이션을 실행하기 위해 AWS에서 빌린 가상 컴퓨터 한 대다.
- Ubuntu는 EC2 인스턴스에서 실행되는 운영체제이고, SSH는 내 컴퓨터에서 원격 서버에 접속하는 방법이다.
- 키 페어는 SSH 접속 권한을 확인하고, 탄력적 IP는 외부에서 서버를 찾아갈 수 있는 고정 주소 역할을 한다.
- Docker는 애플리케이션과 실행 환경을 컨테이너로 묶어 개발 환경과 서버 환경의 차이를 줄인다.
- PowerShell과 Ubuntu 셸은 서로 다른 컴퓨터 환경이므로 명령을 입력할 위치를 먼저 확인해야 한다.

### 핵심 명령

```bash
ssh -i <key-file> ubuntu@<elastic-ip>
sudo apt update
docker --version
docker compose version
```

앞의 두 명령은 원격 서버 접속과 패키지 목록 갱신 과정에서 사용했다. Docker 버전 명령은 설치가 끝난 뒤 성공 여부를 확인하기 위한 다음 검증 항목이며, 오늘 성공 결과까지 확인한 것은 아니다.

### 오늘 수행한 실습

- SSH로 EC2의 Ubuntu 서버에 접속했다.
- Ubuntu 패키지 목록을 갱신했다.
- 서버에서 프로젝트 디렉터리를 정리하고 의존성 동기화를 시도했다.
- Docker 패키지 설치를 시도하며 공식 저장소와 공개키의 역할을 확인했다.
- Docker 저장소가 설치된 공개키 파일을 참조하지 않아 서명 검증에 실패하는 상황을 확인했다.

### 실제 작성한 코드와 검증 상태

```text
작성한 코드: 애플리케이션 코드 변경 없음
검증 방법: SSH 접속, Ubuntu 패키지 갱신 결과, Docker 키와 저장소 설정 확인
확인한 결과: EC2 접속과 Ubuntu 저장소 갱신 성공, Docker 저장소 오류 원인 확인
미완료: Docker 설치, 컨테이너 실행, PostgreSQL 연결, API 기동과 외부 요청 검증
```

---

## 2. Why — 왜 필요한가?

### 이 개념이 필요한 이유

- 로컬 컴퓨터를 끄더라도 사용자가 API를 사용할 수 있으려면 계속 실행되는 서버가 필요하다.
- EC2를 사용하면 필요한 성능의 가상 컴퓨터를 만들고 백엔드 애플리케이션을 실행할 수 있다.
- Docker를 사용하면 Python과 라이브러리 버전 같은 실행 환경을 함께 관리하여 서버마다 설정이 달라지는 문제를 줄일 수 있다.
- 원격 접속, 네트워크 주소, 운영체제, 컨테이너의 역할을 구분해야 오류가 발생한 계층을 찾을 수 있다.

### 내 생각

API를 만드는 것까지는 애플리케이션 코드의 문제라고 생각했지만, 실제 서비스로 제공하려면 그 코드를 실행할 컴퓨터와 운영체제, 외부 접속 경로, 데이터베이스, 실행 환경까지 연결해야 했다. 모든 것을 한꺼번에 이해하려고 하니 막막했지만, 각 단계를 분리하면 지금 어디에서 멈췄는지 찾을 수 있었다.

---

## 3. How — 어떻게 작동하는가?

### 작동 과정

1. AWS에서 Ubuntu가 설치된 EC2 인스턴스를 생성한다.
2. 키 페어와 공인 IP를 사용해 SSH로 원격 서버에 접속한다.
3. Ubuntu의 패키지 정보를 갱신하고 Docker를 설치한다.
4. 프로젝트를 서버로 가져오고 Docker 이미지로 애플리케이션 실행 환경을 만든다.
5. API와 PostgreSQL 컨테이너를 같은 Compose 네트워크에서 실행한다.
6. 서버 포트와 보안 그룹을 설정하고 외부에서 API 요청을 확인한다.

### 내 말로 설명하기

EC2는 인터넷에 연결된 원격 컴퓨터이고 Ubuntu는 그 컴퓨터를 움직이는 운영체제다. SSH로 그 컴퓨터에 들어간 뒤 Docker를 설치하면, 내가 만든 API와 필요한 실행 환경을 컨테이너로 묶어 서버에서 실행할 수 있다. 문제가 생기면 SSH 접속, Ubuntu 설정, Docker 설치, 컨테이너 실행, API 연결 순서로 나누어 확인해야 한다.

---

## 5. 오늘의 문제 해결

### 문제 상황

- 하려고 했던 것: Ubuntu 서버에 Docker를 설치하고 애플리케이션 배포 환경을 준비한다.
- 발생한 문제: Docker 패키지를 찾지 못하거나 저장소 서명을 확인할 수 없다는 오류가 발생했다.
- 오류 메시지:

```text
Package 'docker-ce' has no installation candidate
NO_PUBKEY
The repository is not signed
```

### 문제의 원인

- Docker 공식 저장소 설정이 완성되기 전에 패키지 설치를 시도했다.
- 공개키 파일을 설치했지만 기존 저장소 항목이 그 키 파일을 참조하지 않았다.

### 해결 원리

Ubuntu는 패키지를 설치하기 전에 해당 저장소가 신뢰할 수 있는 곳인지 서명을 검증한다. 따라서 공개키 파일을 두는 것만으로는 충분하지 않고, Docker 저장소 설정이 그 키 파일을 `Signed-By`로 참조해야 한다. 오늘은 원인을 확인했으며 저장소 설정 교체와 Docker 설치 성공 여부는 다음 단계에서 검증해야 한다.

## 7. KPT 회고

### Keep — 계속할 것

- 오류 메시지와 현재 프롬프트를 함께 확인해 어느 컴퓨터에서 실행한 명령인지 구분한다.
- 설치 명령을 연속해서 입력하기보다 각 단계의 결과를 확인하고 다음으로 넘어간다.

### Problem — 개선할 것

- API 구현, 클라우드 서버, 네트워크, Docker가 한꺼번에 연결되면서 전체 과정이 너무 크게 느껴졌다.
- Docker 설치와 컨테이너 실행을 아직 완료하지 못해 전체 배포 흐름이 실제로 이어지는지는 확인하지 못했다.
- 개념을 직접 설명하거나 명령을 독립적으로 재현하는 별도 이해도 평가는 진행하지 않았다.

### Try — 다음에 시도할 것

- 배포 과정을 `EC2 접속 → Ubuntu 준비 → Docker 설치 → DB 실행 → API 실행 → 외부 요청`으로 나누어 한 단계씩 확인한다.
- 각 명령을 실행하기 전에 PowerShell용인지 Ubuntu용인지 먼저 표시한다.
- Docker 설치 후 버전, 서비스 상태, 테스트 컨테이너 실행을 각각 검증한다.
