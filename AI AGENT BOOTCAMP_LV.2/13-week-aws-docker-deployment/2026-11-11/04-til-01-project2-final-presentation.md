# TIL | 2026-11-11 | 프로젝트 2 발표회와 백엔드 구조 회고

> LV.2 / Week 13 · 프로젝트 2 발표 회고

> **13일간의 프로젝트를 돌아보며, 좋은 백엔드는 코드를 구현하는 데서 끝나지 않고 사용자의 여러 상황을 정보의 흐름과 책임으로 구조화하는 일이라는 점을 배웠다.**

> 프론트엔드의 사용자 행동이 백엔드 API와 4계층을 거쳐 처리되는 전체 흐름을 연결해서 볼 수 있게 되었다.

---

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- 기능을 구현하기 전에 사용자가 겪을 수 있는 여러 상황을 나누고, 각 상황에서 어떤 정보가 들어와 어떻게 처리되는지 설계해야 한다.
- 도메인은 단순히 DB 테이블이나 저장 방식을 뜻하지 않는다. 서비스가 해결하려는 핵심 업무 개념과 규칙을 뜻한다.
- 4계층 구조는 요청 처리, 사용 사례 조율, 업무 규칙, 데이터 접근의 책임을 나누어 정보의 흐름을 명확하게 만든다.
- 계층별 의존성을 낮추면 화면이나 DB 구현이 바뀌더라도 핵심 규칙에 미치는 영향을 줄일 수 있다.

### 오늘 확인한 활동

- 백엔드 프로젝트 2의 최종 발표회를 보며 13일간의 구현과 설계 과정을 돌아봤다.
- 프론트엔드에서 시작되는 사용자 행동이 API 요청과 백엔드 처리 흐름으로 이어지는 과정을 정리했다.
- 오늘 새 코드를 작성하거나 테스트한 것은 아니며, 프로젝트 전체 구조와 배운 점을 회고했다.

---

## 2. Why — 왜 필요한가?

### 이 개념이 필요한 이유

사용자는 같은 기능에서도 서로 다른 상태와 조건을 가진다. 예를 들어 티켓 예매에서는 로그인 여부, 예매 가능 기간, 남은 좌석, 기존 예매 상태에 따라 처리 결과가 달라진다. 이런 경우를 미리 나누지 않으면 하나의 함수나 계층에 검증, 처리, 저장 책임이 섞이기 쉽다.

4계층으로 책임을 나누면 다음 질문에 답하기 쉬워진다.

- 요청과 응답 형식은 어디에서 다루는가?
- 하나의 기능이 실행되는 순서는 누가 조율하는가?
- 예매 가능 여부 같은 핵심 규칙은 어디에 있는가?
- DB 조회와 저장은 어디에서 구현하는가?

### 내 생각

> 처음에는 백엔드 프로젝트에서 코드를 완성하는 일이 가장 중요하다고 생각했다. 하지만 발표회를 보며 사용자 상황을 나누고, 정보가 한 방향으로 흐르도록 책임을 배치하는 설계가 코드 구현만큼 중요하다는 것을 느꼈다.

---

## 3. How — 어떻게 작동하는가?

### 4계층의 흐름

1. **Presentation** 계층이 프론트엔드의 HTTP 요청을 받고 입력과 응답 형태를 다룬다.
2. **Application** 계층이 하나의 사용 사례에 필요한 작업 순서를 조율한다.
3. **Domain** 계층이 서비스의 핵심 업무 규칙과 상태 변경 가능 여부를 판단한다.
4. **Infrastructure** 계층이 DB나 외부 시스템에 접근해 필요한 데이터를 읽고 저장한다.

```text
사용자 행동
  → 프론트엔드 화면
  → API 요청
  → Presentation
  → Application
  → Domain
  → Infrastructure
  → DB
```

응답은 처리 결과를 가지고 반대 방향으로 돌아오지만, 핵심 의존성은 업무 규칙이 웹 프레임워크나 DB 구현에 끌려가지 않도록 설계한다.

### 내 말로 설명하기

> 프론트엔드가 사용자의 행동을 화면과 요청으로 표현한다면, 백엔드는 그 요청이 어떤 조건에서 처리될 수 있는지 판단하고 결과를 저장한다. 도메인은 이때 필요한 서비스의 핵심 규칙이고, DB는 그 규칙의 결과로 생긴 상태를 보관하는 수단이다. 4계층 구조는 각 단계가 맡을 일을 분리해 전체 흐름을 이해하고 변경하기 쉽게 만든다.

---

## 6. 협업과 기획 회고

- 발표회를 통해 각 기능의 코드뿐 아니라 사용자 흐름과 계층 간 연결을 함께 설명하는 일이 중요하다는 점을 확인했다.
- 같은 서비스 안에서도 기능별 도메인이 있고, 각 도메인이 다른 기능과 연결될 때는 필요한 정보와 계약을 분명히 해야 한다.
- 이후 프로젝트에서는 구현 전에 사용자 상황, 입력 정보, 핵심 규칙, 저장할 상태를 먼저 나누어 보고 싶다.

## 7. KPT 회고

### Keep — 계속할 것

- 프론트엔드 화면에서 시작해 API와 DB까지 이어지는 전체 정보 흐름을 따라가며 학습한다.
- 기능을 코드 파일이 아니라 사용자 상황과 업무 규칙을 기준으로 이해한다.

### Problem — 개선할 것

- 4계층을 실제 코드에 적용하면서 각 계층의 책임과 의존성을 분리하는 과정이 가장 어렵게 느껴졌다.
- 도메인과 DB 모델의 역할을 같은 것으로 생각하지 않도록 구분이 더 필요하다.

### Try — 다음에 시도할 것

- 하나의 API를 골라 Presentation → Application → Domain → Infrastructure 순서로 실제 호출 흐름을 추적한다.
- 각 계층이 담당하지 않아야 할 책임도 함께 적어본다.
- 사용자 상황별 정상·실패·경계 사례를 먼저 나눈 뒤 구현한다.
