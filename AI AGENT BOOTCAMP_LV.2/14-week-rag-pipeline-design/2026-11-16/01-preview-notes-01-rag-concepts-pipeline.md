## 전체 구조

    LLM의 한계
    ├─ 지식 컷오프: 학습 종료 시점 이후의 정보 부족
    └─ 환각: 모르는 내용을 그럴듯하게 생성할 수 있음
              ↓
    RAG: 외부 문서를 검색하고 근거를 문맥으로 제공
              ↓
    인덱싱: 수집 → 분할 → 임베딩·저장
              ↓
    질의: 질문 → 검색 → 근거 주입 → 생성
              ↓
    답변과 근거 확인

핵심은 LLM이 모든 지식을 새로 외우게 만드는 것이 아니라, 질문할 때 필요한 문서를 찾아 읽게 만드는 것이다.

## 1강: RAG 개념과 등장 배경

### LLM의 두 가지 한계

- **지식 컷오프:** 모델의 사전 학습이 끝난 기준 시점 이후의 사건이나 최신 데이터는 모델 내부 지식만으로 알기 어렵다. 학습 데이터에 없던 비공개 문서도 같은 문제가 생긴다.
- **환각:** 모델은 답을 알지 못해도 자연스러운 문장을 만들 수 있어 사실이 아닌 내용을 확신하는 말투로 출력할 수 있다.

### 단순 LLM 호출과 RAG 비교

| 비교 항목 | 단순 LLM 호출 | RAG 기반 생성 |
|---|---|---|
| 사용 지식 | 모델 내부 가중치 | 검색된 외부 문서와 모델 지식 |
| 최신 정보 | 학습 시점의 영향을 받음 | 최신 문서를 검색 대상으로 추가 가능 |
| 비공개 자료 | 학습되지 않았다면 알 수 없음 | 접근이 허용된 내부 문서를 검색 가능 |
| 근거 | 출처 추적이 어려움 | 검색된 문서의 출처를 연결 가능 |
| 주요 위험 | 지식 부족과 환각 | 잘못된 검색 또는 근거 무시 |

RAG가 환각을 자동으로 없애는 것은 아니다. 정확한 문서를 검색하고, 모델이 그 근거만 사용하도록 프롬프트와 후처리를 설계해야 환각 가능성을 낮출 수 있다.

### 가장 작은 RAG 구조

    사용자 질문
       ↓
    관련 문서 검색(Retrieve)
       ↓
    검색 문서를 context에 넣어 프롬프트 구성
       ↓
    LLM이 context를 근거로 답변 생성(Generate)

최소 예시는 검색 문서를 context 변수에 넣고, 문서에 없는 내용은 지어내지 않도록 지시하는 ChatPromptTemplate을 사용한다.

### RAG와 파인튜닝 선택 기준

| 목적 | 더 직접적인 선택 |
|---|---|
| 자주 바뀌는 최신 지식 반영 | RAG |
| 내부 문서 검색과 출처 제시 | RAG |
| 특정 말투나 행동 양식 학습 | 파인튜닝 |
| 고정된 작업 패턴이나 출력 형식 강화 | 파인튜닝 |

둘은 경쟁 관계로만 볼 필요가 없다. 프로젝트에 따라 파인튜닝한 모델에 RAG 검색 문맥을 함께 제공할 수도 있다.

## 2강: RAG 파이프라인 5단계 구조

### 인덱싱 단계와 질의 단계

| 구분 | 인덱싱 단계 | 질의 단계 |
|---|---|---|
| 시점 | 사용자 질문 이전 | 사용자 질문 직후 |
| 성격 | 배치 또는 사전 준비 | 실시간 응답 |
| 포함 단계 | 수집 → 분할 → 임베딩·저장 | 검색 → 생성 |
| 결과 | 검색 가능한 문서 저장소 | 근거 기반 최종 답변 |

### 1단계: 문서 수집(Loading)

문서, 웹페이지, 데이터베이스 등의 원본을 프로그램이 다룰 수 있는 텍스트와 메타데이터로 읽는다.

- 입력: 원본 문서
- 출력: 텍스트와 문서 정보
- 주요 위험: OCR 오류, 표와 서식 깨짐, 문자 누락

### 2단계: 문서 분할(Chunking)

긴 문서를 검색에 적합한 작은 단위인 청크로 자른다.

- 입력: 로딩된 문서
- 출력: 여러 개의 청크
- 주요 설정: chunk_size, chunk_overlap
- 주요 위험: 청크가 너무 작아 의미가 끊기거나 너무 커서 서로 다른 주제가 섞임

chunk_overlap은 인접한 청크 일부를 겹치게 해 경계에서 문맥이 끊기는 문제를 줄인다.

### 3단계: 임베딩 및 저장(Embedding & Storing)

각 청크를 의미를 나타내는 숫자 벡터로 바꾸고 벡터 저장소에 보관한다.

- 입력: 청크
- 출력: 청크 벡터와 원문·메타데이터
- 예시: OpenAIEmbeddings, InMemoryVectorStore
- 주요 위험: 도메인 용어의 의미가 충분히 반영되지 않거나 원문과 메타데이터 연결이 누락됨

### 4단계: 검색(Retrieval)

사용자의 질문과 의미가 가까운 청크를 찾아온다.

- 입력: 사용자 질문
- 출력: 관련성이 높은 상위 청크
- 예시: as_retriever의 k=1 설정
- 주요 위험: k가 너무 작거나 검색 품질이 낮아 필요한 근거가 빠짐

### 5단계: 생성(Generation)

검색된 청크를 프롬프트의 문맥으로 넣고 LLM이 최종 답변을 만든다.

- 입력: 질문과 검색된 근거
- 출력: 근거 기반 자연어 답변
- 주요 위험: 모델이 근거를 무시하거나 문서에 없는 내용을 덧붙임

### 단계 사이의 입력과 출력

    원본 문서
      → 로딩된 텍스트
      → 여러 청크
      → 청크별 벡터와 메타데이터
      → 질문과 가까운 검색 결과
      → 검색 근거가 포함된 프롬프트
      → 최종 답변

한 단계의 출력이 다음 단계의 입력이므로, 마지막 답변만 보고 문제를 고치기보다 처음 잘못된 단계가 어디인지 역추적해야 한다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| RAG | 외부 문서를 검색해 LLM의 생성 문맥으로 사용하는 검색 증강 생성 |
| Knowledge Cutoff | 모델 학습 종료 시점 이후 정보를 내부 지식만으로 반영하기 어려운 한계 |
| Hallucination | 사실이 아닌 내용을 그럴듯하게 생성하는 현상 |
| Indexing | 문서를 수집·분할·임베딩하여 검색 가능하게 준비하는 과정 |
| Query | 질문을 받아 관련 청크를 찾고 답변을 만드는 실시간 과정 |
| Chunk | 검색을 위해 나눈 문서 조각 |
| Embedding | 텍스트의 의미를 숫자 벡터로 표현하는 과정 |
| Vector Store | 벡터와 문서 정보를 저장하고 유사도 검색을 지원하는 저장소 |
| Retriever | 질문과 관련된 문서 청크를 가져오는 검색기 |
| Context | 모델이 답변할 때 참고하도록 프롬프트에 넣는 근거 문서 |

## 예상 난점

1. **RAG와 웹 검색을 같은 것으로 오해하기:** 검색 대상은 웹뿐 아니라 내부 문서, 데이터베이스, 벡터 저장소일 수 있다.
2. **인덱싱과 질의가 한 번에 실행된다고 생각하기:** 문서 준비는 보통 질문 전에, 검색과 생성은 질문마다 수행한다.
3. **임베딩이 답변을 생성한다고 생각하기:** 임베딩은 의미 비교용 숫자 표현이고 자연어 생성은 LLM이 담당한다.
4. **검색 성공을 전체 RAG 성공으로 판단하기:** 올바른 청크를 찾아도 생성 단계가 근거를 무시할 수 있다.
5. **chunk_size, chunk_overlap, k를 고정 정답으로 보기:** 문서 구조와 질문 유형에 따라 실험하고 평가해야 한다.

## 코치 보충: 오류를 찾는 순서

1. 원본 문서에 정답이 실제로 있는가?

이 순서를 사용하면 “LLM이 틀렸다”라는 큰 결론 대신 파이프라인의 최초 실패 지점을 찾을 수 있다.
