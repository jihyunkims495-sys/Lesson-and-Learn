## 2. What — 무엇을 배웠는가?

### 핵심 개념

- 사용자 플로우는 고객이 어떤 화면을 거쳐 이동하는지 보여준다.
- 구매 퍼널은 각 단계에서 사용자가 얼마나 다음 단계로 이동하고 이탈하는지 측정하는 구조다.
- 개발 플로우는 타입, 데이터, 컴포넌트와 페이지를 어떤 순서로 구현할지 보여준다.
- 기능 로직 플로우는 입력, 조건 판단, 정상 처리와 예외 처리의 내부 동작을 보여준다.
- 프로젝트 구조를 먼저 확인하면 다른 위치에 같은 역할의 파일을 중복으로 만드는 실수를 줄일 수 있다.
- 한 Pull Request에 한 가지 작업만 담으면 변경 이유와 확인 방법이 명확해진다.

### 현재 확인한 개발 순서

```text
Product 타입
→ Mock 상품 데이터
→ 가격 표시 유틸리티
→ ProductCard
→ ProductGrid
→ 상품 목록
→ ProductDetail
→ 상품 상세
→ 장바구니
```

- 상품 목록, 상품 상세, 장바구니와 상품 데이터 관련 파일이 아직 구현 전 상태임을 확인했다.

- 서비스·개발·기능 로직 플로우를 각각 다른 목적으로 구분했다.

## 3. Why — 왜 필요한가?

### 흐름을 나눠야 하는 이유

- 사용자 플로우만으로는 코드 내부의 조건과 예외 처리를 설명하기 어렵다.
- 기능 로직만으로는 고객이 전체 쇼핑 과정에서 어디로 이동하는지 파악하기 어렵다.
- 개발 순서를 정하지 않으면 공통 타입이 확정되기 전에 여러 컴포넌트를 만들어 다시 수정할 수 있다.
- 필수 기능과 확장 기능을 구분해야 짧은 개발 기간에 핵심 사용자 흐름을 먼저 완성할 수 있다.

### 내 생각

> 학습한 내용을 실제 서비스 코드로 옮기는 일은 아직 막막하게 느껴진다. 특히 실제로 개발할 수 있는 워킹 데이가 이틀뿐이라 어디서부터 시작해야 할지 부담이 컸다. 그래도 서비스 기획회의를 하면서 이 쇼핑몰을 왜 만드는지, 누구의 어떤 문제를 해결하려는지, 어떤 경험을 우선해야 하는지를 팀과 함께 정리할 수 있어서 좋았다. 구현 전에 목적과 타깃, 방향성을 맞춘 덕분에 단순히 화면을 따라 만드는 것이 아니라 우리가 세운 가설을 기능과 화면에 어떻게 반영할지 생각할 수 있게 됐다.

## 5. STAR 작업 기록

### Situation — 상황

ONEPIECE는 패션 상품을 빠르게 탐색할 수 있는 자사몰을 만드는 팀 프로젝트다. 전체 기획에는 상품 탐색부터 장바구니와 결제까지 포함되어 있었지만, 실제 저장소는 기본 홈 화면과 비어 있는 기능 파일이 있는 초기 상태였다. 학습한 개념을 실제 개발로 연결하는 일이 아직 익숙하지 않은 데다 실질적인 워킹 데이가 이틀뿐이어서, 전체 구매 과정을 한꺼번에 다루면 우선순위가 흐려지고 구현을 시작하기도 어려운 상황이었다.

### Task — 해결 과제

- 팀 저장소에서 안전하게 개발을 시작할 수 있어야 했다.
- 현재 구현된 것과 폴더만 준비된 것을 구분해야 했다.
- 짧은 일정 안에서 서비스의 목적·타깃·방향성을 실제 구현 우선순위로 바꿔야 했다.
- 고객 화면 이동, 개발 작업 순서와 기능 내부 조건을 별도로 정리해야 했다.
- 팀원이 같은 Commit, Branch와 Pull Request 규칙으로 협업할 수 있는 기준이 필요했다.

### Action — 실행한 행동

1. 대상 폴더가 비어 있는지 확인한 후 팀 저장소를 복제했다.
2. 저장소의 안내 문서와 실제 파일을 확인해 현재 구현 상태를 점검했다.
3. 플로우를 사용자·구매 퍼널, 개발 순서, 기능 내부 로직으로 분리했다.
4. 기획회의에서 서비스의 목적, 타깃 사용자의 특성과 핵심 가설을 구현 방향과 연결했다.
5. 구현 범위를 P0, P1, P2로 나눠 핵심 상품 탐색 흐름을 우선하도록 정리했다.
6. Commit 형식, Branch 이름, Pull Request 본문과 코드 리뷰 기준을 하나의 팀 문서로 정리했다.

### Result — 결과

- 팀 저장소에서 개발을 시작할 수 있는 기반을 준비했다.
- 홈, 상품 목록, 동적 상품 상세를 첫 번째 구현 범위로 정리했다.
- 상품 타입부터 상세 화면까지 이어지는 개발 의존 관계를 확인했다.
- ONEPIECE 구매 퍼널 사용자 흐름을 시각화했다.
- 팀 개발 컨벤션 문서를 만들었다.
- 짧은 일정 속에서도 팀이 같은 목적과 타깃을 기준으로 기능 우선순위를 판단할 수 있는 방향을 만들었다.
- 서비스 기획이 개발 이전 문서 작업에 그치는 것이 아니라 무엇을 먼저 구현하고 무엇을 미룰지 결정하는 기준이라는 점을 이해했다.
- 상품 목록과 상세 기능 코드는 아직 구현하지 않았고 브라우저 기능 테스트도 진행하지 않았다.

## 6. 문제 해결 기록

### 문제 상황

- 하려고 했던 것: 기존에 준비한 개발 환경에서 팀 저장소 작업을 시작한다.
- 발생한 문제: 기존에 연습하던 구조와 팀 저장소의 폴더 구조가 달라 파일을 그대로 합치면 중복과 경로 충돌이 발생할 수 있었다.

### 문제의 원인

- 같은 역할의 파일이 서로 다른 경로에 배치되어 있었다.
- 프로젝트 전체를 복사하면 팀 저장소의 구조와 설정을 기준으로 유지하기 어려웠다.

### 해결 과정

1. 대상 폴더에 기존 파일이 없는지 먼저 확인했다.
2. 팀 저장소를 그대로 복제하여 별도의 기준 프로젝트로 사용했다.
3. 복제 후 Git 연결 상태와 실제 폴더 구조를 다시 확인했다.
4. 이후 구현은 팀 저장소의 구조와 공통 규칙을 따르기로 했다.

### 해결 결과

- 기존 파일을 덮어쓰지 않고 팀 저장소를 준비했다.
- 팀원이 공유하는 프로젝트 구조를 기준으로 다음 작업을 시작할 수 있게 됐다.

## 7. 회의 및 피벗 기록

### 주요 결정

| 결정 | 이유 | 영향 |
| --- | --- | --- |
| 홈·상품 목록·상품 상세를 먼저 구현 | 핵심 상품 탐색 흐름을 먼저 완성하기 위해 | 상품 데이터와 카드 구현이 최우선 작업이 됨 |
| 장바구니는 다음 단계로 분리 | 상품 탐색 기능을 먼저 안정화하기 위해 | 초기 구현 범위가 줄어듦 |
| 주문과 결제는 이후 확장 | 인증과 결제까지 포함하면 범위가 커지기 때문 | 현재 기간의 개발 집중도가 높아짐 |
| 세 종류의 플로우차트를 따로 작성 | 목적이 다른 흐름이 한 장에서 섞이는 것을 막기 위해 | 기획과 개발 논의를 구분할 수 있게 됨 |
| PR은 한 가지 작업 단위로 작성 | 리뷰와 충돌 해결을 쉽게 하기 위해 | 작업 범위와 확인 방법이 명확해짐 |

### 변경된 접근

```text
변경 전
전체 쇼핑몰 흐름을 한 번에 설계하고 구현

변경 후
핵심 상품 탐색 흐름을 먼저 구현하고 장바구니와 결제를 단계적으로 확장
```

### 남은 결정

- 상품 타입에 색상과 대·중분류 카테고리를 어느 수준까지 포함할지 합의가 필요하다.
- 장바구니를 현재 프로젝트의 필수 범위에 넣을지 최종 확인이 필요하다.
- 담당자 이름을 포함한 Branch 형식을 팀에서 최종 확정해야 한다.

## 8. Git 협업 기록

- 기본 브랜치와 원격 저장소 연결을 확인했다.
- 오늘 기능 Commit은 만들지 않았다.
- Pull Request도 생성하지 않았다.
- 팀 컨벤션 문서는 아직 Commit하지 않은 상태다.

### 합의한 형식

```text
Commit: type: 작업 내용
Branch: 이름/type/작업목적
PR: 한 가지 작업 + 변경 내용 + 확인 방법 + 팀원 리뷰
```

## 9. KPT 회고

### Keep — 계속할 것

- 코드를 작성하기 전에 저장소 상태와 파일 구조를 먼저 확인한다.
- 기능을 우선순위로 나눠 핵심 흐름부터 완성한다.
- 구현 전에 서비스의 목적, 타깃과 핵심 가설을 팀원과 먼저 맞춘다.
- 실제 구현 결과와 앞으로 구현할 계획을 구분해서 기록한다.
- 공용 파일을 수정하기 전에 팀원과 변경 내용을 공유한다.

### Problem — 개선할 것

- 학습한 개념을 실제 기능과 코드로 연결하는 과정은 아직 막막하다.
- 실제 워킹 데이가 이틀뿐이라 기획을 구현으로 빠르게 전환해야 한다.
- 오늘은 기획과 환경 준비 비중이 커서 상품 기능 구현을 시작하지 못했다.
- 상품 타입과 개인별 담당 파일이 아직 최종 확정되지 않았다.
- 만들어둔 기능 파일이 많지만 내용이 비어 있어 파일 존재만으로 진행도를 판단하기 어렵다.

### Try — 다음에 시도할 것

- 상품 타입의 필수 필드를 팀원과 먼저 합의한다.
- 최소한의 Mock 상품 데이터부터 작성한다.
- 상품 카드 한 개를 화면에 출력하고 브라우저에서 직접 확인한다.
- 기획에서 정한 타깃과 방향성이 상품 카드의 정보량과 화면 구조에 실제로 반영됐는지 확인한다.
- 구현 후 `lint`와 `build` 결과를 기록한다.
