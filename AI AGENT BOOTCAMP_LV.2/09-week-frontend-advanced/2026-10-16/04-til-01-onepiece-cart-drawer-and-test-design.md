> **공통 Header에서 열리는 Cart Drawer를 구현하고, 전체 Cart와 수량·금액을 공유하는 흐름을 검증했다.**

> 같은 상품을 여러 화면에서 테스트하려면 화면별 Mock을 따로 늘리기보다 상품·옵션의 식별 관계와 실제 상태 변경을 먼저 연결해야 한다.

## 1. What — 무엇을 배웠는가?

### 핵심 개념

- 화면을 반환하는 컴포넌트와 상태 변경 함수를 반환하는 Custom Hook의 책임을 나눴다.
- Drawer·전체 Cart·Header가 하나의 Zustand 상태를 구독하면 수량과 금액을 함께 갱신할 수 있다.
- 상품금액과 총 수량은 원본 상품 배열에서 계산한다.
- 가격 계산에는 숫자를 사용하고, 표시할 때 공통 포맷 함수를 적용한다.
- Mock 프로필을 생성한 것과 실제 브라우저 행동·측정 결과를 얻은 것은 다른 단계다.

### 핵심 코드

오늘 분리한 Hook은 세 행동을 반환한다.

```tsx
return {
    handleIncreaseQuantity,
    handleDecreaseQuantity,
    handleRemoveItem,
};
```

Drawer는 공통 상품 상태를 읽고 합계를 계산한다.

```tsx
const cartItems = useCounterStore((state) => state.cartItems);
const { handleIncreaseQuantity, handleDecreaseQuantity, handleRemoveItem } =
    useCartActions();

const subtotal = cartItems.reduce(
    (total, item) => total + item.unitPriceAtAdded * item.quantity,
    0,
);
```

공통 가격 함수의 접미사를 KRW로 바꿨다.

```ts
export function formatPrice(price: number): string {
    return new Intl.NumberFormat('ko-KR').format(price) + 'KRW';
}
```

## 2. Why — 왜 필요한가?

기존 CART는 전체 장바구니로 이동하는 링크였다. 탐색 중 현재 담긴 상품과 금액을 확인하도록 우측 Drawer를 추가하고, 전체 화면이 필요할 때 VIEW CART로 이동하도록 구성했다.

Drawer와 전체 Cart가 별도 상태를 가지면 같은 상품의 수량이 다르게 보일 수 있다. 하나의 상태와 행동 함수를 재사용해 이 불일치를 줄였다.

이 UI가 전환율을 높이거나 이탈을 줄였다는 결과는 아직 없다. 오늘 확인한 것은 동작과 화면 구성이다.

## 3. How — 어떻게 작동하는가?

1. 공통 Header의 CART 버튼이 Dialog를 연다.
2. Drawer가 공통 상태의 상품 목록과 Hook의 행동 함수를 목록 컴포넌트에 전달한다.
3. 증가·감소·삭제가 이전 배열을 기준으로 새 배열을 만든다.
4. Header 수량·Drawer 합계·전체 Cart가 같은 변경 상태를 읽는다.
5. VIEW CART는 Drawer를 닫고 `/cart`로 이동한다.

패널 전체는 화면 높이 안에 두고 상품 목록만 스크롤되게 했다. 제목과 주문 요약·버튼은 별도 영역으로 배치했다. 새로고침 후 상태를 보존하는 영속 저장은 구현하지 않았다.

## 4. 설계·명세 변경 기록

### 변경 전 문제

- CART 전체 화면만 있어 탐색 중 간단히 장바구니를 확인할 경로가 부족했다.
- Cart와 공용 상품 Mock의 가격·이름·이미지·옵션이 서로 달랐다.
- 프로필·DB를 먼저 준비하면 바로 퍼널 테스트를 할 수 있는지 검토가 필요했다.

### 수정 기준과 반영 내용

| 구분 | 정리한 방향 | 상태 |
| --- | --- | --- |
| CART 진입 | 우측 Drawer → VIEW CART → 전체 Cart | 구현·검증 |
| UI 규칙 | 영문 문구 대문자, KRW, 좌우 여백 20px | Cart 범위 반영 |
| 버튼 | 회색 배경·회색 테두리 VIEW CART, 검정 CHECKOUT | 구현; CHECKOUT 비활성 |
| 상품 데이터 | 공용 상품을 원본으로 선택 옵션·담은 시점 값 생성 | 후속 구현 |
| 테스트 사용자 | 비회원·구매 0회·1회·2회 이상 회원 | 각 25명 데이터 준비 |
| 테스트 방식 | 중립적 페르소나 과업으로 소규모 실행부터 확인 | 실행 전 |

상품 ID와 Variant ID는 의미가 다르므로 서로 대체하지 않는다. 현재 Cart의 상품을 공용 카탈로그에 맞추는 작업도 아직 하지 않았다. 기존 Snapshot을 현재 가격으로 무조건 갱신하는 정책과는 구분해야 한다.

실험용 DB는 서비스 ERD를 그대로 구현한 것이 아니었다. 현재 ERD의 컬럼·키 대조 전에는 서비스 연결을 보류하기로 했다. 화면 흐름 테스트를 시작하는 데 상품 DB 자체가 필수는 아니므로 공용 Mock 통일과 실제 담기 연결을 먼저 진행한다.

## 5. 오늘의 문제 해결

### Hook으로 옮기는 중 JSX가 남은 오류

- 최초 잘못된 상태: 행동 함수뿐 아니라 페이지의 JSX 반환부까지 `.ts` Hook에 복사했다.
- 직접 원인: JSX가 포함되어 `Parsing error: > expected`가 발생했다.
- 최소 수정: Hook은 세 행동 함수 객체를 반환하고 페이지는 JSX를 반환하도록 나눴다. 페이지의 미사용 setter도 제거했다.
- 재실행 결과: 관련 파일 ESLint 통과 후 Drawer와 전체 Cart에서 행동 공유를 확인했다.

### Header의 hydration 수량 차이

서버 3·클라이언트 2의 수량 차이가 보고됐다. 전체 새로고침 후 상품 3개·CART 3·327,000KRW가 표시되고 오류 화면이 사라졌다. 초기 Mock 변경과 개발 상태의 차이가 원인 후보지만 확정하지 않았다. 재발하면 초기화 흐름을 다시 확인해야 한다.

### Drawer 폭·스크롤·선 정리

폭과 글자 크기의 오타를 고치고 최종 최대 폭을 700px로 정했다. 목록에 `min-h-0 flex-1 overflow-y-auto`, 제목·요약에는 `shrink-0`을 적용했다. 목록 하단 선은 Drawer 범위에서만 제거했다.

### 남은 빌드 문제

PR 준비 시 `npm test`는 3개 통과, `npm run lint`는 오류 0·기존 이미지 경고 2개였다. `npm run build`는 컴파일 후 기존 빈 로그인·체크아웃 경로 4개의 TypeScript 검사에서 실패했다. 상품 상세에서 Header의 Suspense 관련 prerender 진단도 관찰했다.

이 결과는 PR 검증 시점의 결과다. 이후 dev 병합 자체가 전체 빌드 통과를 의미하지 않으며, 최신 통합 코드의 빌드는 다시 실행하지 않았다.

## 6. 협업과 기획 회고

### 회의에서 추가한 범위

- 팀원이 각 화면을 합쳐 테스트 서버를 배포하고 레퍼런스 클론도 비교 환경에 올릴 계획을 공유했다.
- 영문 상품명·서비스 UI 문구는 대문자로, 가격은 KRW로, 좌우 여백은 20px로 맞추기로 했다.
- 가상 사용자·상품과 GA4를 활용해 장바구니 전환, 퍼널, 체류시간을 확인하는 방향을 논의했다.

### 데이터·실험 준비 결과

합성 프로필 100개를 네 코호트 각 25명으로 만들고 A/B에 총 50명씩 배정했다. 상품 4개와 제안 옵션 16개를 준비하고 테이블 5개의 RLS 활성화를 확인했다.

프로필은 Auth 계정이나 실제 주문 이력이 아니다. 목표·예산·선호·사이트 친숙도·기기와 같은 페르소나 조건 및 브라우저 실행은 후속 작업이다. GA4는 아직 연결하지 않았다.

### 피벗과 측정 기준

| 처음 생각한 접근 | 정리한 접근 | 이유 |
| --- | --- | --- |
| 상품 DB를 먼저 연결 | 공용 상품·옵션과 실제 담기부터 연결 | UI 퍼널 검증에 DB 연결 자체는 필수가 아님 |
| 가상 사용자 100명으로 바로 측정 | 소규모 과업·기록 검증 후 확대 | 행동·이벤트·성공 판정이 먼저 동작해야 함 |
| 가상 행동을 고객 지표로 해석 | 합성 과업 결과와 실제 고객 행동을 구분 | AI 실행 시간·중단은 사람의 체류·이탈과 다름 |

두 사이트는 상품·가격·과업 조건을 맞춰 비교해야 한다. 사이트 전체의 차이를 한 가설의 효과로 단정하지 않는다. 실제 상품 상세의 담기 함수는 현재 안내 문구만 표시하므로 상태 추가부터 구현해야 한다.

## STAR 문제 해결 기록

### Situation — 상황

전체 Cart의 행동 로직을 우측 Drawer에서도 사용해야 했고, Hook으로 옮기는 과정에서 페이지 JSX가 함께 남아 오류가 발생했다.

### Task — 해결 과제

두 화면의 수량·삭제 동작을 공유하면서 화면 렌더링과 상태 변경의 책임을 나눠야 했다.

### Action — 실행한 행동

1. 증가·감소·삭제를 Custom Hook으로 분리했다.
2. Hook의 JSX 반환을 제거하고 함수 객체를 반환하도록 수정했다.
3. Drawer와 전체 Cart에 같은 행동을 연결하고 실제 수량·합계·이동·빈 상태를 확인했다.

### Result — 결과

관련 파일의 문법 오류가 사라졌고, 재킷 증가 후 Header 4·516,000KRW와 전체 Cart 이동 후 상태 유지가 확인됐다. 전체 빌드와 상품 상세의 실제 담기 연결은 남아 있다.
