- 관련 문서: [측정 지표](../03-metrics-validation/2026-10-21-03-abc-ga4-metrics-spec.md), [GA4 설정 프로세스](../03-metrics-validation/2026-10-21-05-abc-ga4-setup-process-spec.md)

## 1. 목적과 데이터의 성격

브랜드를 인지하고 조건이 맞으면 구매하려는 20~30대 패션 중·고관여 회원 180명을 설계한다. 각 고객의 정보 확인·예산·상품 조합 기준에 따라 AI 에이전트가 브라우저에서 행동하도록 하고, 그 과정이 GA4와 서비스 데이터에 일치하게 남는지 검증한다.

180명은 실제 고객 조사 표본이나 실제 시장의 분포가 아니다. 균형 비교를 위한 가상 프로필이다. DB에 회원 행을 넣는 작업만으로 브라우저 행동·GA 이벤트는 생성되지 않는다. 모든 고객을 강제로 구매 성공시키거나 구매 전환율을 미리 정하지 않는다.

FGI 고객 1의 깊은 정보 탐색·동일 브랜드 앱 구매 경험, 고객 2의 목적성 탐색·판매량 비교 의견을 출발점으로 사용했다. 아래 6개 유형 전체가 FGI에서 실증된 분류라는 뜻은 아니며 실험 조건으로 설계한 유형이다.

## 2. 공통 고객 조건

| 항목 | 확정 조건 |
| --- | --- |
| 브랜드 인지 | 브랜드를 알고 유입 |
| 회원 상태 | 실제 로그인 가능한 테스트 회원 |
| 유입 목적 | 조건이 맞으면 구매 |
| 연령 | 20~39세를 5세 단위로 구분 |
| 계절·과업 | 10월의 경량 아우터·초겨울 아우터·니트·맨투맨·후디 중심, 일부 팬츠 조합 |
| 첫 진입 | 데스크톱 메인 /, 빈 Cart |
| 탐색 | 담은 뒤 추가 탐색·재확인 허용 |
| 핏 판단 | 필요한 실측·소재·관리 정보를 찾을 수 있는지 우선 평가 |
| 신체 조건 | 실제 키·몸무게·총장·가슴 허용 범위는 임의 생성하지 않음 |
| 혜택 의존 | 혜택 필수형 제외. 쿠폰 등이 없어도 조건에 따라 정가 구매 가능 |
| 후속 채널 | B/C 가설에서는 모바일 웹 /cart로 이어가기 |

현재 상품 데이터에 따라 원하는 품목·정보·가격 조건을 만족하지 못할 수 있다. 이때 대체 탐색·부분 구매·중단을 정책에 따라 기록한다. 사이트에 없는 정보를 만들어 구매 조건을 통과시키지 않는다.

## 3. 180명 배분

### 3.1 연령 × 진입 전 구매 이력

| 연령 | prior_0: 0회 | prior_1: 1회 | prior_2plus: 2회 이상 | 합계 |
| --- | ---: | ---: | ---: | ---: |
| 20~24세 | 15 | 15 | 15 | 45 |
| 25~29세 | 15 | 15 | 15 | 45 |
| 30~34세 | 15 | 15 | 15 | 45 |
| 35~39세 | 15 | 15 | 15 | 45 |
| 합계 | 60 | 60 | 60 | 180 |

purchase_stage_at_entry는 진입 전에 배정한 구매 이력 시나리오다. 유효 구매의 업무 기준은 결제 승인 주문이며 전체 취소는 제외한다. 현재 prior_2plus 등을 뒷받침하는 실제 과거 주문·매출 이벤트를 조작해서 생성한 상태는 아니다.

### 3.2 구매 판단 유형 — 각 30명

| 코드 | 한글 정의 | 행동 기준 | 인원 |
| --- | --- | --- | ---: |
| strict_information | 실측·소재 엄격 확인형 | 필요한 실측·소재·관리 정보를 직접 확인해야 함. 누락 시 확신하지 않고 대체 상품 탐색·중단 가능 | 30 |
| alternative_information_allowed | 대체 정보 허용형 | 일부 정보가 부족해도 실제 제공된 대체 설명·이미지 등으로 판단 가능. 없는 정보를 추정해 채우지 않음 | 30 |
| full_price_allowed | 예산 비교·정가 구매 가능형 | 가격·혜택을 살펴보되 혜택 부재만으로 중단하지 않음. 배정 예산과 상품 조건 충족 필요 | 30 |
| usual_size_new_item_recheck | 익숙한 브랜드의 새 상품 재확인형 | 평소 브랜드 사이즈를 알아도 새 상품의 실측·소재를 다시 확인 | 30 |
| partial_purchase_allowed | 코디·부분 구매 허용형 | 묶음 중 한 품목 조건이 맞지 않으면 조건을 충족한 일부 품목 구매 가능 | 30 |
| complete_outfit_required | 코디·조합 완성 필수형 | 원하는 조합 전체를 충족해야 구매. 일부만 맞으면 재탐색·중단 가능 | 30 |

‘혜택 필수형’은 최종 설계에서 제외했다. full_price_allowed를 할인 필수 고객으로 읽지 않는다.

상위 decision_style은 detail_fit_confidence 60명, budget_benefit 30명, brand_familiar_new_item 30명, outfit_coordination 60명이다. budget_benefit은 보존된 상위 코드이며 혜택 필수를 뜻하지 않는다. 상위 4개 유형을 각각 45명으로 나눈 설계가 아니다.

### 3.3 예산·과업 배분

| 차원 | 배분 |
| --- | --- |
| budget_band | tight / standard / relaxed 각 60명 |
| shopping_mission | single / outer_top / outer_top_bottom 각 60명 |
| 단품 고객 세부 | 아우터 30명 / 상의 30명 |

각 차원의 총합을 균형화했다. 연령×이력 12개 셀은 각각 15명이나, 성향×예산×과업까지 모든 조합이 같은 인원이라는 뜻은 아니다. 코디 성향 60명에게는 단품 과업을 배정하지 않았다.

## 4. 예산 상한

단위는 원이며 **상품 가격 합계 기준**이다. 할인·배송비를 포함하지 않는다. 제안 당시 A 클론의 카테고리 가격을 참고해 정한 실험 상한으로, B·C 현재 카탈로그의 평균 가격을 다시 산출한 값은 아니다.

| 구매 과업 | tight | standard | relaxed |
| --- | ---: | ---: | ---: |
| 아우터 단품 | 230,000 | 280,000 | 320,000 |
| 상의 단품 | 130,000 | 150,000 | 180,000 |
| 아우터+상의 | 370,000 | 420,000 | 480,000 |
| 아우터+상의+팬츠 | 550,000 | 610,000 | 700,000 |

에이전트는 자기 상한 안에서 선택한다. 묶음을 일부만 구매할 수 있는지는 decision_policy에 따른다. 서버가 계산한 상품 합계와 대조하고 배송비를 포함한 최종 결제액은 별도로 기록한다. 배송비로 인한 포기·상한 초과 정책은 본 실험 전에 확정한다.

## 5. 대표 고객 시나리오

컨셉과 브랜드 디테일에 관심이 많은 20대 회원은 초겨울까지 입을 경량 아우터를 찾는다. 총장·가슴 실측과 소재·관리 정보를 확인하고, 브랜드 가치와 예산을 비교한다. 장바구니에 먼저 담은 뒤 다른 상품을 보거나 상세를 재확인할 수 있다. 실제 정보와 가격 조건이 충족돼 확신하면 Checkout으로 진행한다.

이 시나리오는 성공 경로를 강제하는 스크립트가 아니다. 정보 누락·품절·예산 초과를 만났을 때의 선택도 결과다. 기능 오류 때문에 중단한 경우는 고객 성향에 의한 중단과 분리한다.

## 7. 6명 파일럿

180명 안에서 유형별 한 명을 선정했다. 추가 6명이 아니다.

| 회원 | 유형 | 연령 | 진입 전 이력 | 과업 | 예산 |
| --- | --- | --- | --- | --- | ---: |
| sim-member-043 | strict_information | 25~29 | 1회 | 상의 단품 | 130,000 |
| sim-member-180 | alternative_information_allowed | 35~39 | 0회 | 아우터+상의 | 420,000 |
| sim-member-021 | full_price_allowed | 30~34 | 2회 이상 | 아우터+상의+팬츠 | 700,000 |
| sim-member-140 | usual_size_new_item_recheck | 35~39 | 0회 | 상의 단품 | 130,000 |
| sim-member-028 | partial_purchase_allowed | 20~24 | 2회 이상 | 아우터+상의+팬츠 | 700,000 |

파일럿은 성공률을 비교하기보다 회원 전환·이벤트·상품·금액·주문 정합성을 확인한다. 같은 6명을 A/B/C에서 한 번씩 실행하면 18회지만 고객은 6명이다. 기존 A 로컬 6회와 B/C 파일럿은 다른 실행이다.

## 8. 현재 계정·실행 상태

| 환경 | Auth 준비 | 확인한 것 | 미확인 |
| --- | --- | --- | --- |
| A 검증 환경 | 180명 | 생성·재조회. A 로컬 6명 브라우저 계측 파일럿 | 전체 180명 행동·GA 고유 사용자 180명 |
| B/C 검증 환경 | 6명 | 생성·재조회·실제 Auth API 로그인·본인 profiles id 조회 모두 6명 | B/C 브라우저 로그인·Cart·주문·Toss 승인·GA 수신 |

서로 다른 인증 환경의 같은 synthetic_member_key는 같은 설계 고객을 뜻한다. 실제 Auth ID·비밀번호·세션이 자동으로 같아지는 것은 아니다.

not_provisioned/not_started는 설계 시점의 초기 상태다. 계정 준비·인증 확인·브라우저 실행은 서로 다른 상태로 구분한다. 환경별 계정 수를 합쳐 고유 고객 186명이라고 보고하지 않는다.

## 9. Toss 테스트 승인까지의 확장

작성 당시의 후속 확장안은 B/C를 최종 테스트 결제 승인까지 비교하는 것이다. 페르소나 배분은 유지하며 revision 3의 target_action은 checkout_click이다. 현재 실험은 `payment_button_click`에서 종료하고 Toss API를 연결하지 않는다. **아래 승인·purchase 항목은 후속 설계이며 현재 구현·계측 완료나 이번 집계 범위를 뜻하지 않는다.**

실행 단계에는 다음 정보를 구분해 기록한다.

| 실행 정보 | 목적 |
| --- | --- |
| 대상 프로젝트·회원 매핑 | 인증 회원과 설계 고객 연결 |
| site_variant·빌드 버전·실행 ID | B/C·재시도·버전 구분 |
| 테스트 주문 필수 입력 | 실제 주문서 필수 입력을 충족. 개인정보를 임의 수집하지 않음 |
| 주문·결제 시도·상태 | 요청·승인·실패·취소 구분 |
| 주문 금액·승인 시각 | 서버 검증 및 GA 대조 |
| transaction_id·GA 수신 확인 | 중복 구매 방지와 승인 주문 대사 |
| 종료 단계·사유 | 조건 불충족·기능 오류·실행 한도 등을 분리 |

진입 전 시나리오와 이번 테스트에서 실제 승인된 구매 횟수를 구분한다. 과거 주문을 만들거나 과거 purchase를 보내 시나리오를 꾸미지 않는다. payment_key와 서버 키는 GA에 보내지 않는다.

## 10. 실행·판정 조건

1. B/C 검증 환경의 회원·프로필·Cart·주문과 B/C 인증을 연결한다.
2. 같은 회원·과업·예산으로 버전별 시작 상태를 분리한다. B의 주문이 C의 상태를 바꾸지 않도록 한다.
3. 상품·가격·재고·배송 조건을 맞춘다. A·B·C 카탈로그가 동일하다는 검증은 아직 없다.
4. 6명으로 실제 B/C 브라우저의 Cart·Checkout·결제 버튼 클릭과 GA 수신을 대조한다. Toss 승인 대조는 후속 설계로 구분한다.
5. 계측·실행 조건이 통과한 뒤 전체 180명 확대를 결정한다. 실제 브라우저 행동 확대는 별도 검증 후 진행한다.

미정 항목은 안별 실행 횟수·반복·순서, 무작위/교차 배정, 행동·시간 종료 기준, 충분한 탐색·빠른 결제의 판정 기준, 실제 기기 전환 방식이다. 같은 180명이 B/C 각각 1회면 360회 실행이지만 이는 산술 예시이며 확정된 실행 수가 아니다.

비밀번호·인증 토큰·서버 Secret Key는 공유 분석 데이터·GA·이 문서에 포함하지 않는다. 회원 ID는 GA4 전용 User-ID로 다루고, 공유 문서에는 설계 고객 키를 사용한다.

## 10/21 추가 확인 — Vercel 모바일 웹과 실행 기록

모바일 환경은 휴대폰 브라우저용 모바일 웹이다. B는 https://onepiece-b-test.vercel.app, C는 https://onepiece-c-test.vercel.app 이다. 새 설치형 앱이나 네이티브 앱 스트림을 추가하는 범위가 아니다.

프로필의 device=desktop, continuation_channel=mobile_web, continuation_entry_path=/cart는 계획된 탐색·전환 조건이다. 계획 조건과 실제 관찰값은 구분한다. GA의 기기 카테고리·지역은 실제 접속 브라우저/네트워크에서 수집되는 관찰값이다. 프로필에 mobile이나 Seoul을 적는 것으로 그 값이 자동 반영되지 않는다.

실행 시 다음 항목을 구분한다. 작성 당시 아직 실제 측정값을 채운 상태는 아니다.

| 항목 | 구분 | 용도 |
| --- | --- | --- |
| target_url / site_variant / build_version | 실행 조건 | B/C 주소·버전 고정 |
| test_run_id / journey_id / stage | 실행 연결 | 같은 과업의 PC 탐색·모바일 이어가기 연결. journey_id는 원시 로그용이며 GA 맞춤 정의로 무조건 등록하지 않음 |
| planned_device / actual_device_category | 계획 / 관찰 | 계획된 단계와 GA가 측정한 desktop/mobile/tablet 구분 |
| source / medium / campaign | 배정 / 관찰 구분 | 실험용 유입 경로와 실제 GA 세션 소스 대조. 의도 없이 UTM 값을 덧붙이지 않음 |
| cart_restored / checkout_reached / approval_status | 결과 | 실제 확인한 뒤 기록 |

국가·도시는 접속 네트워크 기반의 근사값이며 정밀 위치나 가상 고객의 거주지를 증명하지 않는다. 에이전트가 한 실행 환경에서 움직이면 같은 지역으로 보일 수 있다. PC 창 너비만 줄이는 것은 실제 모바일 접속이나 기기 간 Cart 공유 증거가 아니다.

작성 당시 B/C 검증 환경의 계정 준비 범위는 6명이다. 브라우저 본 실행·GA 고유 사용자 180명·Toss 승인은 여전히 미검증이다.
