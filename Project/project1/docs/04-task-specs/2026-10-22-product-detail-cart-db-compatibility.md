## 방향 판단

기존 장바구니의 항목·합계·삭제·서랍 구조를 유지하고, 상세를 실제 DB 상품·옵션으로 연결하는 방향은 타당하다. 그러나 상품별 옵션을 SQL로 새로 만드는 방안은 이번 **Supabase 수정 금지** 조건에 맞지 않는다. 사이즈 이름만 S/M/L로 바꿔도 실제 옵션 ID는 생기지 않는다.

이번 구현은 DB의 `size_label`과 `product_variants.id`를 그대로 사용한다. 없는 S/M/L 버튼이나 임시 ID를 만들지 않는다. 현재 구매 후보는 세 조합이며, 나머지 16개 상품은 조회만 가능하고 담기는 비활성이다. 전 상품의 구매를 허용하려면 향후 DB 담당자가 옵션을 제공해야 하며 이 PR은 그 작업을 실행하지 않는다.

## 반영한 내용

- 상세의 상품명·판매가·설명·이미지·활성 옵션을 Supabase에서 읽는다. 로딩, 조회 실패·재시도, 없는 상품을 구분한다.
- 재고가 있는 실제 옵션만 선택할 수 있다. 같은 옵션은 기존 한 줄에 수량을 더하고 메타데이터도 최신 조회값으로 갱신한다. 담기는 재고와 99개 한도를 함께 지킨다. FREE 한 옵션만 자동 선택한다.
- 숫자형 예시 실측표를 M/L에 임의로 대응시키지 않는다. DB 사이즈와 표의 행 이름이 맞는 경우에만 기존 사이즈 가이드를 표시한다.
- 이미지 URL 대신 파일 경로를 장바구니에 저장한다. 서랍·장바구니·주문서는 표시 시 URL을 발급하며, 30분 간격 및 화면·네트워크 복귀 시 갱신한다. 이전 장바구니에 남은 같은 프로젝트의 서명 URL에서도 파일 경로를 복구한다. 발급 실패를 무한 로딩으로 표시하지 않는다.
- 장바구니 수량 증가는 결제의 99개 한도를 지킨다. 주문 생성 전에 DB 옵션·판매 상태·재고·가격을 GET 조회로 검사한다. 이전 임시 ID가 남아 있다면 해당 상품명과 삭제·재선택 방법을 안내하고 주문 생성 요청을 보내지 않는다. 기존 서버의 최종 검증은 유지한다.
- 초기 데모 3개와 공용 store·합계·삭제 구조는 유지했다. 옵션 추가 SQL·마이그레이션·정책 변경은 포함하지 않았다.

## 검증과 한계

- 자동 테스트 **44개 통과**, ESLint 통과, 실제 폰트를 사용한 `next build` 및 TypeScript 검사 통과.
- 실제 Supabase로 수정된 상세 조회·담기 함수를 실행: 상품 1/4/5의 실제 옵션 ID 3/2/1을 각각 2개씩 담고, 가격과 이미지 경로를 확인했다. 상품 2의 빈 옵션과 임시 ID 100012 차단을 확인했다. 결제 전 옵션 GET 조회도 통과했다.
- 실제 Storage에 1초짜리 이미지 서명 URL을 발급해 만료 전 200, 만료 후 400, 같은 경로 재발급 후 200을 확인했다. 서명 발급은 파일·버킷·정책 수정 없이 수행했다. 30분 자동 갱신 전체를 실제 시간으로 기다린 검증은 아니다.
- 프로덕션 서버의 브라우저에서 사이즈 미선택 안내, M 선택 후 두 번 담기, 헤더 수량 3→5, 기존 자켓 줄 수량 1→3, 서랍·장바구니·주문서 이미지와 금액, 옵션 없는 상품의 담기 비활성, `/products/abc` 안내를 확인했다.
- **Supabase DB·RLS·Storage 파일·설정은 수정하지 않았다. 주문 생성·결제 승인도 실행하지 않았다.** 주문 저장 역시 DB 쓰기이므로 이번 검증의 범위에 포함하지 않는다. 따라서 실제 결제·주문 저장 완료나 전체 상품 구매 가능을 완료했다고 보고하지 않는다.

## 검토할 파일과 후속 단계

핵심은 `getProductDetail.ts`, `useProductDetail.ts`, `ProductDetail.tsx`다. 장바구니 변경은 이미지 표시, 담기 규칙, 수량 한도이며 주문서 변경은 이미지 표시와 읽기 전용 사전 검사다. `seed-product-variants.sql`을 실행할 필요가 없다.

새 PR을 검토·병합하고 해당 브랜치로 배포해야 기존 서비스에 반영된다. 기존 미커밋 폴더나 배포가 자동으로 갱신되는 것은 아니다. 주문·결제까지 포함한 확인은 DB 쓰기를 허용하는 별도 테스트 범위에서 진행해야 한다.
