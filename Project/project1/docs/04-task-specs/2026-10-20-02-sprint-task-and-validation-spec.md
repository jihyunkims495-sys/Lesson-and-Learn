# ONEPIECE 이번 주·오늘 작업 및 비교 검증 명세

- 기준일: 2026-10-20(화), Asia/Seoul
- 버전: v1.1 — 도메인별 역할 배정 반영
- 대상 기간: 이번 주 스프린트. 정확한 최종 마감은 추가 합의 사항.
- 상태: 후속 질의 답변을 반영한 최종 회의 정리 명세. 구현·측정의 완료 보고와 구분한다.

## 1. 스프린트 목적

정의한 고객의 구매 여정을 바탕으로 레퍼런스 서비스를 분석하고, ONEPIECE를 바이브코딩과 손코딩으로 각각 구현한다. 같은 가상 고객 조건에서 각 구현물의 구매 경로와 측정 지표를 비교하며, 매일 손코딩의 시행착오와 UI 개선 과정을 기록한다.

이번 스프린트는 서비스의 성공·실패나 유일한 정답을 판정하는 작업이 아니다. 분석→고객 정의→구현→측정→개선→리뷰의 과정을 연결하고, 각 팀원이 직접 구현하면서 얻은 학습과 한계를 결과물로 남긴다.

## 2. 비교 대상의 정의

| 대상 | 구현 방향 | 비교에서의 역할 |
| --- | --- | --- |
| A: SAN SAN GEAR 레퍼런스 클론 | 참고 서비스의 화면·구매 경로·데이터 구조를 팀이 재구성 | 오늘 준비하는 레퍼런스 분석·비교 대상 |
| B: ONEPIECE 바이브코딩 버전 | 정의한 고객 동선과 원하는 UI를 바이브코딩으로 구현 | 오늘 구현하고 내일부터 A와 리뷰·측정할 대상 |
| ONEPIECE 손코딩 누적 버전 | 팀원이 맡은 도메인을 각자의 학습 난이도에 맞춰 직접 구현 | 내일부터 일별로 통합·개선하며 A/B와 비교할 대상 |

**명칭 기준:** 확정한 ‘A안=산산기어 클론, B안=ONEPIECE 바이브 구현’을 이 문서 전체에 적용한다. 초기 정리의 ‘바이브=A, 손코딩=B’ 표기와 혼용하지 않는다. 손코딩과 바이브 구현의 비교 목적은 유지하되, 손코딩 결과는 이름과 날짜·버전으로 식별한다.

A/B라는 명칭은 이번 스프린트의 비교 버전을 뜻한다. UI·상품·기능·완성도까지 다르면 측정 차이를 코딩 방식만의 효과로 단정하지 않는다.

레퍼런스 ERD는 팀이 구현을 위해 재구성하는 모델이다. 실제 SAN SAN GEAR의 데이터베이스 구조는 확인하지 않았다.

## 3. 웹·앱 및 백엔드 범위

- 웹 화면과 모바일에서의 구매 여정을 함께 고려한다.
- 설치형 PWA 또는 별도 iOS·Android 앱의 채택 여부는 추가 합의 사항이다. 설명을 들었다는 이유만으로 특정 방식을 확정하지 않는다.
- A와 B는 프론트엔드 화면뿐 아니라 ERD와 백엔드까지 구현하는 방향이다.
- 손코딩 버전은 팀원이 직접 작성한 범위를 일별로 통합한다. 미완성 도메인과 바이브 구현을 재사용한 부분이 있다면 실제 상태를 구분해 기록한다.
- 웹·앱에서 같은 장바구니를 사용하는 고객 경험과, 이번에 실제로 구현하는 연결 범위는 구분한다.
- 사이트별 DB 구조·초기 데이터·격리 방법은 비교 조건 확정 시 기록한다. 사진의 ‘ERD 동일’ 표기만으로 하나의 운영 DB를 공유한다고 해석하지 않는다.

## 4. 고객 정의와 가상 고객

고객 정의는 기존 User FGI 정리에서 출발한다.

- 고객 1: 2026-10-14 인터뷰, 20대 패션 고관여자. 웹에서 깊이 탐색한 뒤 동일 자사몰 앱의 장바구니에서 checkout으로 이동하는 경험.
- 고객 1 인터뷰 이후: 3·4·6 그리드 방향 확정.
- 고객 2: 2026-10-16 인터뷰, 30대 패션 중관여자. 필요한 품목을 검색하고 판매량순 등으로 후보를 비교한 뒤 원하는 상품을 구매하는 경험.
- 두 인터뷰는 평소 커머스 탐색·구매 여정에 초점을 두었다. 두 사례에서 얻은 방향을 전체 고객의 검증된 행동으로 일반화하지 않는다.

가상 고객 구현 담당자는 `@jihyunkims495-sys`이다. 실행 방식은 **고객 성향에 따라 브라우저에서 행동하는 AI 에이전트**로 확정했다. 고객의 성향·목적·초기 구매 이력 등 프로필과, 에이전트가 실제 사이트에서 수행하는 탐색·선택·구매 행동을 나누어 정의한다.

A/B 및 손코딩 버전에 같은 가상 고객 데이터를 사용한다는 회의 결정을 반영한다. 회원 데이터 생성과 AI 에이전트의 실제 브라우저 실행을 각각 확인한다.

비교 실행을 위해 기록할 권장 조건은 다음과 같다. 세부 도구·모델·인원·실행 횟수는 이번 회의에서 확정되지 않았다.

- 동일한 고객 프로필·구매 목적·초기 상태를 기준으로 실행한다.
- 에이전트 모델·지시문·도구 설정과 실행 시점을 남긴다.
- 지표를 보기 위해 실제 행동과 무관한 클릭·구매 이벤트를 임의로 만들어 넣지 않는다.
- 상품·재고·회원 이력 등 조건이 다른 경우 실행 결과와 함께 차이를 기록한다.
- 에이전트의 선택 이유·중단 이유와 실제로 확인된 화면·이벤트·주문 상태를 구분해 남긴다.

## 7. 매일 약 17시 통합·측정 운영

1. 각 담당자는 자신이 직접 구현한 범위와 미완료·오류를 정리한다.
2. 기존 팀 규칙대로 최신 dev 기반 개인 브랜치에서 작업하고, base=dev PR과 팀원 리뷰를 거쳐 dev에 통합한다.
3. TypeScript 오류, lint·build와 관련 정상·예외 흐름을 확인한다. 실제 실행 결과를 기록하며 확인하지 않은 항목은 미확인으로 둔다.
4. 측정에 사용할 dev 통합 버전과 배포 환경을 식별한다. 병합만으로 새 버전이 배포되었다고 간주하지 않는다.
5. 해당 버전에 가상 고객을 실행하고 퍼널별 수집·오류·지표를 확인한다.
6. 발견한 UI 문제와 개선 이유를 정리해 다음 구현에 반영한다.

약 17시는 일별 통합·측정 기준 시각이다. 리뷰나 필수 확인이 끝나지 않은 변경을 시간에 맞추기 위해 완료 처리하지 않는다. 배포·최종 반영의 dev→main PR 규칙은 유지한다.

공용 스타일·레이아웃·상품 데이터·타입·설정 파일을 수정할 때는 기존 규칙대로 팀원에게 먼저 공유하고, PR에 영향 범위를 적는다. 명세 작성 요청으로 코드 변경·PR·병합을 실행하지 않는다.

## 8. 측정 및 비교 기록

각 실행마다 대상 A/B/손코딩, 버전, 실행 일시, 기기·화면 조건, 가상 고객과 초기 상태, AI 에이전트 실행 설정, 시작·종료 단계, 수집된 이벤트와 오류를 남긴다. 상세 지표 정의는 측정 전에 합의한다.

- 탐색·상세·장바구니·로그인·주문·결제 중 실제 구현된 단계만 측정했다고 기록한다.
- 이벤트 전송과 실제 상태 변경을 구분한다. 구매 버튼 클릭을 결제 완료로 계산하지 않는다.
- 결제 승인·주문 저장까지 확인하는지, 주문 시뮬레이션까지만 구현했는지 사이트별로 표시한다.
- 동일 가상 고객을 사용하더라도 초기 장바구니·구매 이력·상품·재고와 실행 조건이 다르면 그 차이를 기록한다.
- 가상 고객의 결과는 시뮬레이션·기술 검증 지표로 표시한다. 실제 고객의 구매 의사나 실구매 성과와 구분한다.
- 아직 수집되지 않은 값은 예측값이나 기대 효과로 남기고, 측정 결과로 채우지 않는다.

퍼널 진입·다음 단계 이동·중단, 단계 소요 시간, 조작·오류·복구, 주문·결제 상태를 우선 기록 후보로 둔다. 구체적인 핵심 지표와 분모·관찰 시간·종료 기준은 현재 미정이다.

## 9. 최종 결과물 시나리오

1. **레퍼런스 서비스 해체 분석:** 화면·데이터 구조·구매 경로와 가상 고객 실행에서 확인한 지표.
2. **User FGI를 통한 타깃·서비스 방향:** 두 고객 사례, 가설 변화, UI 방향과 FOMO의 실제 합의 범위.
3. **최종 구현물 확인:** A/B 및 손코딩 버전의 화면·경로·ERD·연결 상태·완료 및 미완료 범위.
4. **손코딩과 바이브 구현 비교:** 직접 작성한 도메인, 구현 방식의 차이, 동작·지표의 양상, 레퍼런스와의 차이.
5. **과정 리뷰:** 매일 발생한 오류·구현 한계·최소 수정·재실행 결과, UI 개선 이유와 다음 작업.

완성된 서비스의 우열만 제시하지 않고, 무엇을 구현·측정했고 어디까지 확인했는지 설명할 수 있는 기록을 남긴다.

## 10. 추가 합의 사항

- 설치형 PWA·별도 모바일 앱의 채택 여부와 실제 구현 범위
- 사이트별 DB 스키마·초기 데이터의 동일 범위와 데이터 격리 방법
- AI 에이전트 도구·모델·실행 횟수와 상세 지표 정의
- FOMO의 구체적인 기능·문구·적용 조건: 현재 답변에 확정 내용이 없어 미정
- 로그인·결제를 포함한 도메인별 세부 일정과 정확한 최종 마감

위 항목은 이번 명세에서 임의로 확정하지 않는다. 오늘의 네 가지 준비 작업과 내일부터의 손코딩·리뷰·측정 흐름은 확정 사항으로 진행하며, 세부 구현에 필요한 결정은 해당 작업 전에 보강한다.
