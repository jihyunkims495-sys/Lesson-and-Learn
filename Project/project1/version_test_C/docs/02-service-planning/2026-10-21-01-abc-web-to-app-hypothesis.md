# ONEPIECE A·B·C 분석과 웹 탐색 → 동일 서비스 앱 구매 가설

- 작성일: 2026-10-21, Asia/Seoul
- 상태: 2026-10-21의 동일 서비스 앱 구매 가설 설계본. 실험 결과 또는 앱 구현 완료 보고가 아니다. 같은 날 후속 설계에서 정한 PC→모바일 웹 검증 범위는 [B·C 모바일 웹 가설](./2026-10-21-02-bc-web-mobile-hypothesis-spec.md)을 따른다.
- 전환 목적지: 웹에서 탐색한 **동일 서비스의 앱 버전 장바구니**다. 다른 쇼핑 플랫폼으로 이동하는 가설이 아니다.
- 기존 맥락: [User FGI 정리](../01-customer-analysis/2026-10-20-01-user-fgi-spec.md), [스프린트 범위](../04-task-specs/2026-10-20-02-sprint-task-and-validation-spec.md).

## 1. 분석 대상과 목적

| 대상 | 역할 | 확인할 내용 |
| --- | --- | --- |
| A안 | SAN SAN GEAR 클론의 레퍼런스 해체 분석 | 탐색을 지원하는 정보·컴포넌트, 주요 경로, 반복·중단 구간과 설계 원칙 |
| B안 | ONEPIECE 바이브코딩 버전의 브랜드 경험 개선 | 어떤 회원 성향에서 탐색과 선택이 막히는지, 개선할 UI와 다음 구매 행동의 연결 |
| C안 | 팀 손코딩 dev 누적 버전 | 최소 구현이 B보다 탐색·구매 준비를 돕는지, 필요한 정보·기능을 덜어낸 부분은 없는지 |

주요 비교는 B/C다. A는 레퍼런스의 구조를 설명하는 별도 분석으로 유지한다. 기존 A/B 보고서 설정이 B/C 비교를 자동 포함하는 것은 아니다.

## 2. 보강한 핵심 가설

**브랜드를 인지한 20~30대 패션 중·고관여 회원은 웹에서 구매 판단에 필요한 상품·옵션·가격·핏 정보를 충분히 확인하고 상품을 장바구니에 보관한 뒤, 평소 사용에 익숙한 동일 서비스의 앱을 열어 장바구니에서 추가 상품 탐색 없이 주문·결제 절차를 시작하려 할 것이다. 웹의 탐색 지원과 선택 정보의 연속성이 좋을수록 이 과정의 재탐색·재선택·중단이 줄어들 것이다.**

이는 검증 대상이다. 20~30대 전체의 확정된 행동으로 일반화하지 않는다. 특정 서비스 앱을 평소 사용하는지와 설치·로그인 상태는 별도 조건이며, 브랜드 인지 또는 회원 가입만으로 앱 사용 습관이 있다고 간주하지 않는다.

‘충분한 탐색’은 오래 머무는 것과 같지 않다. 프로필별 구매 판단 조건을 확인했는지, 상품·옵션을 선택할 근거가 있었는지 기록한다. 탐색 시간을 무조건 줄이는 것을 성공으로 삼지 않는다.

‘바로 결제버튼’은 앱 장바구니에서 불필요한 상품 재탐색·옵션 재선택 없이 **주문 절차를 시작하는 행동**으로 정의한다. 필요한 인증·주문 확인·결제 승인 절차의 생략 또는 결제 완료를 뜻하지 않는다.

## 3. 서로 구분하여 검증할 네 가지 질문

| 질문 | 필요한 관찰 | 이 관찰만으로 말할 수 없는 것 |
| --- | --- | --- |
| H1. 웹이 구매 판단을 충분히 지원하는가? | 정보 탐색, 조건 충족 여부, 옵션 선택, 담기 성공·중단 사유 | 체류 시간이 길다는 이유만으로 혼란이라고 단정 |
| H2. 구매 채널로 앱을 선택하는가? | 웹 결제·동일 서비스 앱·보류 중 선택과 선택 근거 | 앱 이동을 지시한 과업으로 자발적 앱 선호 입증 |
| H3. 웹 선택이 앱까지 유지되는가? | 같은 인증 회원의 상품·옵션·수량 일치, 앱 장바구니 로드, 재고·가격 변경 시 안내 | GA4 식별만으로 장바구니 동기화가 구현됐다고 간주 |
| H4. 앱에서 빠르게 주문을 시작하는가? | 첫 유효 장바구니 표시부터 주문 클릭까지 시간·조작·재탐색·실패 | 주문 클릭을 결제 승인 또는 purchase로 간주 |

H2의 자유 선택 과업과 H3·H4의 앱 경로 동작 검증 과업은 별도로 실행·집계한다. ‘앱을 열고 결제하라’는 지시를 받고 수행한 비율을 앱 선호율로 보고하지 않는다.

## 4. 공통 가상 회원 180명 적용

- 같은 180개 프로필을 A·B·C에 재사용한다. B/C는 같은 프로필의 결과를 짝지어 비교한다.
- 프로필의 예산·과업·판단 성향·초기 구매 이력과 웹 시작 조건은 유지한다. 이전 안의 장바구니나 탐색 기록은 다음 안으로 넘기지 않는다.
- 회원 프로필의 데스크톱 조건은 웹 탐색 단계다. 앱 단계의 기기·앱 형태는 별도 실행 조건으로 기록하며, 기존 device 값을 임의 변경하지 않는다.
- 웹→앱 장바구니 유지 여부를 검사할 때는 웹 담기 이후 같은 안의 앱 확인이 끝날 때까지 해당 장바구니를 보존한다. 다른 안이나 다음 반복을 시작하기 전에만 초기화한다.
- 앱 친숙도·설치·인증 상태가 회원 프로필에 정의되어 있다고 가정하지 않는다. 추가 가정이 필요하면 프로필 속성과 분리된 실행 조건에 표시한다.
- 같은 프로필의 순차 비교는 안별 실행 맥락을 분리한다. 같은 사람이 반복하는 사용성 실험에서는 순서를 교차 배치하고 학습 효과를 기록한다.
- 가상 회원에게 앱 이동이나 구매 성공을 강제하지 않는다. 예산·정보·재고 조건에 따라 웹에서 보류할 수 있다.
- 본 가설 설계 시점의 180개 프로필은 계정 생성·행동 실행 완료와 구분한다. 실제 계정·인증·여정·GA 수신이 확인된 뒤 실행 상태를 갱신한다.

## 5. 지표와 분모

| 지표 | 정의 | 해석 |
| --- | --- | --- |
| 웹 구매 준비 도달률 | 해당 웹 과업 시작자 중 프로필의 구매 판단 조건을 확인하고 유효한 상품·옵션 담기를 완료한 비율 | 정보 탐색 기록과 담기 결과를 함께 확인 |
| 앱 선택률 | 자유 선택 과업에서 구매 준비 후 채널 선택이 관찰된 회원 중 동일 서비스 앱을 선택한 비율 | 웹 결제·보류·관찰 불가도 함께 제시. 앱 사용을 강제한 과업은 제외 |
| 웹→앱 연속 도달률 | 동일 서비스 앱을 선택한 회원 중 후속 관찰 창 안에 같은 회원의 앱 장바구니 진입이 확인된 비율 | 웹 종료만으로 성공·실패를 판정하지 않음 |
| 장바구니 연속성 성공률 | 웹 담기 후 앱 장바구니 확인이 가능한 회원 중 상품·옵션·수량이 유지된 비율 | 가격·재고 변경은 안내 여부와 함께 별도 기록 |
| 앱 장바구니 직행률 | 유효 장바구니가 표시된 앱 과업 중 추가 상품 탐색·옵션 재선택 없이 주문을 시작한 비율 | 동일한 완료 기준을 B/C에 적용 |
| 앱 주문 진입 시간·조작 수 | 첫 유효 앱 장바구니 표시부터 첫 주문 시작까지의 시간과 불필요한 조작 수 | 성공 건의 시간만으로 비교하지 않고 미완료·진행 불가 비율도 함께 보고 |
| 단계별 중단 | 조건 미충족, 정보 부족, 예산, 품절, 인증 실패, 기능 미구현, 앱 미제공, 관찰 불가로 분류 | 기능 미구현을 구매 의사 부족으로 처리하지 않음 |

‘직행’에 필요한 관찰 시간 창, 재시도 처리와 최소 개선 기준은 파일럿 뒤 본실험 전에 고정한다. 본실험 전에는 임의의 성공률·시간 목표나 결과를 만들지 않는다. 실제 앱 접근이 불가능한 과업은 적용 불가로 표시하고 분모와 사유를 함께 공개한다.

## 6. 웹 종료와 이탈 판정

웹의 마지막 행동이 담기이고 이후 앱에서 같은 회원·선택의 장바구니가 확인됐다면, 이를 웹에서 구매하지 않았다는 이유로 전체 구매 여정 이탈로 계산하지 않는다. 웹 종료와 채널 전환 완료를 따로 기록한다.

후속 앱 행동을 관찰할 수 없으면 ‘웹 마지막 행동 확인 / 앱 연결 관찰 불가’로 남긴다. 앱 이동 버튼 클릭만으로 앱 실행·장바구니 복원·구매를 성공 처리하지 않는다.

마지막 클릭 컴포넌트가 곧 이탈 원인은 아니다. 노출·조작·성공/실패·반복 경로와 프로필의 미충족 조건을 함께 남기며, 원인 후보와 확인된 직접 오류를 구분한다.

## 7. 계측·상태 연결 제안

- 공통 실행 기록: 실험 버전, 가상 회원 설계 키, 실행 ID, 웹/앱 단계, 상품·옵션·수량, 단계 시각, 동작 결과, 중단 사유. 가상 설계 키는 인증된 회원 ID나 GA4 사용자 수와 동일하지 않다.
- 웹: page_view, view_item_list, select_item, view_item, select_variant, add_to_cart, view_cart. 컴포넌트 분석에는 실제 노출·조작 결과를 구분하는 계측이 추가로 필요하다.
- 앱: 실제 앱 진입 근거, view_cart, checkout_click, begin_checkout. purchase는 실제 승인·주문 결과가 확인되는 지점에서만 전송한다.
- 안별 구분과 플랫폼 구분은 별개다. B/C 안별 값과 웹/앱 구분을 함께 기록한다. 현재 A/B 배포 주소 기반 비교만으로 웹→앱 여정을 연결할 수 없다.
- 실제 앱을 연결한다면 같은 GA4 속성에서 웹 및 실제 앱 플랫폼에 맞는 데이터 스트림·SDK를 구성하고, 로그인한 같은 회원에 대해 비식별 User-ID를 일관되게 설정한다. 이메일·전화번호를 User-ID로 사용하지 않고, user_id를 맞춤 측정기준으로 등록하지 않는다.
- User-ID는 분석상 식별 연결이며 장바구니를 동기화하는 기능이 아니다. 장바구니는 인증된 회원 기준의 서버 저장·조회와 권한 검증이 별도로 필요하다.
- 신규 네이티브 앱·PWA·딥링크·공용 DB는 이 가설만으로 구현 범위에 포함되지 않는다. 실제 채택 방식과 범위는 별도 설계가 필요하다.

## 8. 현재 구현으로 가능한 결론과 남은 검증

| 현재 가능한 확인 | 추가 환경이 필요한 확인 |
| --- | --- |
| 웹 정보 탐색, 선택, 담기, 장바구니 상태, 웹 주문 버튼까지의 UI·이벤트 | 실제 앱 선택·실행·인증·장바구니 연속성·앱 주문 진입 |
| 같은 웹 화면의 모바일 표시와 터치 동작 | 평소 사용하는 설치 앱으로의 전환과 앱 사용 선호 |
| 가상 회원 조건에 따른 경로·정보 부족·오류 시뮬레이션 | 실제 20~30대 고객의 자발적 선호·익숙함·FOMO와 실제 전환 효과 |

모바일 웹 또는 앱 형태 프로토타입을 사용하는 경우 그 환경에서의 사용성 검증으로 표시한다. 실제 앱 전환 검증으로 바꾸어 보고하지 않는다. 웹 탐색의 질과 구매 결정 이후의 조작 부담을 분리해 분석한다.

우선 파일럿 6명으로 웹 탐색 기록과 현재 장바구니·이벤트의 누락을 확인한다. 앱이 준비되지 않았으면 앱 단계는 미검증으로 남기고, 금요일 결론에서 확인된 웹 구간과 후속 앱 가설을 구분한다.
