# ONEPIECE 구매 여정 UI·추천·혜택 개선 명세

- 작성일: 2026-10-20
- 버전: v1.0 — 사용자 인터뷰 반영
- 대상 프로젝트: ONEPIECE
- 대상 화면: 메인 `/`, 상품 목록 `/products`, 상품 상세 `/products/{id}`, 장바구니 `/cart`, 주문·결제 `/checkout`
- 문서 상태: 구현 전 제안 명세 — 개선 요청 범위 정리, 데이터·추천·테스트 정책의 세부 구현은 팀 합의 후 결정
- 요청 기능: 장바구니 바로가기 / 판매량·추천·신상품 정렬 / 비슷한 상품 및 회원 개인화 추천 / 쿠폰·등급·리워드 혜택 / 구매 흐름 편의성 유지

## 1. 목표와 범위

브랜드를 인지한 20~30대 패션 중·고관여자가 필요한 상품을 충분히 탐색하고, 선택한 상품을 장바구니에서 검토한 뒤 구매로 이어갈 수 있도록 한다. 메인에서는 장바구니 접근을, 목록에서는 상품 비교 순서를, 상세에서는 후보 선택을, 장바구니에서는 적용 가능한 혜택과 금액 이해를 지원한다.

| 기능 | 해결하려는 문제 | 개선 목표 |
| --- | --- | --- |
| 전역 장바구니 오버레이 | 담아 둔 상품으로 돌아가는 경로를 찾기 어렵다. | 자사몰의 어느 페이지에서나 오른쪽 오버레이로 내용을 확인한다. |
| 상품 정렬 | 판매량·추천·신상품 기준으로 후보를 비교하기 어렵다. | 카테고리 탐색을 유지하며 원하는 순서로 상품을 비교한다. |
| 상세 비슷한 상품 추천 | 현재 상품과 유사한 대안을 찾기 위해 목록을 다시 탐색한다. | 상세에서 관련 후보를 확인한다. |
| 회원 개인화 추천 | 신체·구매 정보에 맞는 후보를 판단하기 어렵다. | 사용 가능한 회원 정보에 근거한 추천을 제공한다. |
| 장바구니 테스트 혜택 | 사용할 수 있는 혜택과 최종 금액을 이해하기 어렵다. | 테스트 회원으로 쿠폰·등급·리워드 적용과 금액 변화를 시연한다. |
| 결제 연결 | 로그인·금액 재확인 과정에서 선택 내용이 유실될 수 있다. | 장바구니 선택과 혜택 상태를 이어받는 구매 흐름을 확인한다. |

이 문서는 새로 요청된 개선 기능을 정리한 제안이다. 기존 스프린트 전체에 대한 팀 승인이나 구현 완료를 뜻하지 않는다. 기능별 실제 적용 버전·일정은 팀 합의로 정한다.

## 2. 공통 표시·상태 규칙

1. 기존 상품·카테고리·3·4·6 그리드 탐색을 기반으로 한다. 요청하지 않은 상품 구성 변경은 포함하지 않는다.
2. 판매량순·추천순·신상품순은 상품의 표시 순서를 바꾸는 **정렬**이다. 가격·사이즈 조건으로 상품을 제외하는 추가 필터는 별도 요청 전까지 이 문서의 기능으로 추가하지 않는다.
3. 로딩·빈 결과·정보 부족·오류 상태를 정상 결과와 구분한다.
4. 로그인 전에도 상품 탐색과 장바구니 검토가 가능하도록 기존 정책을 따른다. 회원 개인화와 회원 혜택은 로그인 상태를 기준으로 처리한다.
5. 로그인 시 현재 상품·옵션·장바구니 선택을 보존하고 원래 구매 경로로 복귀한다.
6. 추천·혜택의 설명에는 실제 사용한 기준과 적용 가능한 조건만 표시한다. 미확정 수치나 데이터가 없는 판매량을 실제 결과로 표현하지 않는다.
7. 키보드·터치로 동일한 핵심 기능을 사용할 수 있게 한다. 상태 변경 안내와 포커스 복귀를 제공한다.

## 3. 레퍼런스와 확정한 요청 범위

- 제공된 무신사 상세에서는 상품 이미지의 ‘AI 추천 · 비슷한 상품’ 버튼과, 클릭 후 현재 상품을 기준으로 한 추천 목록 이동을 확인했다.
- 외부 서비스의 추천 알고리즘이나 회원 신체·구매 데이터 사용 방식은 확인한 UI만으로 단정하지 않는다.
- 장바구니: 자사몰의 어느 페이지에서나 오른쪽 오버레이로 확인한다.
- 상세 추천: 현재 상품과 비슷한 상품 추천, 로그인 회원의 신체·구매 정보 기반 맞춤 상품 추천을 모두 포함한다. 참조 서비스의 내부 알고리즘을 동일하게 복제한다고 가정하지 않는다.
- 혜택: 테스트 회원·테스트 혜택으로 적용 흐름을 시연한다. 실제 회원에게 쿠폰·등급·리워드를 운영하는 범위는 포함하지 않는다.
- AI 모델·데이터 처리 방식과 테스트 할인율·등급·적립 기준은 구현 전에 팀이 결정한다. 숫자와 서비스 정책을 이 문서에서 임의 확정하지 않는다.

## 4. F-01 전역 장바구니 오른쪽 오버레이

### 4.1 표시·진입 규칙

1. 메인·상품 목록·상품 상세·장바구니·로그인·주문 등 자사몰 내부의 모든 페이지에서 장바구니 진입점을 사용할 수 있게 한다. 결제사 등 외부 화면은 대상이 아니다.
2. 장바구니를 누르면 현재 페이지 위에 오른쪽에서 오버레이가 열린다. 자동으로 전체 장바구니 페이지로 이동하거나 메인으로 돌아가지 않는다.
3. 기존 코드의 헤더 `CART` 버튼과 `CartDrawer` 연결을 우선 활용한다. 현재 코드에 있는 진입 동작에 더해 페이지별 노출·공유 상태·복귀를 확인한다. 동일한 장바구니 상태를 중복 생성하지 않는다.
4. 수량 표시는 상품 종류 수와 전체 수량을 혼동하지 않도록 기존 기준을 일관되게 사용한다.
5. 오버레이를 열거나 닫아도 현재 URL·카테고리·정렬·스크롤·상품 선택·진행 중 입력을 유지한다.

### 4.2 내용·예외 규칙

- 상품 이미지·이름·옵션·수량·금액을 확인하고, 수량 변경·삭제와 전체 장바구니 이동을 기존 공통 동작으로 처리한다.
- 비어 있으면 빈 상태와 탐색 복귀 경로를 표시한다.
- 우측 패널과 배경 오버레이를 구분한다. 닫기 버튼·배경 선택·Escape로 닫고, 오버레이가 열려 있는 동안 배경 스크롤과 포커스 이탈을 제어한다.
- PC에서는 기존 우측 패널 구조를 활용한다. 모바일에서도 화면 폭 안에서 사용하며 내용은 패널 내부에서 스크롤한다.
- 닫으면 열기 버튼으로 포커스를 돌려준다. 오버레이에서 전체 장바구니로 이동한 경우 새 페이지의 정상 탐색 흐름을 따른다.
- 혜택 선택 UI는 전체 장바구니를 기준으로 한다. 오버레이에 별도의 쿠폰·리워드 계산기를 중복 추가하지 않는다.
- 담긴 상품의 재고·현재 금액은 주문 전 다시 확인한다. 표시한 스냅샷만으로 구매 가능 여부를 확정하지 않는다.

### 4.3 완료 기준

- [ ] 메인·목록·상세·로그인·주문을 포함한 자사몰 내부 각 페이지에서 우측 장바구니를 열 수 있다.
- [ ] 상세·헤더·장바구니가 같은 상품·옵션·수량을 표시한다.
- [ ] 빈 장바구니, 긴 상품명, 여러 상품에서 화면이 깨지지 않는다.
- [ ] 닫기·배경 선택·Escape·내부 스크롤과 포커스 복귀를 확인한다.
- [ ] 오버레이 열기·닫기가 원래 페이지의 URL·탐색·입력 상태를 초기화하지 않는다.
- [ ] PC·모바일·키보드에서 진입과 복귀를 확인한다.

## 5. F-02 상품 판매량·추천·신상품 정렬

### 5.1 컨트롤과 옵션

상품목록 상단의 정렬 컨트롤에서 선택 즉시 목록을 갱신한다. 아래 URL 값은 제안이며 기존 정렬 계약과 함께 확정한다.

| 표시명 | URL 값 제안 | 필요한 기준 |
| --- | --- | --- |
| 판매량순 | `sales` | 상품별 유효 판매 수량, 집계 기간·취소 반영 기준 |
| 추천순 | `recommended` | 공통 추천 또는 회원 개인화 중 선택한 순위 기준 |
| 신상품순 | `newest` | 상품의 실제 출시·게시 시각 중 합의한 기준 |

첫 진입의 기본 정렬과 팀원 명세의 가격순 옵션을 함께 유지할지는 팀 합의 사항이다. 이 문서만으로 기존 가격순 요구를 삭제하지 않는다.

### 5.2 동작·URL 규칙

1. 현재 카테고리에 해당하는 상품을 구한 뒤 선택한 정렬을 적용한다.
2. 카테고리 변경 시 정렬과 그리드 선택을 유지한다.
3. 정렬은 URL과 선택 UI가 일치하도록 한다. 직접 진입·새로고침·뒤로가기에서 복원한다.
4. 다른 쿼리 파라미터를 보존한다. 원본 배열과 원본 상품 데이터는 변경하지 않는다.
5. 동점 상품의 순서는 일관된 보조 기준으로 결정한다. 해당 기준은 데이터 계약에 함께 기록한다.
6. 빈 목록에서도 컨트롤을 유지한다. 변경 후 포커스를 유지하고 목록 변경을 안내한다.

### 5.3 데이터·예외 규칙

- 판매량 집계안: 결제 승인된 주문의 상품별 유효 수량을 기반으로 한다. 집계 기간과 취소 수량 차감 방식은 확정 후 구현한다.
- 주문 건수와 판매 수량을 혼용하지 않는다. 화면에서 정한 기준과 서버 계산을 일치시킨다.
- 추천순은 상세의 ‘비슷한 상품’과 자동으로 같은 기준이라고 가정하지 않는다. 추천 점수가 없을 때의 공통 순서를 정한다.
- 신상품순은 DB 수정 시각만으로 계산하지 않는다. 출시·게시 기준일과 누락 시 처리 방식을 정한다.
- 집계·추천 요청 실패 시 임의 순위를 성공한 결과로 표시하지 않는다. 오류와 재시도 또는 기본순 복귀를 안내한다.

### 5.4 완료 기준

- [ ] 판매량·추천·신상품순 선택 UI와 실제 목록 순서가 일치한다.
- [ ] 카테고리·그리드 변경과 URL 복원에서 정렬을 유지한다.
- [ ] 동점·누락 데이터·0개·1개 상품을 정의한 규칙대로 처리한다.
- [ ] 테스트용 판매·추천 데이터와 실제 데이터를 구분한다.
- [ ] 원본 데이터가 정렬 과정에서 변하지 않는다.

## 6. F-03 상세의 비슷한 상품 추천

### 6.1 표시·동작 규칙

1. 상품 이미지 근처에 현재 상품의 ‘비슷한 상품’ 추천 진입점을 제공한다. 상세 내 결과 영역과 별도 페이지·패널 중 화면 구성은 디자인 합의로 정한다.
2. 추천 카드는 기존 상품 카드의 이미지·상품명·판매가·상세 이동을 재사용한다.
3. 추천 후보는 ONEPIECE의 실제 상품 카탈로그에 존재하는 ID로 제한한다.
4. 현재 상품 자신과 중복 후보를 제외한다. 품절·판매 불가 상품의 표시·제외 기준을 정한다.
5. 추천 상품으로 이동했다가 돌아왔을 때 원래 상품의 선택 옵션과 탐색 위치가 유실되지 않는지 확인한다.

### 6.2 추천 방식·예외 규칙

- AI 기반 유사 상품 추천 기능을 구현 목표로 한다. 모델·서비스·유사도 입력·후보 순위 기준은 팀 구현 결정 사항이다. 개발 중 고정 결과나 규칙 기반 대체를 쓰는 경우 실제 AI 결과와 구분하며 완료로 혼동하지 않는다.
- 데이터가 부족하거나 후보가 없으면 빈 결과를 안내하며 본래 상품 구매 흐름을 유지한다.
- 로딩·실패·재시도를 구분한다. 추천 요청 실패로 상세·옵션 선택·장바구니 담기가 막히지 않게 한다.
- 외부 서비스 연동을 선택하는 경우 요청 데이터와 반환 상품 검증을 정의한다. 클라이언트에 비밀키를 넣지 않는다.

### 6.3 완료 기준

- [ ] 현재 상품을 기준으로 실제 존재하는 다른 후보를 보여준다.
- [ ] 카드의 금액·재고·상세 링크가 실제 상품과 일치한다.
- [ ] 중복·후보 없음·요청 실패를 처리한다.
- [ ] 추천 확인 전후에도 현재 상품의 옵션 선택과 구매 경로를 유지한다.

## 7. F-04 회원 신체·구매 정보 기반 추천

### 7.1 입력과 결과

- 로그인 회원의 신체·구매 정보를 활용한다는 요청을 반영한다.
- 로그인 회원에게 신체 정보와 구매 이력을 바탕으로 한 맞춤 상품을 제시한다. 일반 ‘비슷한 상품’과 개인화 결과를 구분해 표시한다.
- 신체 정보는 상품·옵션 적합성을 비교하는 근거로 사용한다. 현재 상품의 특정 사이즈를 단정하는 별도 사이즈 예측 기능은 추가 합의 없이 요구 범위로 확대하지 않는다.
- 필요한 신체 항목과 단위를 명시한다. 정보 입력 위치와 수정 경로도 함께 정의한다.
- 실제 존재하는 구매 이력과 취소 상태를 기준으로 한다. 구매하지 않은 상품이나 성공하지 않은 주문을 완료 구매로 설명하지 않는다.
- 개인화 입력과 상품 속성을 어떤 방식으로 추천에 반영할지 구현 계약에 명시한다. 추천 이유는 실제 사용한 입력·이력으로 설명 가능한 내용만 제공한다.

### 7.2 상태 규칙

| 상태 | 처리 방향 |
| --- | --- |
| 비로그인 | 공통 추천을 제공하고 개인화에는 로그인 필요 안내. 상품 탐색을 막지 않는다. |
| 로그인, 신체 정보 부족 | 부족한 항목만 선택적으로 보완하도록 안내. 추천을 위해 불필요한 회원 정보를 강제 수집하지 않는다. |
| 로그인, 구매 이력 없음 | 신규 회원용 대체 기준을 안내한다. 존재하지 않는 구매 이력을 이유로 제시하지 않는다. |
| 유효 정보 있음 | 해당 정보를 실제 사용한 추천과 설명을 제공한다. |
| 추천 실패 | 오류·재시도·공통 추천 전환을 구분한다. |

### 7.3 정확성·완료 기준

- [ ] 다른 회원의 데이터가 추천 입력이나 화면에 섞이지 않는다.
- [ ] 입력·이력이 없는 회원에게 근거 없는 개인화 설명을 만들지 않는다.
- [ ] 사이즈 추천을 포함한다면 실제 상품 사이즈표와 추천 결과를 대조한다.
- [ ] 사용자가 추천과 다른 상품·사이즈를 선택할 수 있다.
- [ ] 추천으로 구매가 빨라졌거나 적합성이 개선됐다는 결과는 실제 검증 후 기록한다.

## 8. F-05 장바구니 테스트 쿠폰·등급·리워드 혜택

### 8.1 표시 구성

장바구니의 주문 요약 영역에서 테스트 쿠폰, 회원 등급 혜택, 리워드를 구분한다. 테스트 회원·테스트 정책으로 적용→금액 확인→주문 화면 전달 흐름을 시연한다. 상세한 할인율·등급명·적립률은 확정 전까지 임의로 넣지 않는다.

| 구분 | 표시할 정보 | 정책 결정 항목 |
| --- | --- | --- |
| 쿠폰 | 보유·사용 가능 여부, 적용 조건, 선택·해제 상태 | 정액·정률, 한도, 최소 주문액, 유효기간, 대상 상품, 중복 규칙 |
| 회원 등급 | 현재 등급, 해당 주문에 적용 가능한 혜택 | 등급 기준·산정 기간, 등급별 혜택, 쿠폰과의 중복 |
| 리워드 | 사용 가능 잔액·사용액·예상 적립을 구분 | 사용 단위·한도, 적립 시점, 사용·적립 중복, 취소 복원 |

### 8.2 동작·금액 규칙

1. 테스트 환경에서 혜택 적용 흐름을 시연한다. 운영 쿠폰 발급·실제 회원 등급 변경·실제 리워드 지급이나 차감으로 연결하지 않는다.
2. 쿠폰 선택·해제, 수량 변경·삭제 시 적용 가능 여부와 주문 요약을 다시 계산한다.
3. 적용 불가 사유를 표시한다. 만료되거나 조건이 충족되지 않은 혜택을 적용된 것으로 보여주지 않는다.
4. 할인과 리워드의 적용 순서·계산 기준·반올림 규칙을 정한다. 결제 금액이 음수가 되지 않게 한다.
5. 할인·리워드 사용과 향후 예상 적립을 같은 차감 항목으로 합치지 않는다.
6. 테스트 회원 ID·쿠폰·등급·리워드와 정책은 테스트 설정에서 관리한다. 테스트 주문 금액은 같은 정책으로 재계산하고, 서버가 있는 시연에서는 서버 결과를 기준으로 검증한다. 계산 값이 없는 정적인 UI를 혜택 적용 완료로 표현하지 않는다.
7. 회원 등급을 기존 구매 횟수 구분과 동일하다고 가정하지 않는다. 등급 정책을 별도로 정한다.
8. 시연 화면은 테스트 혜택임을 식별할 수 있게 한다. 주문 화면에서도 같은 테스트 금액과 적용 내역을 전달한다.
9. 테스트 결제 연동 여부와 무관하게 운영 결제·운영 적립에 영향을 주지 않도록 테스트 데이터와 대상을 분리한다.

### 8.3 예외·완료 기준

- [ ] 비회원·보유 쿠폰 없음·리워드 없음 상태를 표시한다.
- [ ] 쿠폰 만료·중복 불가·최소금액 미달을 처리한다.
- [ ] 수량 변경·상품 삭제·로그인 전환 후 적용 가능 여부를 다시 확인한다.
- [ ] 할인 전 금액·할인·사용 리워드·최종 금액을 구분한다.
- [ ] 테스트 혜택 선택·해제로 계산 결과가 바뀌고 테스트 주문 화면에 같은 금액·적용 내역이 전달된다.
- [ ] 테스트 결제를 연결한 경우 요청 금액과 테스트 주문 확정 금액이 일치한다.
- [ ] 테스트 실행이 운영 쿠폰·등급·리워드·결제 상태를 변경하지 않는다.
- [ ] 실패·취소 시 쿠폰·리워드 처리 기준이 정의되어 있다. 구체적인 복원 정책은 확정 후 구현한다.

## 9. F-06 결제 편의성 유지

결제에 독립적인 신규 기능을 추가하지 않는다. FGI에서 확인한 ‘충분히 탐색하고 구매 결정 후 편리하게 checkout으로 이동하는 경험’을 기준으로 기존 경로의 연결을 검증한다.

### 9.1 연결 규칙

1. 장바구니의 상품·옵션·수량을 주문 화면에 정확히 전달한다.
2. 구매 시 로그인 정책을 유지하고 로그인 후 원래 구매 경로로 복귀한다.
3. 혜택 시연에서는 테스트 주문 화면에도 같은 테스트 정책의 금액·적용 내역을 반영한다. 테스트 결제를 연결했다면 요청 금액까지 일치시킨다.
4. 뒤로가기·재시도·결제 실패 시 선택 내용과 오류 복구 경로를 제공한다.
5. 버튼 클릭, 주문 생성, 결제 승인 완료를 구분한다. 중복 실행으로 중복 주문·중복 혜택 사용이 발생하지 않는지 확인한다.

### 9.2 완료 기준

- [ ] 상세→장바구니→로그인→주문·결제에서 선택 내용이 일치한다.
- [ ] 추천·혜택 기능이 기본 구매 경로를 막지 않는다.
- [ ] 금액 변경이 발생하면 사용자가 원인을 확인할 수 있다.
- [ ] 정상·취소·실패·재시도 흐름과 실제 주문·결제 상태를 확인한다.

## 10. 구현 위치와 작업 단위

아래 기존 파일은 기능별 검토 대상 후보다. 데이터·API·새 모듈의 정확한 위치는 구현 전에 코드 계약을 확인해 정한다. 이 문서는 코드 변경을 수행하지 않는다.

| 작업 | 주요 파일 후보 | 구현 방향 |
| --- | --- | --- |
| 전역 우측 장바구니 | `src/shared/components/Header.tsx`, `src/domains/cart/components/CartDrawer.tsx`, 페이지별 공통 레이아웃 | 기존 우측 패널·공유 상태를 활용하고 자사몰 전역의 노출·복귀를 확인한다. |
| 목록 정렬 | `src/domains/products/components/ProductList.tsx`, 별도 정렬 유틸·데이터 조회 계층 | URL 상태와 실제 정렬 기준을 연결한다. |
| 상세 추천 | `src/domains/products/components/ProductDetail.tsx`, 추천 전용 컴포넌트·서버 계층 | 추천 요청·후보 검증·카드 표시를 분리한다. |
| 테스트 혜택·금액 요약 | `src/domains/cart/components/CartSummary.tsx`, `src/app/(shop)/cart/page.tsx`, 테스트 정책 모듈 | 테스트 회원·정책과 계산·표시를 분리한다. |
| 테스트 주문·결제 일치 | `src/app/(shop)/checkout/page.tsx`, 주문·결제 서버 계층 | 같은 테스트 정책과 적용 내역을 전달·검증한다. |

신규 데이터 요구는 판매 집계·추천·회원 정보·혜택 정책으로 나누어 검토한다. 현재 ERD에 해당 데이터나 기능이 이미 있다고 가정하지 않는다. 공용 파일·상품 타입·ERD 변경은 기존 팀 공유·리뷰 규칙을 따른다.
