## 1. 문제와 개발 방향

현재 Cart는 고정 상품 2종으로 동작을 확인할 수 있지만, 수량이 다른 여러 상품, 이미지·옵션 누락, 긴 상품명과 빈 목록을 반복 검증할 데이터 구성이 없다. 이미지가 없으면 이미지 영역 자체가 없어지고, 상품별 단가와 수량을 확인하더라도 행별 상품금액을 바로 비교하기 어렵다.

오늘은 기존 Cart 화면을 중심으로 작은 Mock 시나리오를 추가하고, 화면과 상태가 같은 데이터를 반영하는지 확인한다. 사용자 관점의 목표는 선택한 상품·옵션·수량·금액을 짧게 검토하고 수량 변경이나 삭제 결과를 바로 확인하는 것이다. 실제 전환율·이탈률 개선은 이번 Mock 실습으로 검증하지 않는다.

전체 프로젝트 우선순위는 P0 홈·상품 목록·동적 상세, P1 Cart, P2 로그인·비회원 주문·결제를 유지한다. 이 문서의 '필수'는 오늘 Cart 작업 안에서의 순서이며 프로젝트 우선순위를 바꾸지 않는다.

### 팀 합의: 서비스 화면의 영문 대문자 표기

- 2026-10-16 사용자가 전달한 팀 합의에 따라, 서비스 화면에 노출되는 영문 상품명과 아이콘 이름, 메뉴·버튼 등 영문 UI 이름은 대문자로 통일한다.
- 상품명 예: `ONEPIECE SHELL JACKET`, `ONEPIECE T-SHIRT`, `ONEPIECE HOODIE`, `ONEPIECE CROSSBODY BAG`.
- 아이콘·메뉴·버튼 이름 예: `CART`, `SEARCH`, `LOGIN`, `CHECKOUT`, `ORDER SUMMARY`. 이미 합의된 영문 문구의 대소문자를 맞추며, 새 메뉴나 기능을 추가하는 의미는 아니다.
- 검증용 Mock의 영문 상품명도 같은 규칙으로 작성한다. 긴 상품명 시나리오에도 대문자를 적용한다. 기존 상품 데이터의 원본은 보존하며, 화면 표시가 규칙을 따르도록 적용 위치를 정한다.
- 한글 안내 문구는 현재 표현을 유지한다. 전체 문구를 영문으로 번역하는 작업은 이번 합의에 포함하지 않는다.
- 코드의 컴포넌트는 PascalCase, 함수·변수는 camelCase 등 기존 팀 코드 컨벤션을 따른다. 이미지 파일명·URL·객체 필드명은 기존 계약을 유지한다.
- 오늘은 Cart에 적용하고, Header 등 다른 담당 영역은 팀에 같은 기준을 공유한다. 공용 파일 수정은 기존 사전 공유 규칙을 따른다.

### B. Cart 페이지의 정보·예외 화면 보완

1. **이미지 없는 상품의 대체 영역**
   - `imageUrlAtAdded === null`이면 다른 행의 이미지와 비슷한 폭을 갖는 대체 영역과 '이미지 준비 중' 안내를 표시한다.
   - 빈 `src`를 Image에 넘기지 않는다. 상품명과 수량 조작은 계속 사용할 수 있어야 한다.
   - URL은 있지만 파일이 없는 네트워크 오류 이미지는 별도 문제다. 이번 필수 테스트는 `null`이며 네트워크 오류 처리까지 완료했다고 적지 않는다.
2. **단가와 행별 상품금액 구분**
   - 기존 가격은 '단가'로 구분하고, 해당 상품의 `unitPriceAtAdded × quantity`를 '상품금액'으로 표시한다.
   - 행 금액·요약 합계·Header 수량은 현재 `cartItems`에서 계산한다. 별도 합계 State나 동기화용 Effect를 만들지 않는다.
   - 주문 요약의 값은 상품금액 합계다. 배송·할인·세금이 반영된 최종 결제금액으로 표현하지 않는다.
3. **긴 이름·옵션 없음·조작 버튼 검토**
   - 긴 상품명은 줄바꿈하고 가격·수량·삭제 버튼을 가리지 않도록 한다.
   - `null` 옵션은 문자열 `null`이나 비어 있는 줄로 출력하지 않는다.
   - 증가·감소 버튼의 접근 가능한 이름에 상품명을 포함해 어떤 상품의 수량을 바꾸는지 구분한다.
   - 기존 `min-w-0`, 버튼 줄바꿈, 최소 수량 제한과 빈 상태 처리 의도를 유지한다.
4. **팀 합의에 따른 대문자 표기**
   - Cart의 영문 상품명과 영문 아이콘·메뉴·버튼 이름에 대문자 규칙을 적용한다.
   - `CART`, `ORDER SUMMARY`, `TOTAL`, `CHECKOUT` 등 현재 표시와 신규 Mock 상품명을 함께 확인한다.
   - 대문자 적용 뒤 긴 상품명의 줄바꿈과 좁은 화면 배치를 다시 확인한다.

수정 순서: 이미지 대체 영역 하나 → 브라우저 확인 → 행별 금액 하나 → 브라우저 확인 → 긴 이름·버튼 확인. 한 번에 전체 컴포넌트를 교체하지 않는다.

완료 기준: 375px·768px·1280px에서 Cart 본문이 가로로 넘치지 않고, 정보와 조작이 겹치지 않는다. 사용자가 정한 데스크톱의 넓은 간격을 임의로 다시 설계하지 않는다. 공통 Header의 모바일 문제는 Cart 본문 문제와 분리해서 담당자에게 전달한다.


- `npm run test`는 현재 등록된 자동 테스트의 회귀 확인이다. 현재 가격 표시 테스트만 통과해도 Cart 테스트 통과라고 쓰지 않는다.
- `npm run build`는 `prebuild`로 기존 테스트를 다시 실행한 뒤 빌드한다. 테스트 성공·컴파일 성공·TypeScript 검사·전체 빌드 결과를 각각 구분한다.
- 기존 로그인·Checkout 빈 라우트 4개는 빌드 차단 가능성이 있다. 실제 실행 오류를 확인하고 Cart 변경으로 생긴 문제인지 기존 공용 문제인지 구분한다. 담당 범위 밖 라우트를 임의로 채우지 않는다.
- 자동화가 필요한 계산·상태 로직을 실제로 분리하는 단계가 생기면 Node의 기존 테스트 구성을 재사용한다. 테스트 파일 안에서 `map`/`filter`를 새로 작성해 통과시키고 실제 Cart 핸들러를 검사했다고 주장하지 않는다.
- 추가 테스트 프레임워크 설치는 오늘 필수 범위가 아니다.

완료 기준: T01~T14의 실제 결과와 실패·보류 이유가 기록되고, 검사 명령의 종료 결과와 남은 오류가 구분돼 있어야 한다. 실패가 있으면 전체 완료로 표시하지 않는다.

모든 아래 상대 경로는 팀 저장소를 기준으로 한다.

| 파일 | 오늘 역할 | 변경 구분 |

| `src/domains/cart/mocks/cart.mock.ts` | 기존 2종 보존, 이미지·옵션 계약 확인 | 필요 시 최소 변경 |
| `src/domains/cart/components/CartItemList.tsx` | 대체 이미지·행 금액·긴 이름·버튼 이름 | 주요 수정 후보 |

공용 store는 Cart와 Header 모두에 영향을 주므로 팀에 변경 목적을 알린다. 추가로 전역 CSS, 공통 레이아웃, `src/shared/mocks/mockData.ts`, 상품 타입, 패키지·lockfile·TypeScript·Next 설정은 사전 공유 대상이다. 오늘 기본안은 새 패키지 없이 기존 Cart 도메인과 기존 store만 사용한다.

`useCounterStore` 이름을 바꾸는 작업, 파일 구조 전면 개편, 공용 상품 데이터 재작성은 이번 필수 작업과 묶지 않는다.

## 6. 선택 단계: 필수 검증 뒤에 하나만 선택

### 선택 A. Zustand 도메인 액션 연습

기존 범용 `setCartItems`와 페이지 핸들러의 역할을 읽은 뒤, 필요하면 수량 변경·삭제를 이름이 있는 store 액션으로 옮긴다. 같은 동작을 두 군데에 중복 구현하지 않는다. 실제 액션을 호출해 최소 수량·대상 행만 변경·존재하지 않는 ID·원본 Mock 보존을 자동 검증할 수 있을 때 진행한다. 리팩터링만을 위한 대규모 이동은 하지 않는다.

### 선택 B. Persist로 새로고침 유지

새로고침 후 상태 유지가 필요한 경우, 필수 완료 후 팀과 적용 범위를 공유하고 별도 작은 작업으로 진행한다.

- 기존 store에 저장·복원을 적용하고 Cart와 Header 모두의 서버·클라이언트 초기 표시를 확인한다.
- 새로고침·새 탭에서도 변경된 수량·빈 목록이 복원되는지 확인한다.
- 저장 데이터가 있으면 새 Mock을 선택해도 이전 데이터가 복원될 수 있다. 테스트용 키와 해당 키의 초기화 절차를 정한다. 전체 localStorage를 지우지 않는다.
- 저장 데이터의 형식·버전·잘못된 데이터 처리와 Hydration 불일치 대응을 정한다.
- 이 단계를 구현하면 T13의 기대값을 '변경 상태 복원'으로 명시적으로 수정하고 재검증한다.

선택 A/B를 둘 다 오늘의 완료 조건으로 추가하지 않는다. 선택하지 않은 항목은 다음 작업으로 남긴다.

## 7. 오늘 범위 밖과 협업 의존성

- 상품 상세 실제 담기: 다음 연동 후보. `Product`와 Variant·옵션·Cart Snapshot의 전달 계약을 상세 담당자와 먼저 정한다. 옵션 없는 Product 필드를 임의로 Variant ID로 바꾸지 않는다.
- 재고 상한·품절: 현재 타입과 정책이 없으므로 오늘 수량은 최소 1만 검증한다. 임의의 최대 수량을 만들지 않는다.
- CHECKOUT 이동·로그인·비회원 주문·PG 결제: 기존 UI-only 합의를 유지한다.
- 배송비·할인·세금 계산: 실제 정책 확정 뒤 별도 처리한다. 상품 상세 Mock의 배송 문구를 확정 정책으로 자동 적용하지 않는다.
- 전체 삭제 버튼·선택 구매·Drawer·쿠폰·포인트·찜·추천·서버 DB·전환율 이벤트: 오늘 기본 범위에 추가하지 않는다.

## 8. Git 작업 순서와 완료 단계

1. 구현 시작 직전에 `git status --short --branch`와 최신 dev 상태를 다시 확인한다. 오래된 개인 브랜치의 변경을 확인 없이 적용하지 않는다.
2. 기존 변경을 보존하며 dev를 최신으로 갱신한 뒤 Cart Mock 검증 목적의 개인 작업 브랜치를 만든다.
3. Mock 시나리오 하나, 화면 보완 하나씩 직접 작성하고 실제 동작을 확인한다.
4. 변경 목록과 공용 파일 영향을 확인한다. 관계없는 파일은 포함하지 않는다.
5. 변경 범위를 검토하고 Commit·Push·PR을 진행한다. PR base는 `dev`다.
6. 최소 한 명의 리뷰와 수정 요청 반영, 승인 후 dev 병합은 별도 팀 단계다. 로컬 구현 완료와 팀 통합 완료를 구분한다.
