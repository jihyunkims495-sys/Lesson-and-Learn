# A·B·C안 GA4 측정 지표 명세

- 버전: v1.0
- 작성일: 2026-10-21, Asia/Seoul
- 대상 기간: 2026-10-20~2026-10-21
- 독자: ONEPIECE 기획·개발·분석 담당자
- 관련 문서: [가상 회원 180명 정의](../01-customer-analysis/2026-10-21-04-virtual-members-180-spec.md), [GA4 설정·검증 프로세스](./2026-10-21-05-abc-ga4-setup-process-spec.md)

## 1. 측정 목적과 비교 대상

브랜드를 인지한 20~30대 패션 중·고관여 회원이 상품을 탐색하고 구매를 결정하는 과정을 관찰한다. 탐색이 충분히 제공되는지, 구매 결정 이후 불필요한 마찰이 있는지 확인한다.

| 구분 | 의미 | 분석 용도 |
| --- | --- | --- |
| A안 | SAN SAN GEAR 레퍼런스 클론 | 레퍼런스의 탐색·장바구니·결제 진입 구조 분석 |
| B안 | ONEPIECE 바이브코딩 구현 | C안과 비교할 ONEPIECE 구현 |
| C안 | 팀원이 도메인별로 직접 구현하는 ONEPIECE | B안과 탐색·구매 여정 비교 |

주 비교는 B·C다. A에 승인 결제까지 구현하지 않는 동안 A는 공통으로 구현된 단계까지만 비교한다. 구현 방식 외에 상품·가격·재고·인증·결제 조건까지 다르면 UI 차이만의 효과라고 해석하지 않는다.

핵심 가설은 **PC 웹에서 상품을 충분히 탐색한 회원이 동일 서비스의 모바일 웹에서 같은 장바구니를 열고 빠르게 결제로 진행할 것이다**이다. 현재 구현 대상으로 확정한 채널은 휴대폰 브라우저의 모바일 웹이다. FGI 고객의 원래 동일 브랜드 앱 사용 경험과 구분한다.

## 3. 집계 단위와 공통 규칙

1. **고객**은 고유 가상 회원, **실행**은 한 고객이 특정 안·버전에서 수행한 한 번의 과업, **이벤트**는 실행 중 발생한 개별 행동이다.
2. 기본 비교 단위는 동일한 안·버전·코호트·과업의 유효 실행이다. 재시도는 별도 실행 ID로 기록한다.
3. 분모와 분자는 같은 관찰 구간·버전·조건을 사용한다. 분모가 0이거나 계측되지 않았으면 0%가 아니라 산출 불가로 표시한다.
4. 퍼널은 같은 실행에서 시간 순서를 충족한 경우에만 연결한다. 단계 도달 실행 수는 한 실행당 한 번 센다. 반복 클릭 횟수는 별도 지표다.
5. 이탈은 정해진 관찰 구간 안에 다음 단계가 확인되지 않은 상태다. 고객이 싫어해서 떠났다는 원인까지 증명하지 않는다. GA4 이탈률·반송률과 프로젝트 퍼널 이탈률을 혼용하지 않는다.
6. 강제 실패·취소·사이즈 입력 오류 같은 기능 QA는 일반 행동 실험에서 분리한다.
7. 6명 파일럿은 기능·계측 검증이다. AI 고객 결과는 배정 조건에서 나타난 시뮬레이션이며 실제 시장의 선호나 통계적 유의성을 보장하지 않는다.

## 4. 구매 퍼널과 이벤트 정의

현재 합의한 실험 종료점은 `payment_button_click`이다. Toss API는 연결하지 않는다. 아래 승인·구매·환불 이벤트는 후속 설계이며 이번 행동 실험의 완료·전환 집계에서 제외한다.

| 단계 | 이벤트 | 발생 기준 | 현재 조건 |
| --- | --- | --- | --- |
| 메인·페이지 방문 | page_view | 실제 경로 조회. SPA 이동 중 중복 전송 방지 | 기본 수집 경로 있음 |
| 목록 탐색 | view_item_list | 상품 목록을 보여줌 | 화면에 실제 노출된 카드의 노출 계측과는 구분 |
| 상품 선택 | select_item | 목록에서 상품 선택 | 상세 도달 여부는 view_item으로 재확인 |
| 상세 조회 | view_item | 특정 상품 상세 표시 | 상품·옵션·가격 식별 필요 |
| 실제 담기 | add_to_cart | 공통 Cart에 상품이 실제 추가됨 | 클릭 시도만으로 전송하지 않음 |
| 담기 실패·시도 | add_to_cart_attempt | 사이즈 미선택 또는 연결 미완료 등 | 성공 퍼널에서 제외하고 오류 진단에 사용 |
| Cart 확인 | view_cart | Cart 화면 또는 Drawer에 담긴 상품 표시 | surface 구분 필요 |
| 주문 진입 클릭 | checkout_click | 주문 화면으로 가는 CTA 클릭 | 주문서 도달과 구분 |
| 주문서 진입 | begin_checkout | 유효한 담긴 상품으로 실제 주문서 표시 | 기존 click_only 진입과 신규 Toss 주문을 구분 |
| 결제 버튼 | payment_button_click | Toss 버튼 클릭 | 기존 payment_mode=click_only 기록은 승인과 무관 |
| 테스트 결제 완료 | purchase | 서버가 Toss 테스트 승인 성공 및 주문 paid 상태를 확인 | B/C 후속 연결·검증 필요 |
| 환불 | refund | 승인 주문의 취소·환불을 실제 반영 | 후속 범위. 단순 화면 닫기와 구분 |

A 로컬의 checkout_mock_click은 로컬 Checkout 시연이다. 이를 begin_checkout 또는 purchase로 이름만 바꾸어 승인 결과로 취급하지 않는다.

승인 구매 이벤트는 고유 transaction_id, currency, value, items를 포함한다. transaction_id는 안·테스트 회차까지 구분 가능한 주문 식별자로 중복을 방지한다. value는 상품 금액 기준을 일관되게 사용하고 배송비·세금은 별도 항목과 대조한다. 결제 실패·취소·결과 페이지 새로고침에 purchase를 새로 발생시키지 않는다. 테스트 구매금액은 실제 매출과 분리한다.

## 5. 핵심 퍼널 지표

표의 실행 수는 중복 제거한 유효 실행 수다. 전환에는 동일 실행의 선행 단계가 필요하다.

현재 최종 지표는 **결제 버튼 클릭 도달률 = 결제 버튼을 클릭한 유효 실행 / 유효 시작 실행**이다. 주문서 이후의 진행률은 결제 버튼 클릭 실행 / 주문서 도달 실행으로 구분한다. 아래 승인·구매 금액·환불 관련 지표는 후속 설계이며 이번 집계에서 제외한다.

| 지표 | 계산·정의 | 확인할 질문 |
| --- | --- | --- |
| 목록 도달률 | 목록 도달 실행 / 메인 시작 실행 | 상품 탐색으로 쉽게 진입하는가? |
| 상세 도달률 | 목록→상세 도달 실행 / 목록 도달 실행 | 목록에서 상품을 고를 수 있는가? |
| 상세→담기율 | 상세→담기 성공 실행 / 상세 도달 실행 | 정보 확인 후 담기로 이어지는가? |
| 담기→주문서 도달률 | 담기→주문서 도달 실행 / 담기 성공 실행 | Cart 이후 마찰이 있는가? |
| 주문서→승인 전환율 | 주문서→테스트 승인 실행 / 주문서 도달 실행 | 결제 완료까지 진행되는가? |
| 전체 테스트 구매 전환율 | 테스트 승인 1건 이상 실행 / 유효 시작 실행 | 과업에서 최종 승인까지 도달하는가? |
| 단계별 이탈률 | 1 − 다음 단계 도달 실행 / 해당 단계 도달 실행 | 어느 단계에서 중단이 나타나는가? |
| 결제 승인율 | 승인된 결제 시도 / 서버에 기록된 유효 결제 시도 | 요청·실패·재시도가 어떻게 나뉘는가? |
| 테스트 주문 금액·객단가 | 승인 주문의 상품금액 합계 및 합계 / 승인 고유 주문 수 | 과업·예산별 주문 구성이 어떤가? |
| 구매 소요시간 | 실행 시작→승인, 주문서 진입→승인 시간 | 탐색과 결제에 각각 시간이 얼마나 걸리는가? |

Toss 버튼 클릭 수는 결제 요청 API 호출 수와 다르다. 승인율의 분모는 실제 시도 기록을 사용한다. 중앙값·복잡한 실행별 시간 분석은 원시 실행 로그 또는 별도 분석이 필요할 수 있으며 현재 이벤트 비교 보고서가 자동 계산하는 값은 아니다.

## 6. 요청한 UI별 측정 지표

아래 새 이벤트명은 **추가 계측 제안**이다. 기존에 모두 배포됐다는 뜻이 아니다. 노출 판정 기준과 호버 최소 지속시간은 본 실행 전에 확정한다.

| UI | 지표·분모 | 필요한 계측 | 현재 보완점 |
| --- | --- | --- | --- |
| 상품 호버 | 호버 실행 / 카드 노출 실행, 노출 카드당 호버 횟수·지속시간 | product_card_impression, product_hover, duration_ms | CSS 호버만으로 GA에 자동 수집되지 않음. 별도 구현 필요 |
| 3·4·6열 그리드 | 변경 실행 / 선택기 노출 실행, 선택 열 분포, 변경 후 상세 도달 | grid_control_impression, grid_change | 변경 코드 있음. 노출 분모·매개변수 표준화 필요 |
| 중앙 카테고리 내비게이션 | 클릭 실행 / 메뉴 노출 실행, 클릭 후 상세·담기 | navigation_impression, navigation_click | category·위치·destination 구분 필요. 클릭 수만으로 위치의 우수성 확정 불가 |
| 우측 Cart Drawer | 열기→View Cart, 열기→Checkout, 닫기 후 재탐색 | Drawer 열기·닫기, view_cart_click, checkout_click, surface | A panel_open, B cart_drawer_open 등 기존 이름 차이 정리 필요 |
| View Cart 대 Checkout | 각 버튼이 노출된 실행 중 클릭 실행 비율, 이후 주문서·승인 도달률 | 버튼 노출, button_id, surface, 후속 퍼널 | 동일 노출 조건에서 비교. 두 버튼을 순서대로 누른 실행도 보존 |
| Cart 넣기·빼기 | 삭제·수량 변경 실행 비율, 담긴 상품 수 변화, 추가 탐색 | add_to_cart, remove_from_cart, cart_quantity_change | 수량 감소와 상품 행 삭제 사유를 구분하면 해석에 도움 |
| 로그인·채팅·Cart·검색 | 기능별 클릭 실행 / 해당 기능 노출 실행 | header_action_impression, header_action_click, feature | 링크 이동 수집만으로 전체 아이콘 클릭을 측정했다고 보지 않음 |
| 상품 정보 확인 | 실측·소재·관리 안내를 연 실행 비율, 확인 후 담기 | size_guide_open, product_info_toggle 또는 안별 기존 이벤트 | 이벤트명·section_name·open/close 기준 통일 필요 |

그리드 값은 A의 previous_columns/grid_columns와 B/C의 from_columns/to_columns가 다르다. 비교 시 표준 from_columns/to_columns로 매핑하고 과거 기록을 소급 변경했다고 주장하지 않는다. Cart 위치도 A cart_surface와 B/C surface의 매핑이 필요하다.

관찰 결과가 ‘많이 클릭했다’면 사용 빈도를 뜻한다. 유용성·레이아웃 효과는 과업 완료·시간·오류와 함께 해석한다. 위치의 인과 효과를 주장하려면 위치 외 조건을 통제한 비교가 필요하다.

## 7. PC→모바일 웹 가설 지표

| 지표 | 정의 | 선행 조건 |
| --- | --- | --- |
| Cart 복원 일치율 | 전환 후 상품·옵션·수량이 같은 실행 / 전환 시도 실행 | 동일 회원의 서버 Cart, 실제 두 기기 또는 검증 가능한 분리 환경 |
| 모바일 Cart→주문서 도달률 | 복원된 Cart에서 주문서로 간 실행 / 복원 성공 실행 | 채널·실행 연결 |
| 모바일 승인 도달률 | 모바일에서 테스트 승인된 실행 / 전환 시도 실행 | Toss 테스트 승인·User-ID |
| 모바일 결제 진행시간 | 모바일 Cart 표시→Checkout 및 승인까지 시간 | 기기별 시각과 동일 실행 매핑 |

현재 A Cart는 localStorage다. 창 크기만 모바일로 바꾸는 것은 실제 기기 간 Cart 공유 증거가 아니다. ‘충분한 탐색’·‘바로 결제’의 시간·행동 기준은 미정이다. 에이전트에게 강제로 전환시킨 결과로 실제 고객의 자발적 채널 선호를 입증하지 않는다.

## 9. GA4에서 보는 방법과 본 실행 전 조건

- 즉시 검증: DebugView에서 실행 ID·이벤트·매개변수 대조, 실시간에서 수집 여부 확인.
- 처리 후 비교: 보고서에서 A·B·C 호스트 또는 site_variant 조건을 적용한 행동 비교. 현재 보고서는 이벤트 수·총 사용자·사용자당 이벤트 중심이다. 모든 퍼널·비율을 자동 제공하지 않는다.
- 퍼널: 탐색의 유입경로 탐색에서 단계·순서·구간을 설정한다. User Explorer는 회원 식별 조건을 검증한 뒤 개별 여정 확인에 사용한다.
- 세분화: site_variant, 고객 성향, 진입 전 구매 이력, 예산, 과업, 실험 버전. 가상 age_band는 GA 기본 추정 연령과 다르다.
- 보고서용 낮은 범주 수의 매개변수·속성은 맞춤 정의가 필요하다. 사용자 ID는 전용 User-ID 설정을 사용하고 맞춤 측정기준으로 등록하지 않는다.
- 개발자·내부 트래픽 제외 필터, 분석 동의, 날짜 범위, 호스트 필터를 확인한다. 로컬 A는 배포 호스트 3개만 포함한 기존 비교 보고서에서 제외된다.
- 일반 보고서·맞춤 정의 반영에는 보통 24~48시간이 걸릴 수 있다. DebugView 수신 확인을 위해 기다릴 필요는 없고, 시간이 지나도 미전송 이벤트가 자동 생성되지는 않는다.

본 실행 완료 기준은 **공통 상품·과업·버전 고정 → 안별 실제 담기·회원 연결 → 추가 UI 계측 → 맞춤 정의·필터 점검 → 6명 검증 → 실행 계획 확정 → 180명 확대**다. 각 안의 반복 수·순서·관찰 종료 기준은 아직 확정해야 한다.

## 10/21 추가 확인 — 모바일 웹 관찰값

B/C의 새 Vercel 주소에서도 기존 웹 스트림을 사용한다. 모바일 웹의 플랫폼 값은 web이며 기기 카테고리 mobile과 구분한다. 기기 카테고리·국가·시/군/구·세션 소스/매체는 실제 접속에서 수집하는 기본 차원이다. 해당 고객의 CSV 나이·기기 계획·가상 거주지로 자동 채워지지 않는다.

모바일 수집에는 실제 모바일 브라우저 접속 또는 검증 가능한 기기 환경, 태그 로딩과 분석 동의가 필요하다. 휴대폰에서의 실제 이벤트·기기 분류 수신은 별도로 확인해야 한다. 본 실험의 방문 유입은 합성 트래픽이므로 실제 고객 획득 성과로 해석하지 않는다.
