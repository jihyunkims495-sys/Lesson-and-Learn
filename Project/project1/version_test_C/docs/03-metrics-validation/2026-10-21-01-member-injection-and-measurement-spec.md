# 가상 회원 생성·행동 실행·GA4 측정 절차

- 작성일: 2026-10-21
- 상태: 6명 브라우저 로그인·로컬 A 계측 스모크 실행 완료. GA4 Checkout 시연 6건 수신 관찰, 3개 실행 ID 상세 표본 대조. 선행 환경 Auth 180명 준비와 팀 환경 Auth 6명 검증은 구분하며, 180명 본 행동 실험은 미시작.
- 관련 가설: [B·C PC 웹→모바일 웹 구매 여정](../02-service-planning/2026-10-21-02-bc-web-mobile-hypothesis-spec.md)
- 대상 프로필: [가상 회원 180명 정의](../01-customer-analysis/2026-10-21-04-virtual-members-180-spec.md)
- 현재 데이터: revision3, 180명·27개 컬럼. 기존21컬럼 값을 보존하고 가설·B/C 비교·모바일 이어가기·Cart 공유·Checkout 목표 조건6개를 추가했다. 이 값은 실행 계획이며 성공 결과가 아니다.

## 1. ‘주입’의 의미

CSV를 GA4에 업로드하는 작업이 아니다. 프로필을 실제 테스트 회원 계정과 연결하고, 그 회원으로 로그인한 AI 에이전트가 브라우저에서 상품을 탐색·선택·수정하게 한다. 사이트에 연결된 태그가 그 행동의 이벤트를 GA4에 보내도록 한다.

프로필 180개 → 실제 인증 계정 → 회원별 브라우저 실행 → 사이트의 실제 상태 변화·이벤트 → GA4 수신 대조 순서다. 계정 수, 실행 수, GA4 사용자 수, 이벤트 수를 각각 기록한다.

## 3. 단계별 실행

### 단계 1 — 실제 테스트 계정 생성

먼저 선정한 6명만 실제 Supabase Auth 계정으로 만들고, 성공 후 나머지로 확대한다. 실험용 이메일 식별자와 회원별 비밀번호는 일반 회원 데이터·공유 CSV와 분리한다. 일반인의 이메일 주소로 일괄 가입 메일을 보내는 방법은 사용하지 않는다.

관리자 계정 생성은 서버에서만 처리한다. 관리자 자격정보와 회원별 비밀번호를 브라우저 코드·GA4·공유 문서·Git에 포함하지 않는다. 계정별 인증 상태를 확인하고 기존 회원과 프로젝트 전체의 이메일 확인 정책에 영향을 주지 않도록 한다.

계정 매핑에는 synthetic_member_key, 인증 회원 ID, 계정 생성 상태를 남긴다. 재실행할 때 같은 회원을 중복 생성하거나 기존 사람 계정의 비밀번호를 바꾸지 않도록 설계한다.

purchase_stage_at_entry는 실험에 배정한 진입 전 이력이다. 실제 과거 주문을 만들거나 GA4에 과거 purchase를 전송해 해당 유형을 꾸미지 않는다.

### 단계 2 — GA4의 회원·성향·실행 식별 연결

실제 인증 상태를 확인한 뒤 회원 ID를 GA4 전용 User-ID에 설정하고, 로그아웃 시 해제한다. User-ID를 맞춤 측정기준이나 일반 사용자 속성으로 중복 등록하지 않는다.

| 값 | 역할 | 사용 방법 |
| --- | --- | --- |
| user_id | 로그인한 회원의 일관된 식별 | Google 태그 전용 설정값. 웹·모바일에서 같은 회원을 연결 |
| experiment_id | 이번 실험 구분 | 버전 고정 시 동일한 실험 ID 사용 |
| site_variant | A/B/C 사이트 구분 | 현재 A는 sansan_clone. B/C 값과 의미는 명시적으로 정함 |
| test_run_id | 개별 실행 구분 | 회원·대상 버전·시도별 고유 값. 실행 로그 및 수신 대조에 사용 |
| is_synthetic | 가상 고객 실행 표시 | 사람의 QA·실제 고객 행동과 구분 |
| age_band | 가상 프로필 연령 | 사용자 지정 분류. GA4 기본 연령이 아님 |
| purchase_stage_at_entry | 초기 구매 이력 시나리오 | prior_0 / prior_1 / prior_2plus |
| decision_policy | 6개 행동 유형 | CSV의 확정 코드와 일치시킴 |
| budget_band / shopping_mission | 예산·과업 조건 | 성향 비교 시 과업 차이를 함께 확인 |

낮은 범주 수의 연령·성향·초기 구매 이력 등을 보고서에서 분류하려면 수집 코드와 맞춤 정의를 함께 준비한다. 회원별 고유 ID와 실행 ID를 모두 보고서용 맞춤 측정기준으로 늘리지 않는다. CSV만 읽거나 URL에 회원 번호를 적는 것으로 인증·성향 연결이 완료되지 않는다.

A의 persona URL 인자는 기존 예시 ID 2개를 위한 호환 기능이다. 6명 파일럿 계측은 해당 URL 인자를 신뢰하지 않고 실제 로그인 계정의 app_metadata.onepiece_fixture에서 검증한 성향을 사용하도록 보강했다. 로그아웃 때 해제하며 User-ID는 전용 설정으로만 사용한다. 계정 생성·브라우저 로그인·GA4 수신은 각각 별도 검증 항목으로 기록한다.

### 단계 3 — 회원별 브라우저 행동 실행

1. 회원마다 쿠키·인증·저장소가 섞이지 않는 브라우저 환경을 준비한다. 새 탭만 여는 것은 회원 격리를 보장하지 않는다.
2. 준비 단계에서 해당 회원으로 로그인한다. 측정 시작은 합의대로 메인·빈 Cart이며, 준비 로그인과 본 탐색의 시간을 구분한다.
3. 에이전트에 구매 과업·예산·정보 확인 기준을 제공한다. 원하는 결과를 만들기 위한 강제 클릭 수·강제 이탈률·강제 구매율은 지정하지 않는다.
4. 실제 페이지 정보로 판단하고, 정보가 없거나 예산에 맞지 않으면 대체 탐색·부분 구매·보류 이유를 기록한다.
5. 실제 UI 조작, 화면 경로, 시각, 선택 상품·옵션·수량, 오류와 종료 이유를 실행 기록에 남긴다.
6. PC→모바일 웹 흐름은 같은 회원·같은 여정으로 연결하고 Cart 복원을 확인한 뒤 진행한다.

화면 크기만 바꾼 테스트는 모바일 레이아웃·조작 검증이다. 실제 휴대폰의 다른 브라우저 저장소에서 Cart를 복원했다는 증거로 사용하지 않는다. 실행 도구의 기기·세션 분리 지원도 사전에 확인해야 한다.

### 단계 4 — 행동과 GA4 이벤트 대조

목록 노출, 상품 선택·상세 조회, 담기·삭제·수량 변경, Cart 조회, Checkout 버튼 클릭을 사이트의 실제 동작에 연결한다. UI 버튼 클릭, Checkout 화면 진입, 결제 승인 완료는 각각 다른 사건으로 관리한다.

| 실제 행동 | 이벤트 의미 |
| --- | --- |
| 목록·상세 표시 | view_item_list / view_item |
| 상품 선택 | select_item |
| 장바구니 담기·빼기 | add_to_cart / remove_from_cart |
| Cart 표시 | view_cart. page/drawer를 구분 |
| Checkout 버튼 클릭 | 클릭 이벤트. 위치와 출발 화면을 함께 기록 |
| Checkout 화면 진입 | 실제 구현된 화면·주문 시작 상태를 확인한 경우 begin_checkout |
| 결제 승인·주문 저장 | 실제 검증된 승인에만 purchase. 모의 클릭은 제외 |

현재 A의 Checkout은 checkout_mock_click인 시연 흐름이다. B의 실제 측정 가능한 범위와 공통 종료점을 맞추기 전에는 단순 이벤트 이름만 보고 같은 구매 성공으로 합산하지 않는다. 호버·그리드·카테고리·Cart CTA 등 추가 UI 계측의 존재와 중복·누락도 확인한다.

### 단계 5 — 파일럿 후 180명으로 확대

먼저 6명으로 계정별 식별, 초기 조건, 정상·예외 행동, Cart 공유, 이벤트 중복·누락을 점검한다. 실행 로그의 회원·버전·실행 ID·행동과 DebugView 실제 수신을 대조한다. 정상 파일럿 전에는 전체를 실행하지 않는다.

확대 실행에서는 같은 프로필이 B와 C에서 같은 조건을 받도록 하고 상품·가격·재고·기기·버전·모델·지시문을 고정해 기록한다. 동일 180명을 두 사이트에서 각각 실행하면 회원 수와 전체 여정 수가 달라지므로 전체 실행 횟수·순서는 실행 전에 확정한다. 재시도는 신규 회원으로 세지 않는다.

일반 보고서와 맞춤 정의의 처리 지연을 고려하되, 디버그·내부 트래픽 필터로 테스트가 제외되는지도 점검한다. 앞서 만든 팀 배포본 비교 보고서는 배포 도메인만 포함하도록 설정되어 있으므로, 해당 필터가 유지되는 동안 로컬 실행은 별도 DebugView·테스트 보기에서 확인한다.

## 4. 두 가지 검증을 구분

- 경로 재현·계측 검증: PC에서 담고 모바일에서 Cart를 열도록 지시해 기능·연결·단계·이벤트를 확인한다. 이 트랙의 전환율은 자연스러운 채널 선호를 증명하지 않는다.
- 고객 행동 가설 검증: 실제 타깃 사용자에게 구매 채널을 강제하지 않고 관찰한다. AI 시나리오 결과를 2030대 전체의 선호·실제 구매 전환율·통계적 우열로 일반화하지 않는다.

## 5. 현재 다음 미완료 단계

10/21에는 6명 실제 브라우저 로그인·계측 스모크를 수행했다. 180명 계정 준비와 180명 본 행동 실행은 다른 단계다. 본 실행은 추가 UI 계측·GA 보고서 분류 및 공통 실행 조건을 확인한 뒤 진행한다. 프로필의 초기 account_status·execution_status와 실제 실행 결과를 구분한다. PC·실제 휴대폰 Cart 공유는 아직 검증이 필요하다.

## 팀 Supabase 전환 준비 — 2026-10-21

B·C는 공통 팀 Supabase 환경을 기준으로 같은 성향의 파일럿 6명을 별도로 생성·검증한다. 선행 환경의 Auth 180명 준비 결과를 팀 환경의 계정 준비·행동 실행 결과와 합산하지 않는다.

- C의 Supabase 연결 설정은 준비됐으나, 해당 설정의 배포 반영·브라우저 로그인 검증은 당시 미완료다.
- B 정적 시연 모드의 실제 Supabase 회원·Cart·주문 연결은 미완료다.
- 팀 Auth 파일럿 6명 생성·재조회 완료. 실제 Auth API 로그인 및 본인 profiles id 조회도 6명 모두 통과했다. 동일 파일럿 6명으로 수행한 B/C 브라우저 여정과 GA 수신은 별도 미검증이다.
- 선행 환경의 파일럿 성공을 팀 환경의 성공으로 간주하지 않는다. 팀 DB·B/C 브라우저 행동·GA 이벤트를 새로 대조한다. 결제 승인 연동은 버튼 클릭 검증과 구분한 후속 항목이다.
